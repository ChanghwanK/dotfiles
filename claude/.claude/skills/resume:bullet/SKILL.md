# resume:bullet Skill

Eng Note 또는 대화에서 완료된 작업의 핵심 성과를 추출해, 이력서용 1줄 bullet과 경력기술서용 PAAR을 함께 만든다.

---

## 핵심 원칙

- **증거 기반**: 문서·대화에 없는 성과를 추측해 넣지 않는다. 정량 수치가 없으면 `[N%]` 같은
  플레이스홀더로 남기고 가짜 수치를 채우지 않는다.
- **산출물과 효과를 구분**: PR·문서 개수 같은 산출물이 아니라 비용·시간·에러율처럼 독자에게 가치가
  읽히는 효과만 Result로 쓴다.
- **포맷 표준은 별도 문서를 따른다**: 이력서 bullet은 `~/.claude/docs/resume-format-convention.md`,
  PAAR은 `~/.claude/docs/par-format-convention.md`(프로파일 A) 기준을 그대로 적용한다
  (이 스킬 안에서 규칙을 재정의하지 않는다).
- **task:review와 역할 분리**: 같은 세션에서 방금 끝난 작업을 성과측정 + 성장회고까지 깊게 하고
  싶다는 요청이면 `task:review`로 안내한다. 이 스킬은 이미 문서화된 작업에서 이력서/PAAR만 빠르게
  뽑는 용도다.

---

## 워크플로우

### Step 0: 입력 소스 판별

- 사용자가 Notion URL(Eng Note, Task, 또는 다른 페이지)을 줬으면 그 문서를 분석 대상으로 삼는다.
- URL이 없으면 현재 대화 맥락에서 작업 내용을 스캔한다 (Step 1과 동일한 추출 스키마 적용).

### Step 1: 문서/대화 fetch 및 성과 추출 ("체크")

**URL이 있는 경우**, URL에서 page UUID를 추출해 조회한다:

```
mcp__notion-personal__API-retrieve-page-markdown(page_id=<UUID>)
```

404나 권한 오류로 실패하면 `mcp__claude_ai_Notion__notion-fetch(id=<원본 URL>)`로 폴백한다.

**URL이 없는 경우**, 대화를 처음부터 끝까지 스캔해 무엇을 하려 했고 무엇을 했는지 확정한다.

**공통 추출 스키마** (문서든 대화든 아래 4항목으로 정규화한다):

| 항목 | 추출 기준 |
|------|-----------|
| Problem | 어떤 상황·문제였는가. Before 수치가 있으면 포함 |
| Analyze | 어떤 후보(가설·대안)를 비교했고 왜 그 방법을 택했는가. 기각한 후보와 근거가 드러나야 함. 문서에 없으면 `대안 검토 없음` |
| Action | 어떤 방법·기술로 실행했는가 |
| Result | 정량 After 수치. 불가능하면 검증 가능한 정성 표현("추적 가능성 확보" 등) |
| Role | 본인이 직접 수행한 범위. 팀·타 조직과 협업한 부분은 협업으로 구분 |

**Role은 문서에 명시돼 있을 때만 채운다.** 근거가 없으면 `미확인`으로 두고 사용자에게 물어본다.
Eng Note는 보통 "누가 했는가"를 적지 않으므로, 이 항목을 추론으로 채우면 팀 성과가 1인칭 단독
성과로 둔갑한다. 면접·평가에서 가장 먼저 검증되는 지점이다.

성과가 여러 개 섞인 문서·대화면 각각에 대해 위 4항목을 추출한다.

추출 후 사용자가 분석 대상이 맞는지 확인할 수 있도록 짧게 보여준다:

```
**분석 대상**: {문서 제목 또는 "현재 대화"}
**핵심 성과**: {Problem 한 줄} → {Analyze 한 줄} → {Action 한 줄} → {Result 한 줄}
**기여 범위**: {본인 수행 범위 / 협업 범위, 근거 없으면 "미확인"}
```

성과가 여러 개면 임팩트 순으로 나열한다. 하나의 문서·대화에 서로 무관한 프로젝트가 여러 개
섞여 있으면, 어느 것을 이력서용으로 뽑을지 사용자에게 먼저 확인한다.

### Step 2: 이력서 bullet 생성

`~/.claude/docs/resume-format-convention.md`를 Read로 읽고 그 기준을 **그대로** 적용한다.

이 스킬은 그 문서의 규칙을 요약하거나 재정의하지 않는다. 요약본을 두면 원본이 개정돼도 출력이
따라가지 않고, 요약에서 빠진 규칙이 검증에서도 함께 누락되기 때문이다.

이 스킬에만 있는 규칙은 아래 하나뿐이다:

- 성과가 여러 개면 임팩트 순으로 최대 3개까지 생성한다.

### Step 3: 경력기술서 PAAR 생성

`~/.claude/docs/par-format-convention.md`를 Read로 읽고 **프로파일 A(채팅 간이형)** 를 그대로
적용한다. PAAR 구성, 작성 규칙, 출력 템플릿, 품질 체크가 모두 그 문서에 있다. 이 스킬은 PAAR 규칙을
요약하거나 재정의하지 않는다.

이 스킬에만 있는 규칙은 아래 둘이다:

- 성과가 여러 개면 대표 PAAR 1개를 기본으로 출력하고, 사용자가 요청하면 추가로 작성한다.
- 사용자가 Notion에 옮겨 적겠다고 하면 프로파일 B(레이블 이탤릭 + 하위 불릿 중첩, Analyze/Action/Result
  그룹핑)로 다시 써준다.

### Step 4: 출력

Step 2(이력서 bullet)와 Step 3(PAAR)을 채팅으로 함께 출력한다.

**저장은 이 스킬의 범위가 아니다.** allowed-tools가 읽기 전용이라 파일·Notion 쓰기를 수행할 수
없다. 사용자가 저장을 원하면 직접 저장하지 말고 아래로 안내한다:

- Notion Eng Note에 반영: `notion:add-engineering-note`
- 성과 측정·성장 회고까지 포함한 전체 리뷰 후 문서화: `task:review`

### Step 5: 출력 전 검증 (MUST)

출력하기 전 아래를 스스로 점검하고, 위반 항목은 그 자리에서 고친 뒤 출력한다.
bullet 항목은 `resume-format-convention.md`의 규칙과 1:1로 대응한다. 그 문서를 고쳤다면 이
체크리스트도 함께 갱신한다.

**증거**

- [ ] bullet과 PAAR의 모든 수치가 Step 1에서 실제로 추출된 값인가 (없으면 `[N%]` 플레이스홀더, 날조 금지)
- [ ] PAAR의 Result가 Step 1의 Result와 일치하는가 (Action에서 새로운 성과를 지어내지 않았는가)
- [ ] Step 1의 Role이 `미확인`인데 본인 단독 성과처럼 서술하지 않았는가 (협업 범위는 협업으로 표기)

**이력서 bullet 포맷**

- [ ] 명사형으로 끝나는가 (개선/해결/절감/전환 등, "~했습니다" 없음)
- [ ] Before 수치가 있으면 Problem 절에 포함됐는가 (After 수치 또는 검증 가능한 정성 표현은 필수)
- [ ] Result가 대괄호 또는 화살표로 시각 분리됐는가
- [ ] Result 대괄호에 성과가 1개인가 (병기해도 최대 2개, 3개 이상이면 가장 강한 1개만 남김)
- [ ] 구현 산출물 수치(룰 개수, 파일 수, PR 수)를 Result로 쓰지 않았는가
- [ ] 진단 메커니즘·구현 디테일(룰/API/스크립트 이름)이 bullet에 없는가 (PAAR의 Analyze·Action 몫)
- [ ] 기술명이 나열이 아니라 Action의 근거로 쓰였는가
- [ ] 사내 서비스명·도구명이 외부인이 아는 일반 용어로 치환됐는가
- [ ] 공백 포함 110자 하드캡 이내인가 (90자 권장). 넘치면 내용을 자르지 말고 디테일을 PAAR로 내린다

## Eng Note 포맷별 매핑 가이드

- **장애/실패 4섹션**(문제 요약/문제 원인/어떻게 해결/교훈): 문제 요약+원인 → Problem, 어떻게
  해결 → Action(그 안의 대안 비교·기각 근거는 Analyze), 교훈 중 정량 결과가 있으면 Result에 반영
- **Tech Spec 포맷**(문제 정의/Summary/기대 효과): 문제 정의 → Problem, 검토한 대안 → Analyze, Summary·접근 방법 →
  Action, 기대 효과 대비 실측 결과(있으면) → Result
- 위 두 포맷에 안 맞는 자유 형식 문서는 본문 전체를 읽고 Step 1 스키마로 직접 추출한다

## 워크드 예시

아래는 Tech Spec 포맷 Eng Note 1건을 처리한 전체 흐름이다. 규칙이 실제로 어떻게 적용되는지
보여주는 기준 예시이므로, 새 요청에 이 내용을 그대로 옮겨 쓰지 않는다.

**입력 (Eng Note 발췌)**

```
문제 정의: prod 로그 수집량이 늘어 로그 스토리지 비용이 월 $2,400까지 상승.
          개발자 조회는 대부분 최근 7일에 집중.
Summary:  수집 단계에서 debug 레벨 드롭 + 네임스페이스 등급별 보존 기간 분리
          (일괄 30일 → 핵심 14일 / 일반 7일)
기대 효과: 스토리지 비용 40% 절감 예상
```

**Step 1 추출**

```
**분석 대상**: 로그 파이프라인 보존 정책 개선
**핵심 성과**: 로그 스토리지 비용 월 $2,400 상승, 조회는 최근 7일에 집중
             → 수집 단계 debug 드롭 + 등급별 보존 기간 분리
             → 비용 절감 (문서에는 40% "예상"만 있고 실측 없음)
**기여 범위**: 미확인
```

**Step 2 이력서 bullet**

```
prod 로그 수집량 증가로 월 $2,400까지 늘어난 로그 스토리지 비용을, debug 레벨 드롭과
등급별 보존 기간 분리로 [N% 절감]
```

**Step 3 PAAR (프로파일 A)**

```
**Problem**
prod 로그 수집량이 증가해 로그 스토리지 비용이 월 $2,400까지 상승. 조회 패턴은 최근 7일에
집중돼 있어 비용의 상당 부분이 실제로 조회되지 않는 구간에 쓰이고 있었다.

**Analyze**
보존 기간 일괄 축소를 먼저 검토했으나, 장애 조사에 필요한 핵심 네임스페이스의 구간까지 함께
잘리므로 기각. 조회 패턴이 최근 7일에 집중된 점을 근거로 유입량 감축과 등급별 보존 분리 두 축으로
접근하기로 판단. 대가는 등급 분류의 유지 관리 부담이며, 조회 패턴이 바뀌면 등급을 다시 잡아야 한다.

**Action**
수집 단계에서 debug 레벨을 드롭해 유입량을 줄이고, 네임스페이스를 조회 빈도 기준으로 등급화해
보존 기간을 분리(핵심 14일 / 일반 7일). 핵심 등급의 보존 기간은 조회 집중 구간보다 길게 설정.

**Result**
스토리지 비용 [N% 절감]. 문서에는 40% 절감 "예상"만 있고 적용 후 실측치가 없어
플레이스홀더로 남김. 실제 청구서 기준 절감률을 알려주시면 채워 넣겠다.
```

**이 예시가 보여주는 규칙 적용**

- **기대 효과를 Result로 쓰지 않는다**: 문서의 "40% 절감 예상"은 예측이므로 `[N% 절감]`
  플레이스홀더로 두고 실측치를 요청한다. 이 스킬에서 가장 흔한 오류다.
- **산출물 수치를 Result로 쓰지 않는다**: "드롭 룰 N개 추가", "네임스페이스 N개 등급화"는
  독자에게 가치가 읽히지 않으므로 bullet에 넣지 않는다.
- **판단 근거는 PAAR로 내린다**: "왜 일괄 축소가 아니라 등급 분리인가"는 bullet 110자 안에
  들어가지 않으므로 PAAR의 Analyze가 받는다.
- **기여 범위가 미확인이면 단독 성과처럼 쓰지 않는다**: PAAR의 Action을 "설계했다"가 아니라
  수행한 내용 중심으로 서술하고, 확정되면 그때 주어를 명확히 한다.

## 주의사항

- 정량 수치가 대화·문서 어디에도 없으면 절대 지어내지 않는다. 플레이스홀더로 남기고 사용자에게
  실측치를 물어본다.
- Notion 문서 URL은 `notion-personal` 워크스페이스 연결을 우선 시도한다. 다른 워크스페이스
  소속 문서라 404가 나면 `claude_ai_Notion`으로 폴백하고, 그래도 실패하면 사용자에게 접근 권한
  문제일 수 있음을 알린다.
