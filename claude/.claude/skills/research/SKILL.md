# research Skill

## 핵심 원칙 (두 모드 공통)

- **인용 강제**: 모든 주장 뒤에 인라인 `[n]`, 하단 References에 `[n] → 제목/URL/tier/date`. 주장 신뢰는 confidence grade(높음/중간/낮음) 하나로 표기한다. 산정 규칙, stale 판정, tier 정의는 `references/source-tiers.md`
- **환각 금지**: `WebFetch`로 실제 확인한 내용만 쓴다. 검색 스니펫만 보고 단정하지 않는다. 소스가 상충하면 어느 소스가 무엇을 말하는지 쓴다
- **읽기 전용**: 조사·정리·인용까지만 한다. 저장은 마지막에 한 줄 제안만 하고 자동 실행하지 않는다
- 웹 공개 문서 전용이다. 사내 문서는 Slack/Notion MCP 검색 도구나 devops-wiki로 보낸다

## 모드 판별

애매하면 표준 모드로 가되, 사례·인사이트 신호가 있으면 blog-insight로 간다.

| 모드 | 발동 신호 | 무게중심 |
|------|-----------|----------|
| **표준 (tier-cascade)**: 워크플로우 A | 정의·스펙·버전·개념, "~가 뭐야", "어떻게 동작해" | T1 공식 문서 우선, 하위 tier는 공백 보완. 커뮤니티부터 검색하지 않는다 |
| **blog-insight**: 워크플로우 B | "운영사례", "실전 사례", "다른 회사는 어떻게", "블로그 사례", "인사이트 도출", 장애 회고·마이그레이션 서사 | 국내외 엔지니어링 블로그가 1차 소스. 블로그가 말하는 사실(버전·동작·수치)은 T1/T2로 교차 검증 |

출력 템플릿과 규칙은 모드별로 `assets/output-format.md`를 Read해 따른다.

## 워크플로우 A: 표준 조사

### Step 1: 쿼리 분해

서브질문으로 나눈다(1개로 명확하면 생략). 축은 대상에 맞게 고른다: 정의/개념, 동작 원리, 버전/변화(GA/deprecated/breaking), 실무 함정, 운영/모범사례(운영·튜닝·마이그레이션 질의면 필수), 대안 비교(요청 시만). 환경·규모가 여럿인 질의(dev/stg/prod, 소규모/대규모)는 그 축으로도 나눈다(dev는 비용, prod는 가용성처럼 모범사례가 다르다).

### Step 2: Tier cascade 검색

0. **최신 버전 anchor** (버전 민감 주제 필수): 공식 releases/changelog를 먼저 1회 fetch해 "현재 최신 버전 + 릴리스 날짜"를 확정한다. 이후 stale 판정의 기준이다
1. **T1**: `allowed_domains`로 공식 docs 도메인을 지정한다. 쿼리에는 연도 대신 버전 번호·`release notes`·`changelog`를 넣는다(공식 문서 본문엔 연도가 거의 없어 연도 쿼리가 canonical 문서를 떨어뜨린다. 연도는 T3·뉴스성 검색에만)
   ```
   WebSearch(query="<기술> <서브질문> <버전 또는 release notes>", allowed_domains=["kubernetes.io", "github.com"])
   ```
2. 서브질문이 모두 T1으로 답해졌으면 멈춘다
3. **T2**: T1이 못 메운 서브질문만
4. **T3**: 실무 경험·최신 릴리스 반응·상세 트러블슈팅이 필요한 서브질문만. 출력에서 낮은 권위로 표기

노이즈(콘텐츠팜, SEO 스팸)는 `blocked_domains`로 뺀다. `WebSearch`는 US 기준 결과라 국내 특화 주제는 tier를 유연하게 조정한다.

### Step 3: 후보 fetch + 검증

```
WebFetch(url="<후보 URL>", prompt="<서브질문>에 답하는 내용과 게시/수정 날짜, 대상 버전을 추출하라")
```

- fetch 전에 버전드/아카이브 URL을 current/latest로 정규화한다(`source-tiers.md` "versioned docs trap"). 본문에 "out-of-date version"류 배너가 보이면 인용하지 않고 최신 경로로 다시 fetch한다
- 관련성, 스니펫과 본문의 일치, 시점(`source-tiers.md` 판정 우선순위)을 window·anchor와 비교한다. window 밖이면 버리기 전에 stale 3단계 판정을 적용한다
- **구체 산출물은 원문 그대로 받는다**: 코드·설정 블록·URL 템플릿·함수/플래그 이름이 필요하면 prompt에 "본문의 코드/예시 블록을 원문 그대로 인용하라, 요약·재작성 금지"를 넣는다. `WebFetch`는 요약 모델이라 예시를 재작성하거나 누락한다. literal 스니펫 없이 의미만 풀어 썼으면 유실 신호로 보고 한 번 더 fetch한다
- 소스가 10개를 넘으면 서브질문별 상위 소스만 채택한다. 인증 URL은 실패하고, cross-host redirect는 반환된 URL로 다시 부른다

### Step 4: 종합

서브질문별로 정리하고 주장마다 `[n]`과 confidence grade를 단다. 시간 가변 주장(기본값·API·GA 상태·수치)이 `낮음`이면 T1 재확인 전 인용하지 않는다.

**자작 예시 금지**: 코드·문법·URL 템플릿을 원문으로 확보하지 못해 직접 조합했다면 `중간`/`낮음`을 붙인 "파생 패턴"으로 내보내지 말고 Step 3으로 돌아가 원문을 다시 확보한다. 문서에 예시가 실제로 없음을 확인한 경우에만 `구성 예시(문서 미검증)`로 표기한다.

### Step 5: 실무 팁 + 함께 볼 주제

- **실무 운영팁**: 운영·모범사례·튜닝·마이그레이션 질의면 필수, 순수 개념·스펙 조사면 생략. 근거가 있으면 `[n]`
- **함께 보면 좋은 주제**: 2개 이상 필수. 원 질의의 다음 궁금증에서 파생하고 한 줄 이유를 붙인다. "보안 일반" 같은 범용 주제는 피한다

### Step 6: 출력 전 점검

- 인용 없는 주장, URL·tier·date가 빠진 References 항목이 없다
- T1을 최소 1회 시도했고, 버전 민감 주제면 현재 버전을 명시했다
- 코드·플래그·URL 템플릿 주장이 원문 그대로다(조합이면 위 자작 예시 규칙)
- T1 URL에 버전드/아카이브 경로가 남지 않았다. `stale-confirmed` 소스는 "구버전 X → 현행 Y" 서사 목적일 때만 남았다
- `낮음`인 시간 가변 주장이 없고, 벤더 자사·경쟁 비교 주장에 이해관계 하향을 적용했다
- 소스 상충을 명시했고, 함께 볼 주제 2개 이상과 (해당 시) 실무 운영팁이 있다

통과 후 저장이 유용해 보이면 한 줄 제안: `이 조사 결과를 /wiki:note 로 저장할 수 있습니다.`

## 워크플로우 B: blog-insight

seed 도메인과 관심 축 키워드는 `references/tech-blogs.md`.

### Step B1: 대상 확정

기술/도메인(예: Kafka consumer lag), 관심 축(운영·튜닝 / 장애 회고 / 마이그레이션·도입기 / 스케일링 / 비용, 복수 가능), 범위(국내·국외·둘 다, 기본 둘 다)를 정한다.

### Step B2: 탐색

국내는 한국어, 국외는 영어 쿼리로 seed 도메인을 `allowed_domains`로 묶어 각각 검색한다. 연도는 최신 글 유도용이고, 결과가 빈약하면 빼고 다시 검색한다(좋은 사례 글은 수년 전 게시가 많다).

```
WebSearch(query="<기술> <관심축 한국어> <현재 연도>", allowed_domains=[<국내 seed>, "medium.com"])
WebSearch(query="<tech> <axis in English> <현재 연도>", allowed_domains=[<국외 seed>])
```

seed에 없는 회사 사례는 애그리게이터(GeekNews `news.hada.io`, Hacker News, InfoQ)에서 찾은 뒤 원문 도메인으로 fetch한다. 번역 스크랩·SEO 요약은 `blocked_domains`로 빼고 1차 게시글만 인용한다.

### Step B3: 사례 추출

```
WebFetch(url="<사례 글 URL>", prompt="이 글의 회사, 규모/맥락, 해결한 문제, 실제 접근·해결 방법(설정값·아키텍처 변경 포함), 결과 수치, 교훈, 게시 날짜를 추출하라")
```

사례 카드 필드는 회사/출처(국내/국외), 규모·맥락, 문제, 접근·해결, 결과(남은 한계 포함), 교훈이다. 본문에 없으면 `(미상)`으로 두고 지어내지 않는다. 오래된 사례는 버리지 않되, 게시 후 메이저 변경이 있었으면 `(당시 <버전/연도> 기준, 이후 변경 있음)`을 붙여 기술 디테일과 교훈을 나눈다. 축과 무관하거나 검증에 실패한 글은 버린다.

### Step B4: 인사이트 종합 (필수)

사례 요약을 다시 나열하지 않고 교차 분석한다:
- **공통 패턴**: 여러 회사가 수렴한 접근
- **트레이드오프**: 같은 문제를 다르게 푼 이유(규모/비용/팀 역량)
- **안티패턴**: 여러 사례가 공통으로 겪은 실수·후회

신뢰도: 단일 사례 `낮음`, 독립 사례 2건 이상 수렴 `중간`, T1/T2 교차 확인까지 `높음`. 사유에 사례 수를 쓴다(예: `(신뢰 중간: 3건 수렴)`).

### Step B5: 출력 전 점검

- 사례 카드 2건 이상(1건뿐이면 "일반화 주의"를 쓰고 모범사례로 단정하지 않는다), 각 카드에 회사·원문 URL·게시일
- 인사이트마다 confidence grade(사례 수)와 근거 `[n]`
- 원문(1차 게시)만 인용

통과 후 한 줄 제안: `이 사례/인사이트를 /wiki:note(개인 wiki) 또는 /devops:wiki:ingest(팀 wiki)로 남길 수 있습니다.`
