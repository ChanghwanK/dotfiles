# tasks:capture

Notion Task DB에 Task를 만든다. 나중에 연 사람이 무슨 작업이고 무엇이 문제이고 왜 하려 했는지, 어디서부터 이어 가면 되는지를
알 수 있어야 한다. 업무 노트를 쓰기 전까지의 맥락은 `작업 Context`가 보존한다.

## 핵심 원칙

- **템플릿이 기본**: 모든 캡처는 Task 템플릿으로 만들고 섹션을 채운다
- **pass/simple일 때만 생략**: 입력에 "pass" 또는 "simple"(대소문자 무관)이 있을 때만 제목(+due)만으로 만든다(Step 2-B).
  "가벼워 보인다"는 이유로 Claude가 스스로 생략하지 않는다
- **추정으로 채우지 않는다**: 세션에서 확인되지 않은 내용은 비워 두거나 `(미확인)`으로 쓴다
- **확인은 1회**: 섹션 초안과 속성(Due/Type)을 한 화면에 모아 한 번에 확인받는다
- 출력은 완료 메시지와 제목 링크뿐이다

## 입력 파싱

| 속성 | 추출 방법 | 기본값 |
|------|-----------|--------|
| **이름** (필수) | 아래 "제목" 규칙으로 Claude가 합성 | 없음 |
| **Category** | "개인", "MY", "personal", "사적" → MY, 그 외 WORK | `WORK` |
| **Due Date** | YYYY-MM-DD 또는 "오늘"/"내일"/"이번 주 금요일"/"다음 주" → KST 절대 날짜 | 누락(아래 추천 로직) |
| **Description** | 아래 "Description" 규칙 | 템플릿 경로에서는 반드시 작성 |
| **Images** | 파일 경로, URL, 대화에 첨부된 이미지 | 없음 |
| **Type** | "Task"/"Project" 명시 또는 문맥상 명확("여러 단계로", "설계+구현+배포"). 명시가 없으면 확인 화면에 `Type: Task [추천]` | `Task` |
| **simple 여부** | "pass"/"simple" 명시 여부 | 아니오 |

**이미지**: 경로·URL마다 `--image`를 붙인다. 대화에 시각 첨부된 이미지는 `~/.claude/todo-images/<title-slug>.png`로 저장해 경로를 쓴다.
URL은 이미지 블록, 로컬 경로는 callout 텍스트로 페이지 끝(작업 Context 뒤)에 붙는다.

**제목**: 입력 전체를 제목으로 쓰지 않는다.
- 짧은 입력: 메타 키워드("개인", "pass", "simple" 등)만 지운다
- 조건·이유·배경이 붙은 입력: 동사+목적어를 담은 20~40자로 합성하고 조건·이유는 뺀다. `[카테고리 태그]`는 앞에 유지한다
- `#Task - ` / `#Project - ` 접두어는 `create-task`가 Type에 따라 붙이므로 `--name`에는 빼고 넘긴다. 확인 화면과 완료 보고는 접두어가 붙은 최종 제목(응답 JSON의 `name`)으로 보인다

**Description**:
- 템플릿 경로: 어떤 작업인지 한 줄(대상 + 무엇을 하는가). 문제·이유는 본문 섹션에 쓰고 반복하지 않는다
- simple 경로: 제목 외 추가 정보(조건·이유·배경)가 있을 때만 원문을 요약한다

예시와 엣지 케이스: `references/extraction-rules.md`

| 기본(아이디어/메모), "나중에", "언젠가", "시간 되면", "여유 될 때" | 없음 |

## 본문 섹션 (Task 템플릿)

템플릿 구조의 단일 출처는 Notion 템플릿(`notion-task.py`의 `TASK_TEMPLATE_ID`)이다. 스크립트가 템플릿을 적용하고 heading 아래를 채우며,
Claude는 sections JSON만 만든다. 값은 Markdown이고, 생략한 키는 템플릿의 빈 칸으로 남는다.

키 → heading: `problem` → `### 문제`, `root_cause` → `### 근본 원인`, `value` → `### 기대 가치`(세 H3는 `## 왜 이걸 해야하는가?` 아래),
`context` → `## 작업 Context`. 예: `{"problem": "- ...", "value": "- ...\n\n가설:\n\n- ...\n\nKey Result:\n\n- KR1: ...", "context": "출발점:\n\n- ...\n\n다음 액션:\n\n- ..."}`

### 섹션별 작성 기준

- **문제**: 관측된 사건이 아니라 그 사건을 가능하게 한 경계·장치·절차의 결함을 현재형으로 쓴다(아래 "현상을 빼고 문제를 쓴다").
  신규 구축·학습·개인 일은 "지금 없어서 불편한 것 / 막혀 있는 것"을 한두 줄로 쓴다
- **근본 원인**: 신호가 아니라 신호를 만든 메커니즘. 측정으로 확정한 원인만 사실로 쓰고, 아니면 `(원인 미확인)` 아래에 세션에서 논의한 만큼
  원인 후보와 변별 증거를 적는다(`~/.claude/docs/hypothesis-first.md` "원인 가설 단계"). 원인 개념이 없는 작업(신규 구축, 학습, 개인 일)은 키를 생략한다
- **기대 가치**: 끝나면 사람·팀이 무엇을 얻는가를 1~4 불릿으로 쓴다. 해결 가설을 세울 수 있으면 두 라벨을 붙인다
  - `가설:` 무엇을 적용하면 위 문제가 해결되는가, 한 문장
  - `Key Result:` 한 줄 지표 제목(지표 하나·목표값 하나) + 구체 기준 하위 불릿. 형식은 `task:keyresult` 스킬 "Key Result"가 정본이다.
    현재값만 알면 `현재값 → (목표 미정)`
  - 정의 전 캡처, 학습·개인 일처럼 해결할 문제가 없으면 두 라벨을 생략한다. Goals와 실행 계획은 Task가 아니라 업무 노트에서 다룬다(세 칸 구분은 `task:keyresult`)
- **작업 Context**: 이 세션을 못 본 사람이 재조사 없이 다음 액션을 시작할 수 있어야 한다. 세션에 근거가 있는 라벨만 쓴다
  - `출발점:` 어떤 알럿·대화·세션·요청에서 나왔는가(날짜 포함)
  - `확인한 사실:` 측정치·관측값과 그 값을 다시 얻는 방법(쿼리, 명령, 대시보드 이름). 시각·횟수·지속 시간·재발 이력은 문제가 아니라 여기에 둔다
  - `관련 리소스:` PR URL, 파일 경로, Grafana·Notion 링크
  - `검토한 것:` 세운 가설과 기각한 대안, 기각 근거(실제로 논의했을 때만)
  - `다음 액션:` 재개 시 첫 행동 하나
  - `미결 질문:` 아직 답이 없는 것

### 정의되지 않은 불편함에서 시작한 작업

신호: 입력이 불편함을 형용사로 말하고("코드가 복잡하다", "재사용이 어렵다") 제목이 해결책 이름(모듈화, 리팩터링, 표준화, 마이그레이션)이며,
무엇이 어떤 순간에 걸렸는지(구체 사례)가 입력과 세션에 없다. 문제를 지어내지 않고 grill-me로 넘길 수 있게 쓴다.

- 문제: `- (정의 전) {사용자가 말한 불편함 요지}` 한 줄. 현상 제거·추상화 판별은 적용하지 않는다
- 근본 원인: 키 생략
- 기대 가치: 사용자가 말한 동기를 사용자 표현에 가깝게
- `출발점:`: "정의되지 않은 불편함에서 시작"과 사용자가 한 말 그대로
- Step 1.5-B에서 문제 정의를 요구하지 않는다. 동기가 없을 때만 "이걸 왜 하고 싶으세요?"를 Due 질문과 묶어 묻는다

### 현상을 빼고 문제를 쓴다

현상은 "무엇이 일어났다"이고, 문제는 "무엇이 작동하지 않아서 그 사건이 가능했는가"다. 초안의 문장마다 아래를 적용한다.

- 날짜·시각·횟수·지속 시간·노드/파드 이름을 지워도 성립하는가? 무너지면 현상이다
- 같은 일이 또 나도 그대로 참인가? 이번 건만 설명하면 현상이다
- 주어가 사건("노드가 NotReady가 됐다")이 아니라 경계·장치·절차("노드 경계가 파드 장애를 가두지 못한다")인가
- 표준 용어(장애 격리 실패, retry storm, 자동 복구 부재 등)로 이름을 붙일 수 있는가? 못 붙이면 아직 현상이다
- 해결 대상(특정 파일·문서·도구·리소스 이름)을 지워도 성립하는가? 무너지면 해결 수단 쪽에 머문 것이다. 결함의 종류를 주어로 쓰고
  해결 대상은 근본 원인이나 근거로 내린다(예: "README 기준이 `aws_rds_cluster`를 제외한다" → "조직의 결정을 한 번 정의하고 재사용·강제하는 단위가 없다")
- 현재형으로 쓴다. 과거형이 나오면 관측을 옮겨 적고 있다는 신호다
- "하나", "매번", "일상", "방치됐다" 같은 범위·빈도·완료 표현은 증거와 대조한다
- 지운 관측값은 `확인한 사실:`로 옮긴다. 같은 사실을 두 섹션에 쓰지 않는다

예: "09-24 04:40 노드가 NotReady가 된 뒤 55시간 복구되지 않았다"(현상) → "워커 하나가 비정상이 되면 컨테이너 경계와 노드 경계가
그 장애를 가두지 못해 노드 전체로 번지고, 번진 노드를 자동 교체하는 경로가 없어 사람이 개입할 때까지 복구되지 않는다"(문제)

### 문장·포맷

- 초안 시점부터 `~/.claude/docs/notion-writing-style.md` "쓰기 시점 체크리스트"를 적용한다
- 체크리스트는 `- [ ] 항목`으로 쓴다(스크립트가 to_do 블록으로 변환). 목차 텍스트는 쓰지 않는다(템플릿의 목차 블록이 만든다)

## 워크플로우

### Step 1: 입력 파싱

"입력 파싱" 규칙으로 속성을 뽑는다(내부 처리). "pass"/"simple"이 있으면 Step 2-B, 아니면 Step 1.5로 간다.

### Step 1.5: 세션 컨텍스트 분석 게이트 (템플릿 경로)

1.5-A → 1.5-B 순서로 통과시킨다. 순서가 반대면 "정보는 많은데 전부 증상"인 경우를 걸러내지 못한다.

#### grill-me 인터뷰 결과가 있는 경우 (먼저 확인)

args나 세션에 "grill-me 인터뷰 완료"가 있으면 그 결과를 1차 입력으로 쓴다.
- 확정된 문제·목적·근거로 섹션을 합성하고 1.5-B 질문은 하지 않는다
- 인터뷰로 문제가 정의됐으면 `(정의 전)`을 쓰지 않는다
- 남은 Gap은 `미결 질문:`, 확정된 결정은 `검토한 것:`으로 옮긴다
- 1.5-A의 A5와 해결 대상 판별은 합성한 문장에 그대로 적용한다
- 호출자가 업무 노트로 이어 갈 예정이면(grill-me Option A) 완료 출력의 "다음 단계 안내" 줄을 붙이지 않는다

#### Step 1.5-A: 진짜 문제 검증 (5개 자문)

초안 전에 자문하고, 걸리면 사용자에게 묻기 전에 조회·측정으로 해소한다. 알럿·인시던트에서 파생된 Task는 A1·A2를 건너뛸 수 없다
(근본 원인은 알럿 아래의 메커니즘에, 여파는 같은 메커니즘이 건드린 옆 대상에 있다).

kubernetes 레포에서는 `devops-wiki/03-guardrails/rca-shared-criteria.md` §1(Procedure step 4 + 4-way verdict)이 정본이고 A1~A4는 그 축약본이다.
A5는 정본 유무와 관계없이 적용한다. 선행 RCA verdict가 `MISMEASURED`면 문제·근본 원인을 메커니즘이 만든 비용으로 쓰고, `NO IMPACT (NOISE)`면 근본 해결 Task가 아니라 알럿 룰 튜닝 Task다.

| # | 자문 | 걸리면 할 일 |
|---|------|-------------|
| A1 | 고치면 "그 신호가 사라진다" 말고 달라지는 것을 말할 수 있는가? | 없으면 아직 증상이다. 신호를 만든 메커니즘을 근본 원인에 쓴다 |
| A2 | 영향 단위가 진단 도구 단위(알럿 횟수, 노드 수, 로그 라인)인가? | 실제 영향 대상(파드, 요청, 배포, 사용자)으로 다시 센다 |
| A3 | `확인한 사실:`의 근거가 이번 세션에서 내가 쓴 요약 문장인가? | 재측정한다. "영향 없음" 같은 부정 결론은 그 0을 만든 쿼리를 이번 맥락에서 다시 돌린다 |
| A4 | 표본이 몇 건인가? | n=1이면 일반화하지 않고 모수를 넓혀 다시 센다 |
| A5 | 문제 초안에서 날짜·횟수·지속 시간·리소스 이름을 지우면 무너지는가? | 관측값은 작업 Context로 옮기고 결함으로 다시 쓴다 |

진단의 결론은 그 진단의 질문에만 유효하다. "이 알럿이 진짜 고갈인가"의 답을 "서비스 영향이 있는가"의 답으로 옮겨 쓰지 않는다.

#### Step 1.5-B: 정보 충분성 확인

| 섹션 | 충분 | 불충분 |
|------|------|--------|
| 문제 | 무엇이 안 되거나 부족한지가 대화에 구체적으로 있음 | "이거 해줘" 수준 |
| 기대 가치 | 영향, 불편함, 얻는 것이 명시됨 | 동기 언급 없음 |

불충분하고 조회로도 해소되지 않으면 등록 전에 AskUserQuestion으로 묻는다(가벼운 작업도 예외 없음). Due 누락이면 같은 질문에 묶어 1회만 묻는다.

```
Task를 만들기 전에 확인할게요.
1. 문제: 지금 무엇이 안 되거나 부족한가요?
2. 이유: 이걸 하면 무엇을 얻나요? 안 하면 어떤 영향이 있나요?
3. (Due 누락 시) 마감일: 추천 {날짜} / 다음 주 금요일 / 없음
```

근본 원인과 작업 Context는 묻지 않는다. 근거가 없으면 근본 원인은 생략하거나 `(미확인)`, 작업 Context는 `출발점:`과 `다음 액션:`만이라도 쓴다.

### Step 2: 확인

#### Step 2-A: 템플릿 경로

Description + 섹션 초안(채운 섹션 전부) + 속성을 한 번에 보이고 확인받는다. Due를 추천값으로 채웠으면 고른 신호를 한 줄로 적는다.

```
다음 내용으로 Task를 생성할까요? (Type: Task [추천] · ~{due})
제목: #Task - {이름}
Description: {한 줄}

{섹션 초안: ### 문제 / ### 근본 원인 / ### 기대 가치(가설:, Key Result:) / ## 작업 Context}

1. 생성 [추천]
2. 수정 (속성·본문 직접 입력)
0. 취소
```

- "1. 생성" → Step 3
- "2. 수정" 또는 자유 문장의 수정 요청 → 반영한 뒤 바뀐 섹션만 다시 보이고 같은 3지선다로 재확인한다. 수정 요청은 생성 승인이 아니다
- "0. 취소" → 중단

#### Step 2-B: simple 경로 (pass/simple 명시 시만)

섹션 합성과 게이트를 건너뛴다. Due가 파싱됐으면 바로 Step 3. 누락이면 1회 묻는다:
`1. 이번 주 금요일 ({날짜}) [추천]` / `2. 다음 주 금요일 ({날짜})` / `3. 마감일 없음` / `4. 직접 입력 (예: 내일)` / `0. 취소`.
직접 입력 파싱에 실패하면 마감일 없음으로 두고 완료 메시지에 경고로 표시한다.

### Step 3: Notion Task 생성

sections JSON은 셸 인용이 깨지기 쉬우므로 스크래치패드에 Write하고 `--sections-file`로 넘긴다.

```bash
# 템플릿 경로 (기본). 이미지가 있으면 --image "<URL 또는 경로>"를 반복해 붙인다
python3 /Users/changhwan/.claude/skills/tasks:manage/scripts/notion-task.py \
  create-task --name "Task 이름" --due "2026-03-27" \
  --category "WORK" --type "Task" --description "어떤 작업인지 한 줄" \
  --sections-file "/path/to/scratchpad/task-sections.json"

# simple 경로 (pass/simple 명시 시만)
python3 /Users/changhwan/.claude/skills/tasks:manage/scripts/notion-task.py \
  create-task --name "Task 이름" --category "WORK" --simple
```

템플릿 적용이 30초 안에 안 되거나 채우기가 실패하면 스크립트가 같은 heading 구조로 다시 만들고(버튼만 빠짐)
`template_applied: false`, `template_error`를 돌려준다. `--body`/`--body-file`은 쓰지 않는다(deprecated).

### Step 3.5: Task 간 연결 / PR 참조

후속·연관 Task는 본문 텍스트 백링크가 아니라 `Related Task` self-relation(양방향 sync)으로 연결한다.

```bash
# 생성 시 연결
python3 /Users/changhwan/.claude/skills/tasks:manage/scripts/notion-task.py \
  create-task --name "Task 이름" --category "WORK" --related-task "<기존-task-page-id>"
# 기존 두 Task를 사후 연결
python3 /Users/changhwan/.claude/skills/tasks:manage/scripts/notion-task.py \
  link-related-task --page-id "<task-A-page-id>" --related-page-id "<task-B-page-id>"
```

PR은 `PR #1234` 텍스트 대신 실제 URL(`https://github.com/riiid/kubernetes/pull/1234`)을 붙인다(Notion이 멘션으로 렌더링).

### Step 4: 완료 출력

JSON의 `success`로 판단한다.

**성공**: 첫 줄 `캡처 완료`에 Due가 있으면 ` (~{due})`, 경고가 있으면 ` (경고: {사유})`를 붙이고, 다음 줄에 `제목: [{name}]({url})`을 반드시 쓴다
(URL을 따로 노출하지 않는다).

```
캡처 완료 (~2026-03-20)
제목: [#Task - Task 이름](https://www.notion.so/xxxxxxxx)
```

- 경고 사유: 직접 입력 파싱 실패(→ 마감일 없음), 또는 simple 경로가 아닌데 `template_applied: false`(`템플릿 미적용: {template_error} → 같은 구조로 대체 생성, 버튼 없음`)
- 템플릿 경로에서만 마지막에 한 줄을 붙이고, 실행은 사용자가 요청할 때만 한다:
  `이어서 작업을 정리하려면 /notion:add-engineering-note (grill-me → tech-spec → 노트, 이 Task에 연결)`

**실패**: `error`를 사람이 읽을 말로 옮긴다. 예: `캡처 실패: NOTION_TOKEN 미설정. 1Password에서 토큰을 확인하세요.`

## 범위

- 이 스킬은 Task 생성만 한다. 상태 변경은 `notion-task.py update-status`, 이월은 `notion-task.py carry-over`, 삭제는 Notion에서 직접 한다
- 업무 노트(`notion:add-engineering-note`)를 쓰면 노트의 문제/근본 원인/기대 가치가 최종본이 되어 `update-why`로 이 Task에 반영된다. 작업 Context는 교체되지 않는다
- 같은 이름 Task가 있어도 중복 생성한다(의도된 설계)
