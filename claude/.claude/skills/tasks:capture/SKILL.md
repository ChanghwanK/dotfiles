# tasks:capture

작업 중 떠오른 할 일을 Notion Task DB에 캡처한다. 캡처는 빨라야 하지만, **나중에 이 Task를 연 사람이
"무슨 작업이고, 무엇이 문제이고, 왜 하려 했는지"와 "어디서부터 이어가면 되는지"를 알 수 있어야 한다.**
업무 노트(Engineering Note)는 바로 쓰지 않을 수도 있으므로, 그때까지의 맥락은 Task의 `작업 Context`가 보존한다.

---

## 핵심 원칙

- **템플릿이 기본**: 모든 캡처는 Task 템플릿으로 만들고 섹션을 채운다. 가벼운 작업도 무슨 작업이고
  무엇이 문제이고 왜 하는지가 나중에 필요할 수 있기 때문이다.
- **pass/simple일 때만 생략**: 사용자가 입력에 "pass" 또는 "simple"을 명시하면 템플릿과 섹션 합성을
  건너뛰고 제목(+due)만으로 만든다(Step 2-B). Claude가 "가벼워 보인다"는 이유로 스스로 생략하지 않는다.
- **추정으로 채우지 않는다**: 세션에서 확인되지 않은 내용은 쓰지 않는다. 모르면 비워 두거나
  `(미확인)`으로 표시하고, 필요하면 1회 질문으로 확인한다.
- **최대 1회 확인**: 섹션 초안과 속성(Due/Type)을 한 화면에 모아 한 번에 확인받는다.
- **단일 출력**: 완료 메시지와 제목 링크만 출력한다.

---

## 입력 파싱 규칙

사용자 입력에서 아래 속성을 추출한다. 명시되지 않은 속성은 기본값 적용.

| 속성 | 추출 방법 | 기본값 |
|------|-----------|--------|
| **이름** (필수) | 아래 "제목 추출 원칙" 참조. 반드시 Claude가 합성 | 없음 |
| **Category** | "개인", "MY", "personal", "사적" → MY; 그 외 모두 → WORK | `WORK` |
| **Due Date** | YYYY-MM-DD 또는 "오늘"/"내일"/"이번 주 금요일"/"다음 주" → 절대 날짜 변환 (KST 기준) | 누락으로 처리 |
| **Description** | 어떤 작업인지 한 줄(대상 + 무엇을 하는가). 아래 "Description 원칙" 참조 | 템플릿 경로에서는 항상 작성 |
| **Images** | 파일 경로 또는 URL 목록 (아래 "이미지 파싱" 참조) | 없음 (선택) |
| **Type** | "Task"/"Project" 명시 또는 문맥상 명확(예: "여러 단계로 나눠서", "설계+구현+배포"). 명시가 없으면 Step 2-A 확인 화면에 `Type: Task [추천]`을 함께 보여준다 | `Task` |
| **simple 여부** | 입력에 "pass" 또는 "simple"(대소문자 무관)이 명시됐는가 | 아니오 |

### 이미지 파싱

이미지 첨부 신호가 있으면 `--image` 플래그를 추가한다.

**신호:**
- 사용자가 파일 경로를 명시: `"/Users/changhwan/Desktop/error.png"` 등
- 대화에서 이미지(스크린샷)가 시각적으로 첨부됨 → Claude가 해당 이미지를 `~/.claude/todo-images/<title-slug>.png`로 저장 후 경로 사용
- URL 형태: `https://...` (Notion 페이지에 이미지 블록으로 삽입됨)

**규칙:**
- URL은 Notion 페이지에 image 블록으로 삽입
- 로컬 경로는 Notion 페이지에 callout 텍스트로 기록 (경로 보존)
- 이미지는 페이지 끝(작업 Context 뒤)에 붙는다. 이미지 없으면 플래그 생략

### 제목 추출 원칙

**입력 전체를 제목으로 쓰지 않는다.** 반드시 핵심만 뽑아 합성한다.

- **단순 짧은 입력**: 메타데이터 키워드("개인", "pass", "simple" 등)만 제거하고 나머지를 제목으로 사용
- **추가 정보가 있는 입력**: Claude가 핵심 동작/목표를 담은 **20~40자 제목**을 합성
  - 추가 정보 = 조건·이유·배경·상세 요구사항 (예: "window는 7일", "왜냐하면", 쉼표 이후 설명)
  - `[카테고리 태그]`가 있으면 제목 앞에 유지
  - 제목 구성 규칙: **동사+목적어 포함, 조건·이유 제외**

### Description 원칙

- 템플릿 경로: **어떤 작업인지** 한 줄(대상 + 무엇을 하는가)을 항상 쓴다. 문제·이유는 본문 섹션에 쓰고 여기서 반복하지 않는다.
- simple 경로: 입력에 제목 외 추가 정보(조건·이유·배경)가 있을 때만 원문을 요약해 넣는다.

## 본문 섹션 (Task 템플릿)

Task 템플릿의 구조는 Notion에 있는 템플릿이 단일 출처다(`notion-task.py`의 `TASK_TEMPLATE_ID`).
스크립트가 템플릿을 적용하고 아래 heading 아래를 채운다. Claude는 **sections JSON만** 만든다.

```
[버튼] [📌 목차]
## 왜 이걸 해야하는가?
### 문제          ← sections.problem
### 근본 원인     ← sections.root_cause
### 기대 가치     ← sections.value
---
## 작업 Context   ← sections.context
```

sections JSON (값은 Markdown, 없는 키는 생략하면 템플릿의 빈 칸이 그대로 남는다):

```json
{
  "problem":    "- ...",
  "root_cause": "- ...",
  "value":      "- ...\n- *가설:*\n  - ...\n- *검증 기준:*\n  - ...",
  "context":    "- *출발점:*\n  - ...\n- *확인한 사실:*\n  - ...\n- *다음 액션:*\n  - ..."
}
```

### 섹션별 작성 기준

- **문제**: 무엇이 제 역할을 못 하고 있는가. 관측된 사건이 아니라 **그 사건을 가능하게 한 경계·장치·절차의
  결함**을 현재형으로 쓴다(아래 "현상을 빼고 문제를 쓴다"). 개선 작업이 아닌 일(신규 구축, 학습, 개인 일)은
  "지금 없어서 불편한 것 / 막혀 있는 것"을 한두 줄로 쓴다.
- **근본 원인**: 문제가 왜 존재하는가를 **메커니즘 수준**으로 쓴다. 알럿·에러 같은 신호가 아니라 신호를 만든
  구조를 쓴다(Step 1.5-A). 측정으로 확정한 원인만 사실로 쓴다. 아직 확인하지 못했으면 단정하지 않고
  `(원인 미확인)` 아래에 세션에서 논의한 만큼 원인 후보(둘 이상 + 그 외)와 후보를 가를 변별 증거를 적는다
  (CLAUDE.md Hypothesis-First "원인 가설 단계").
  원인 개념이 성립하지 않는 작업(신규 구축, 학습, 개인 일)은 키를 생략한다.
- **기대 가치**: 왜 하려는가. 이 일이 끝나면 **사람·팀이 무엇을 얻는가**(판단 단계가 사라진다, 복구가
  빨라진다, 같은 문제가 다시 쌓이지 않는다 등)를 1~4개 불릿으로 쓴다. 이어서 해결 가설을 세울 수 있으면
  두 라벨을 붙인다(CLAUDE.md Hypothesis-First).
  - `*가설:*` 무엇을 적용하면 위 문제가 해결되는가, 한 문장
  - `*검증 기준:*` 무엇이 어느 방향으로 얼마나 바뀌면 해결인가. 대표 지표 1~2개의 현재값 → 목표값으로 쓴다
    (현재값만 알면 `현재값 → (목표 미정)`). 시간이 걸리는 판정이면 판정 시점을 괄호로 붙인다.
    적용 직후(변경이 의도대로 걸렸는가)와 결과(문제가 풀렸는가)로 나눌 수 있으면 두 줄로 나눈다
  - 정의 전 캡처, 학습·개인 일처럼 해결할 문제가 없으면 두 라벨을 생략한다
  세부 목표·검증 시나리오(Goals)와 실행 계획은 Task가 아니라 업무 노트에서 다룬다.
- **작업 Context**: 이 세션을 못 본 사람이 **재조사 없이 다음 액션을 시작할 수 있는가**가 기준이다.
  아래 라벨 중 세션에 근거가 있는 것만 쓴다(없는 라벨은 생략, 지어내지 않는다).
  - `*출발점:*` 어떤 알럿·대화·세션·요청에서 나왔는가(날짜 포함)
  - `*확인한 사실:*` 측정치·관측값과 **그 값을 다시 얻는 방법**(쿼리, 명령, 대시보드 이름). 시각·횟수·
    지속 시간·재발 이력 같은 관측값은 문제가 아니라 여기에 둔다. 출처 없는 결론은 쓰지 않는다
  - `*관련 리소스:*` PR URL, 파일 경로, Grafana·Notion 링크
  - `*검토한 것:*` 세운 가설과 기각한 대안, 기각 근거(세션에서 실제로 논의했을 때만)
  - `*다음 액션:*` 재개 시 첫 번째로 할 구체적 행동 하나
  - `*미결 질문:*` 아직 답이 없는 것

### 정의되지 않은 불편함에서 시작한 작업

"코드가 복잡하다", "재사용이 어렵다", "인지 부하가 크다"처럼 형용사로 된 불만에서 시작한 작업은 캡처 시점에
문제를 또렷하게 쓸 수 없다. 억지로 문제를 지어내지 않고, 사용자의 말과 동기를 보존해 grill-me로 넘긴다.

- *판별 신호:*
  - 입력이 불편함을 형용사로 말하고, 제목이 해결책 이름(모듈화, 리팩터링, 표준화, 마이그레이션)이다
  - 무엇이 어떤 순간에 걸렸는지(구체적 사례)가 입력과 세션에 없다
- *섹션 작성:*
  - 문제: `- (정의 전) {사용자가 말한 불편함 요지}` 한 줄만 쓴다. 현상 제거·추상화 판별은 적용하지 않는다(정의는 grill-me가 한다)
  - 근본 원인: 키를 생략한다
  - 기대 가치: 사용자가 말한 **동기**(왜 하고 싶은지, 무엇이 나아지길 바라는지)를 사용자 표현에 가깝게 쓴다
  - 작업 Context `*출발점:*`: "정의되지 않은 불편함에서 시작"이라고 밝히고 사용자가 한 말을 그대로 옮긴다
- *질문:*
  - Step 1.5-B에서는 문제 정의를 요구하지 않는다. 동기가 입력에 없을 때만 "이걸 왜 하고 싶으세요?"를 묻는다(Due 질문과 묶어 1회)
- *넘김:*
  - 이렇게 캡처된 Task는 grill-me가 `(정의 전)` 표시와 기대 가치의 동기를 보고 "왜"를 다시 묻지 않고 사례 질문부터 시작한다

### 현상을 빼고 문제를 쓴다

현상은 "무엇이 일어났다"(관측된 사건)이고, 문제는 "무엇이 작동하지 않아서 그 사건이 가능했는가"(구조의
결함)다. 알럿·RCA에서 출발한 Task는 관측 타임라인을 그대로 문제에 옮기기 쉬우므로, 초안을 쓴 뒤 문장마다
아래를 적용한다.

- *판별:*
  - 날짜·시각·횟수·지속 시간·노드/파드 이름을 지워도 문장이 성립하는가? 무너지면 현상이다
  - 다음에 같은 일이 또 나도 문장이 그대로 참인가? 이번 건만 설명하면 현상이다
  - 주어가 사건("노드가 NotReady가 됐다")인가, 경계·장치·절차("노드 경계가 파드 장애를 가두지 못한다")인가
  - 문제 유형에 표준 용어로 이름을 붙일 수 있는가(장애 격리 실패, retry storm, 자동 복구 부재 등)? 못 붙이면 아직 현상 수준이다
  - 해결 대상(특정 파일·문서·도구·리소스 이름)을 지워도 문장이 성립하는가? 무너지면 추상화 수준이 해결 수단 쪽에 머문 것이다.
    문제는 "어떤 종류의 결함인가"(예: 정책을 강제하는 지점 부재, 결정이 재사용되지 않음)를 주어로 쓰고, 해결 대상은
    근본 원인이나 근거로 내린다
    - 예(2026-09-27 테라폼 모듈화): "README 기준이 `aws_rds_cluster`를 모듈화에서 제외한다"는 해결 대상이 주어라서 README를
      고치면 문제가 끝난 것처럼 읽힌다. "조직의 결정을 한 번 정의하고 재사용·강제하는 단위가 없어, 안전한 구성이 기본값이
      아니라 매번의 선택이다"로 올리고, README 기준은 근본 원인으로 내렸다
- *현상의 자리:*
  - 관측값은 버리지 않고 `작업 Context`의 `*확인한 사실:*`로 옮긴다. 같은 사실을 두 섹션에 쓰지 않는다
- *시제:*
  - 문제는 현재형으로 쓴다("~하지 못한다"). 과거형("~했다")이 나오면 관측을 옮겨 적고 있다는 신호다
- *범위 주장 대조:*
  - "하나", "매번", "일상", "방치됐다" 같은 범위·빈도·완료 표현은 증거와 대조한다
- *예시(2026-09-26 prod 노드 NotReady):*
  - 나쁜 예(현상): "09-24 04:40 노드가 NotReady가 된 뒤 55시간 복구되지 않았고, 09-03에도 노드 3대가 7시간 NotReady였다"
  - 좋은 예(문제): "예고된 인프라 이벤트에서 워커 하나가 비정상이 되면, 컨테이너 경계(memory limit)와 노드 경계(kubelet 보호)가 그 장애를 가두지 못해 노드 전체로 번지고, 번진 노드를 자동으로 교체하는 경로가 없어 사람이 개입할 때까지 복구되지 않는다"
  - 나쁜 예의 날짜·시간·대수는 `작업 Context`의 `*확인한 사실:*`로 옮긴다

### 문장·포맷

- 초안 합성 시점부터 `~/.claude/docs/notion-writing-style.md`의 "쓰기 시점 체크리스트"를 적용한다.
  - 불릿 `레이블: 내용`은 레이블을 `*레이블:*`(이탤릭) 상위 불릿으로, 내용은 한 단계 들여쓴 하위 불릿으로 쓴다.
    내용이 한 줄이어도 인라인으로 붙이지 않는다.
  - 서로 밀접한 사실(원인+결과, 결론+그 근거)은 연결어로 한 문장에 묶고, 무관한 사실만 끊는다.
  - 버전/태그/상태 전환은 "to" 대신 화살표(`→`)로 쓴다.
  - 섹션 간 같은 사실을 재진술하지 않는다.
- 중첩은 2단계(라벨 → 내용)까지만 쓴다. 한 요청에서 Notion이 허용하는 중첩 깊이이기 때문이다.
- 체크리스트가 필요하면 `- [ ] 항목` Markdown을 쓴다(스크립트가 to_do 블록으로 변환).
- 목차는 템플릿의 네이티브 목차 블록이 자동으로 만든다. 목차 텍스트를 직접 쓰지 않는다.
- em dash/본문 이모지는 쓰기 스크립트가 결정적 backstop을 건다(그래도 처음부터 쓰지 않는다).

## 워크플로우

### Step 1 - 입력 파싱

사용자 입력을 분석하여 이름, Category, Due Date, Description, Type, simple 여부를 추출한다.
- 추출 과정은 내부적으로만 처리.
- "오늘"/"내일"/"이번 주" → KST 기준 절대 날짜(YYYY-MM-DD)로 변환.
- **제목 합성 (반드시)**: "제목 추출 원칙"을 적용. 입력 전체를 제목으로 사용하지 않는다.
- **simple 여부 판정**: "pass" 또는 "simple"이 명시됐으면 Step 2-B로 간다. 그 외에는 Step 1.5로 간다.

### Step 1.5 - 세션 컨텍스트 분석 게이트 (템플릿 경로)

섹션은 추정으로 채우지 않는다. 아래 두 검사를 **1.5-A → 1.5-B 순서로** 통과시킨다. 순서가 반대면
"정보는 많은데 전부 증상"인 경우를 걸러내지 못한다(맥락이 풍부하면 1.5-B는 무조건 통과하기 때문이다).

#### grill-me 인터뷰 결과가 있는 경우 (먼저 확인)

args나 세션에 grill-me 인터뷰 결과("grill-me 인터뷰 완료")가 있으면 그것을 1차 입력으로 쓴다.
- 인터뷰에서 확정된 문제·목적·근거로 섹션을 합성하고, Step 1.5-B 질문은 하지 않는다(이미 충족).
- 인터뷰로 불편함이 문제로 정의됐으면 `(정의 전)` 표시를 쓰지 않는다. 정의되지 못한 채 끝났을 때만 쓴다.
- 인터뷰의 남은 Gap은 `작업 Context` > `*미결 질문:*`에, 확정된 결정은 `*검토한 것:*`에 옮긴다.
- 1.5-A(A5 현상 제거, 해결 대상 판별)는 합성한 문장에 그대로 적용한다.
- 이 경로로 호출됐고 호출자가 업무 노트로 이어갈 예정이면(grill-me Option A), 완료 출력의 "다음 단계 안내" 줄은 붙이지 않는다.

#### Step 1.5-A - 진짜 문제 검증 (5개 자문)

세션에 맥락이 풍부해도 그것이 곧 올바른 문제 정의는 아니다. 특히 **알럿·에러 로그·대시보드
이상에서 출발한 Task는 진단 도구가 보여준 신호를 문제로 착각하기 쉽다.** 초안 합성 전에 아래
5개를 자문하고, 하나라도 걸리면 **사용자에게 묻기 전에 먼저 조회·측정으로 해소한다.**

**알럿·인시던트에서 파생된 Task는 A1·A2를 건너뛸 수 없다.** 알럿은 진입점이지 문제의 경계가
아니다. 근본 원인은 알럿보다 **아래**(신호를 만든 메커니즘)에 있고, 여파는 알럿보다 **옆**(같은
메커니즘이 건드린 다른 대상)으로 퍼진다.

**정본은 이 파일이 아니다.** kubernetes 레포에서 작업 중이면 이 절차의 단일 출처는
`devops-wiki/03-guardrails/rca-shared-criteria.md` §1이다 (Procedure step 4 + 4-way verdict).
아래 A1~A4는 그 정본이 없는 프로젝트를 위한 **이식 가능한 축약본**이므로, 정본이 있으면 정본을 따른다.
A5(현상 제거)는 문제 문장 작성 검사이므로 정본 유무와 관계없이 항상 적용한다.
선행 RCA의 verdict가 `MISMEASURED`이면 문제·근본 원인은 알럿이 아니라 **메커니즘이 만든 비용**으로 쓴다.
`NO IMPACT (NOISE)`로 끝난 사안은 근본 해결 Task의 근거가 될 수 없다 (알럿 룰 튜닝 Task가 맞다).

| # | 자문 | 걸리면 할 일 |
|---|------|-------------|
| A1 | 이걸 고치면 "그 신호가 사라진다" 말고 달라지는 것을 말할 수 있는가? | 말할 수 없으면 아직 증상이다. 신호를 만든 메커니즘까지 한 단계 내려가 근본 원인에 쓴다 |
| A2 | 영향을 세는 단위가 진단 도구의 단위(알럿 발화 횟수, 노드 수, 로그 라인 수)를 그대로 물려받았는가? | 실제로 영향받는 대상(파드, 요청, 배포, 사용자)으로 다시 센다 |
| A3 | `*확인한 사실:*`의 근거가 **이번 세션에서 내가 쓴 요약 문장**인가, 조회 가능한 측정치인가? | 자기 인용이면 재측정한다 |
| A4 | 근거의 표본이 몇 건인가? | n=1이면 일반화하지 않는다. 모수를 넓혀 다시 센다 |
| A5 | 문제 초안에서 날짜·횟수·지속 시간·리소스 이름을 지우면 문장이 무너지는가? | 무너지면 현상이다. 관측값은 작업 Context로 옮기고 경계·장치·절차의 결함으로 다시 쓴다 |

**A3은 부정 결론에 특히 강하게 적용한다.** "영향 없음", "문제 없음", "무해함" 같은 문장은
*측정해서 0이었다*와 *찾아보지 않았다*가 겉으로 구분되지 않는다. 부정 결론을 근거로 쓰려면
그 0을 만든 쿼리나 조회를 이번 Task 맥락에서 다시 실행한다.

**진단 맥락의 결론은 그 진단의 질문에만 유효하다.** "이 알럿이 진짜 고갈인가"의 답을
"이 현상이 서비스에 영향이 있는가"의 답으로 옮겨 쓰지 않는다. 질문이 바뀌면 근거도 다시 만든다.

> 실패 사례(2026-09-07): VPCCNIIPAllocationFailing 알럿 RCA에서 "실제 서비스 영향 0"이라는
> 정오탐 판정을 그대로 Task의 근거로 옮겨 적었다. A2를 어겨 알럿 단위(노드 21건)로만 셌고,
> A4를 어겨 노드 1대의 관찰을 일반화했다. 파드 단위로 다시 세니 30일 68개 파드 중 31개가
> 제품 워크로드(퍼블릭 인그레스 게이트웨이 포함)였고, 시작 지연은 65초 중 33초였다.
> 데이터는 처음부터 있었고 질문만 없었다.

#### Step 1.5-B - 정보 충분성 확인

| 섹션 | 충분한 경우 | 불충분한 경우 |
|------|------------|--------------|
| 문제 | 무엇이 안 되거나 부족한지가 대화에 구체적으로 있음 | "이거 해줘" 수준으로 문제 맥락이 없음 |
| 기대 가치 | 영향, 불편함, 얻는 것이 명시됨 | 동기가 전혀 언급되지 않음 |

**불충분하고 조회로도 해소되지 않으면 등록 전 질문한다.** 가벼운 작업도 예외가 아니다(생략은 pass/simple일 때만).
Due Date가 누락됐으면 같은 AskUserQuestion에 묶어 **1회만** 묻는다.

```
Task를 만들기 전에 확인할게요.

1. 문제: 지금 무엇이 안 되거나 부족한가요?
2. 이유: 이걸 하면 무엇을 얻나요? 안 하면 어떤 영향이 있나요?
3. (Due 누락 시) 마감일: 추천 {날짜} / 다음 주 금요일 / 없음
```

1.5-A를 통과했고 두 섹션 모두 세션에서 추출 가능하면 질문 없이 합성 후 Step 2-A로 간다.
근본 원인과 작업 Context는 질문하지 않는다. 세션에 근거가 없으면 근본 원인은 생략하거나 `(미확인)`으로,
작업 Context는 `*출발점:*`과 `*다음 액션:*`만이라도 쓴다.

### Step 2 - 확인

#### Step 2-A - 템플릿 경로

합성한 Description + 섹션 초안 + 확정될 속성(Due/Type)을 **한 번에** 보여주고 단일 확인한다.
추천 Due가 기본값(이번 주 금요일)과 다르면 **왜 다른지 한 줄로 적는다**.

```
다음 내용으로 Task를 생성할까요? (Type: Task [추천] · ~2026-03-27)
제목: {이름}
Description: {어떤 작업인지 한 줄}

### 문제
- ...

### 근본 원인
- ...

### 기대 가치
- ...
- *가설:*
  - ...
- *검증 기준:*
  - ...

## 작업 Context
- *출발점:*
  - ...
- *다음 액션:*
  - ...

1. 생성 [추천]
2. 수정 (속성·본문 직접 입력)
0. 취소
```

- "1. 생성" → Step 3 진행.
- "2. 수정" (또는 번호 없이 수정 요청을 자유 문장으로 보낸 경우) → 반영한 뒤, **바로 생성하지 않고 바뀐 섹션만
  다시 보여주며 같은 3지선다로 재확인한다.** "1. 생성"을 받은 뒤에만 Step 3을 실행한다. 수정 요청은
  "생성 승인"이 아니다 (2026-09-24: 수정 요청 직후 바로 생성했는데 사용자가 뒤이어 "생성"을 입력해 중복 생성 직전까지 감).
- "0. 취소" → 중단.

#### Step 2-B - simple 경로 (사용자가 pass/simple을 명시한 경우만)

섹션 합성과 게이트를 건너뛴다. **모든 선택지 마지막에 "0. 취소" 포함.**

**Case A (질문 없음)**: Due Date가 파싱됨 → Step 3으로 즉시 진행.

**Case B (Due Date 누락)**: 추천값과 함께 1회 질문한다.

```
마감일을 설정할까요?
추천: 이번 주 금요일 (2026-03-20)

1. 이번 주 금요일 (2026-03-20) [추천]
2. 다음 주 금요일 (2026-03-27)
3. 마감일 없음
4. 직접 입력 (예: 내일)
0. 취소
```

"4. 직접 입력" 선택 후 파싱 실패 → 마감일 없음으로 fallback 후 완료 메시지에 ⚠️ 표시.

### Step 3 - Notion Task 생성

섹션 JSON은 백틱·따옴표·체크박스가 섞여 셸 인용이 깨지기 쉬우므로 스크래치패드에 파일로 Write한 뒤
`--sections-file`로 넘긴다.

```bash
# 템플릿 경로 (기본)
python3 /Users/changhwan/.claude/skills/tasks:manage/scripts/notion-task.py \
  create-task --name "Task 이름" --due "2026-03-27" \
  --category "WORK" --type "Task" --description "어떤 작업인지 한 줄" \
  --sections-file "/path/to/scratchpad/task-sections.json"

# simple 경로 (사용자가 pass/simple을 명시한 경우만)
python3 /Users/changhwan/.claude/skills/tasks:manage/scripts/notion-task.py \
  create-task --name "Task 이름" --category "WORK" --simple

# 이미지 포함 (URL: 이미지 블록, 로컬 경로: callout 텍스트. 페이지 끝에 붙는다)
python3 /Users/changhwan/.claude/skills/tasks:manage/scripts/notion-task.py \
  create-task --name "Task 이름" --category "WORK" \
  --sections-file "/path/to/scratchpad/task-sections.json" \
  --image "https://example.com/diagram.png" \
  --image "/Users/changhwan/Desktop/screenshot.png"
```

> 스크립트는 템플릿을 적용하고(보통 2~3초) heading 아래를 채운다. 템플릿이 30초 안에 적용되지 않거나
> 채우기가 실패하면 그 페이지를 휴지통으로 보내고, 템플릿과 같은 heading 구조로 다시 만든다(버튼만 빠진다).
> 이때 응답은 `template_applied: false`와 `template_error`를 담는다. 캡처는 유실되지 않는다.
> `--body`/`--body-file`(구 00~05 본문 형식)은 deprecated이므로 쓰지 않는다.

### Step 3.5 - Task 간 연결 / PR 참조 표기

Task DB에는 `Related Task`라는 self-relation 프로퍼티가 있다 (양방향 sync: 한쪽만 채우면
반대쪽에도 자동 반영). 새 Task가 기존 Task의 후속·연관 작업이면 본문에 마크다운 텍스트
백링크를 쓰지 말고 이 프로퍼티로 연결한다.

```bash
# 생성 시점에 바로 연결 (기존 Task의 page ID를 알고 있을 때)
python3 /Users/changhwan/.claude/skills/tasks:manage/scripts/notion-task.py \
  create-task --name "Task 이름" --category "WORK" \
  --related-task "<기존-task-page-id>"

# 이미 존재하는 두 Task를 사후에 연결
python3 /Users/changhwan/.claude/skills/tasks:manage/scripts/notion-task.py \
  link-related-task --page-id "<task-A-page-id>" --related-page-id "<task-B-page-id>"
```

**PR 참조는 링크 멘션으로.** 본문·description에서 PR을 언급할 때 `PR #1234` 같은 plain text
대신 GitHub PR의 실제 URL(`https://github.com/riiid/kubernetes/pull/1234`)을 그대로 붙인다.
Notion이 bare URL을 자동으로 언마크(unfurl)해 리치 프리뷰/멘션으로 렌더링한다.

### Step 4 - 완료 출력

스크립트 JSON 출력의 `success` 필드로 성공 여부를 판단한다.

**성공** (`"success": true`): 태그 요약 줄 다음에 반드시 `제목: [{name}]({url})` 줄을 붙인다.
JSON의 `url` 필드(Notion 페이지 URL)를 제목 텍스트 자체의 markdown 링크로 건다 (URL을 별도로 노출하지 않는다).
사용자가 제목을 클릭해 캡처된 내용을 바로 확인할 수 있게 하기 위함이다.

**절대 생략 금지**: 이 줄은 성공 응답마다 예외 없이 포함한다. 완료 메시지만 출력하고
제목/링크 줄을 빠뜨리는 실수가 있었으므로, 최종 답변을 보내기 전에 이 줄이 있는지 반드시 확인한다.

```
📥 캡처 완료
제목: [Task 이름](https://www.notion.so/xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx)

📥 캡처 완료 (~2026-03-20)
제목: [Task 이름](https://www.notion.so/xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx)

📥 캡처 완료 ⚠️ (직접 입력 파싱 실패 → 마감일 없음 기본값 적용)
제목: [Task 이름](https://www.notion.so/xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx)

📥 캡처 완료 ⚠️ (템플릿 미적용: {template_error} → 같은 구조로 대체 생성, 버튼 없음)
제목: [Task 이름](https://www.notion.so/xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx)
```

`template_applied`가 `false`인데 simple 경로가 아니었다면 위 ⚠️ 줄을 쓴다(템플릿 ID 변경·권한 문제를 알아채기 위함).

**다음 단계 안내 (템플릿 경로에서만, 한 줄)**: 대부분의 작업은 캡처 뒤 "grill-me로 작업 파악 → tech-spec으로 작성 →
업무 노트 반영"으로 이어진다. 성공 출력 마지막에 아래 한 줄을 붙이고, 실행은 사용자가 요청할 때만 한다(캡처만 하고
끝내는 경우도 있으므로 자동으로 이어가지 않는다). simple 경로에서는 붙이지 않는다.

```
💡 이어서 작업을 정리하려면 `/notion:add-engineering-note` (grill-me → tech-spec → 노트, 이 Task에 연결)
```

**실패** (`"success": false`): JSON의 `error` 필드를 추출하여 사람 친화적으로 출력한다.

```
❌ 캡처 실패: NOTION_TOKEN 미설정. 1Password에서 토큰을 확인하세요.
❌ 캡처 실패: Notion API 오류 (HTTP 400). 속성명 불일치 가능성.
```

## 주의사항

- 이 스킬은 **Task 생성 전담**. Task 상태 변경/삭제는 Alfred week·task 모드(`notion-task.py update-status`/`delete-task`), 이월은 `notion-task.py carry-over` 사용.
- **확인은 1회**로 속성과 섹션을 확정한 후 즉시 실행한다. 단, 확인 화면에서 수정 요청이 오면 반영본으로 한 번 더 확인한다(Step 2-A "2. 수정" 참조).
- 업무 노트를 쓸 때(`notion:add-engineering-note`) 노트의 문제/근본 원인/기대 가치가 최종본이 되고, 이 Task의 같은 섹션은 `notion-task.py update-why`로 그 최종본으로 교체된다. 작업 Context는 캡처 기록이므로 교체되지 않는다.
- 동일 이름 Task가 이미 존재해도 중복 생성됨 (의도적 설계, GTD 원칙). 중복 정리는 `/tasks:manage`에서.
