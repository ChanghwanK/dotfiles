# 작업 분해 기준

배경과 목표가 정해진 작업에서 "어떻게 도달하는가"를 Task로 나누고 순서를 정하는 기준의 정본이다(2026-11-27 사용자와 합의, Codex 리뷰 반영).
배경·목표·Key Result 작성은 `task:keyresult`, 원인 미상 문제의 가설 단계는 `~/.claude/docs/hypothesis-first.md`가 정본이다. 이 스킬은 그 사이의 실행 경로만 다룬다.
소비처: `notion:add-engineering-note`(`plan`, 실행 계획), `task:keyresult`(Todo 칸 포인터). 롤백(`롤백:`) 등 업무 노트 고유 규칙은 `notion:add-engineering-note` "실행 계획 작성 기준"을 따른다.

## 적용 판단

갈림 질문: **"이 작업이 끝났을 때의 상태를 지금 명사로 적을 수 있는가?"**

| 답 | 분해 방식 | 예 |
|----|----------|----|
| 적을 수 있다 | 이 스킬의 산출물 중심 분해(WBS) | 도입·전환·업그레이드 |
| 앞부분만 모른다 | 앞은 질문 단위, 답이 나온 뒤 이 스킬로 분해 (rolling wave planning) | 해결책 미정인 재발 방지·성능 개선 |
| 적을 수 없다 | 질문·가설 단위. 결과("가설별 반증 결과", "원인 판정")로는 쓸 수 있지만 방법을 미리 고정하지 않는다 | 원인 미상 RCA, 리서치 |
| 급박하다 | 분해보다 우선순위(완화 → 복구 → 원인). 완화와 원인 확인을 같은 완료로 묶지 않는다 | 장애 대응 |

알려진 절차로 끝나는 작은 작업은 단계 없이 Task 하나와 하위 항목만 쓴다.

## 구조: 단계 > Task > 하위 항목

| 층 | 무엇인가 | 판단 질문 | 예 |
|----|---------|----------|----|
| 단계 | 끝에서 계속 갈지 판단하는 지점(phase gate) 사이의 구간 | 여기서 멈추고 계속 갈지 판단하는가 | PoC, 전환 준비, 전환, 정리 |
| Task | 끝나면 상태 하나가 만들어지는 일. 그 상태(To-be)가 산출물이다 | 끝난 뒤의 모습을 As-is → To-be로 쓸 수 있는가 | dev istio ambient 환경 구축 |
| 하위 항목 | Task를 이루는 의미 있는 변경·확인 한 덩어리(작업 패키지) | 담당·검증·롤백을 하나로 관리할 수 있는가 | dev istio-system에 istio-cni, ztunnel 추가 |
| 실행 체크리스트 | 하위 항목 안의 실행 세부(활동). 순서 제약이 있을 때만 적는다 | 순서를 틀리면 사고가 나는가 | ambient 라벨 → injection 해제 → Pod 재시작 |

- 깊이를 통일하지 않는다. 작은 Task는 하위 항목이 없어도 된다.
- "라벨 적용", "ArgoCD sync"처럼 순서 제약 없는 실행 세부는 적지 않는다.

## 판단 조건 3가지

적용 순서: 1번으로 자르고, 2번으로 남길 것을 고르고, 3번으로 순서를 정한다.

### 1. 결과 조건: 경계를 정한다

질문: **이 Task가 끝나면 As-is → To-be 상태 변화가 관측되는가?**

- 너무 작음: 혼자서는 확인할 결과가 없다(예: 라벨 적용). 상위 Task의 실행 체크리스트로 내린다.
- 너무 큼: 확인할 결과가 둘 이상이거나, 담당자·실패 영향·롤백 경로가 갈린다(예: dev와 stg를 함께 전환). 나눈다.
- 멈춤 기준은 최소 크기가 아니라 관리에 충분한 크기다. 더 쪼갤 수 있어도 하나의 책임과 검증으로 관리되면 멈춘다.

### 2. 결정 조건: 남길지 정한다

질문: **이 Task의 결과에 따라 다음 행동이 달라지는가?**

- 통과: 결과가 바꾸는 결정을 한 줄로 쓸 수 있다(예: 전환 범위, stg 진행 여부).
- 통과 못 함: 결과가 어떻든 다음 행동이 같다. 범위에서 빼거나 다른 Task에 합친다.
- 예외: 인수 검증, 복구 훈련, 규정 준수 시험은 결정을 바꾸지 않아도 남긴다.

### 3. 순서 조건: 선행관계를 정한다

질문: **이 Task의 결과를 알기 전에 시작하면, 나중에 다시 해야 할 작업이 생기는가?**

- 생긴다: 선행으로 둔다. 결정에 미치는 영향이 크고 늦게 알았을 때 재작업이 클수록 앞에 둔다.
- 안 생긴다: 병렬로 진행하거나 뒤로 보낸다.
- 되돌리기 어려운 Task는 맨 끝에 둔다. 단, 실행 가능성과 복구 제약 확인은 앞에서 한다.
- 오래 기다리는 일(외부 팀 승인 등)은 일찍 시작한다.
- 결정이 닫히기 전에는 그 결정을 전제로 문서·설계를 키우지 않는다.

## Task 카드

```markdown
- **Task 0N. [Task 제목]**
  - 완료 조건
    - As-is: [지금 시스템·사람이 겪는 것, 못 하는 것]
    - To-be: [끝나면 시스템이 어떻게 동작하고 사람이 무엇을 할 수 있는가]
  - 연결된 결정: [이 결과가 바꾸는 결정]
  - 판정 근거: [제3자가 To-be 도달을 판정할 관측]
  - 선행: [Task 번호 또는 없음]
  - 실행 체크리스트 (순서 제약이 있을 때만)
    1. ...
```

- **완료 조건**: 주어는 산출물(코드, 문서)이 아니라 시스템이나 사람이다. "코드를 변경했다", "문서를 작성했다"는 To-be가 아니다. To-be를 읽고 "그래서 뭐가 좋아졌는데?"가 남지 않아야 한다.
- **판정 근거**: 관측 대상과 비교 기준을 쓴다(예: 5xx 비율과 p99 지연을 전환 전과 비교). 관찰 기간·기준값이 아직 없으면 비워 두고 계획 확정 때 채운다.
- **선행관계**: Task 카드와 별도로 전체 그림을 그린다. 병렬 가능한 Task가 보이게 한다.

```
Task 01 ─→ Task 02 ─→ Task 03 ─→ Task 04 ─┐
              └─────→ Task 05 ────────────┴─→ Task 06
```

## 표현

- Task·하위 항목 제목: `[대상]에/의 [무엇] [행동 명사]`. 실제 시스템·리소스 이름을 쓴다.
  - 좋음: `Okta argocd-admin, argocd-readonly Group에서 개발자 제외`
  - 나쁨: `권한 정리`(영역), `조사`(활동), `values.yaml 수정`(위치)
- 결과를 좌우하는 방법은 앞에 붙인다: `helm diff 확인 후 helm upgrade로 적용`, `테스트 계정으로 권한 검증`
- 명사형으로 끝낸다(연동, 확인, 적용, 검증, 제외, 업데이트, 구축, 전환).
- 제목에는 이유와 완료 조건을 넣지 않는다. Task 카드 필드에 둔다.
- 검증과 문서 업데이트도 별도 하위 항목으로 둔다.
- Key Result에 번호가 있으면 Task 제목 끝에 기여하는 KR을 `(KR1, KR3)`로 붙인다. KR의 수치 기준은 반복하지 않는다.
- 범위 밖 후속 작업은 마지막 `*분리*` 단계 아래에 남긴다.
- 단계는 굵은 글씨 목록으로 쓴다. 채팅 출력에는 체크박스를 쓰지 않고, Notion 업무 노트 실행 계획(`plan`)에서는 하위 항목을 체크박스로 쓴다(alfred gate가 대조하는 원본).

## 작성 후 점검

1. 100% 규칙: 하위 항목을 모두 끝내면 Task가, Task를 모두 끝내면 단계가 완성되는가. 같은 일이 두 곳에 중복되지 않는가. 검증·모니터링·롤백 절차·문서·정리가 빠지지 않았는가
2. 모든 Task의 To-be가 시스템·사람 주어의 상태이고, 판정 근거가 관측인가
3. 결정을 바꿀 Task가 그 결정을 전제로 하는 Task보다 앞에 있는가
4. dev → stg → prod처럼 앞 결과가 뒤 계획을 바꾸는 Task를 하나로 묶지 않았는가
5. Runbook·롤백 절차가 최초 변경보다 앞에 있는가
6. 순서 제약 있는 실행 세부가 실행 체크리스트에 남아 있는가
7. 제목이 영역·활동·위치가 아니라 대상 + 행동인가

## 용어 근거

- WBS, 작업 패키지(Work Package), 100% 규칙: PMI *PMBOK Guide* "Create WBS", *Practice Standard for Work Breakdown Structures*. 작업 패키지는 비용·기간을 추정하고 관리하는 WBS 최하위 단위다.
- 활동(Activity)은 WBS가 아니라 일정 계획에서 다룬다. 분해(무엇이 포함되는가)와 순서(무엇부터 하는가)는 별개라서 선행관계를 따로 그린다.
- Phase와 phase gate, rolling wave planning: PMBOK.
- 순서 기준(결정 영향 × 늦은 발견의 재작업)과 판단 조건 3가지는 표준이 아니라 이 스킬의 운영 규칙이다.
