# 선택 단계: Phase 2 How · Phase 3 What-if · Phase 4 Apply

learn SKILL.md에서 분리한 선택 단계 상세다. 사용자가 해당 Phase로 넘어갈 때 Read한다.

## Phase 2: How (선택)

내부 동작 원리와 구현을 다룬다. Phase 1 Overview의 동작 원리 다이어그램과 특징 목록을 지도로 삼아, 그 안의 컴포넌트와 특징을 하나씩 깊게 판다. Overview를 다시 그리지 않는다.

### 다루는 내용

- **컴포넌트 내부**: Overview 동작 원리의 각 컴포넌트가 내부에서 무엇을 하는가
- **핵심 코드 경로**: 요청이 처리되는 과정 (critical path)
- **데이터 흐름**: 입력 → 변환 → 출력 과정
- **핵심 자료구조/알고리즘**: 성능과 동작을 결정하는 내부 구조

### Feature Explanation Pattern

Phase 1 Overview에서 고른 특징을 하나씩 설명할 때, 각 특징마다 아래 구조를 따른다:

1. **해결하는 문제**: 이 특징이 없으면 어떤 문제가 발생하는지 (1~2문장)
2. **동작 방식**: 어떻게 작동하는지 (기존 How 내용)
3. **트레이드오프**: 이 접근의 장단점 (성능, 복잡도, 운영 비용 등)
4. **대안 접근법**: 같은 문제를 다르게 해결하는 방법과 차이점

#### 수준별 조절

| Level | 적용 범위 |
|-------|----------|
| easy | 핵심 특징 1~2개에만 간략히 적용 |
| medium | 주요 특징 모두에 적용, 대안은 이름+한 줄 설명 |
| hard | 모든 특징에 적용, 대안의 구현 차이까지 비교 |

#### 예시 (Karpenter Consolidation)

```
**Consolidation (빈 패킹 최적화)**
- 해결하는 문제: 노드가 underutilized 상태로 방치되면 비용 낭비
- 동작 방식: 주기적으로 노드 utilization 평가 → 워크로드를 다른 노드로 이동 → 빈 노드 제거
- 트레이드오프: 비용 절감 vs Pod 재배치로 인한 일시적 서비스 중단
- 대안: Cluster Autoscaler의 scale-down (노드 단위 판단, 빈 패킹 없음)
```

### 수준별 조절

| Level | 깊이 |
|-------|------|
| easy | Overview 다이어그램의 컴포넌트 1~2개를 골라 동작 순서 설명 |
| medium | 주요 인터페이스, 설정 옵션, 동작 모드 |
| hard | KEP·RFC·설계 문서 수준의 인터페이스와 내부 동작. 소스 추적은 사용자가 요청할 때만 (버전 태그 명시) |

### 설명 보조 도구

복잡한 구조는 ASCII 다이어그램이나 시퀀스 다이어그램으로 보충한다:

```
[Component A] --request--> [Component B] --lookup--> [Store]
      ^                          |
      +------response------------+
```

### 이해 점검 + Socratic 전환 질문 (Phase 2 → 3)

Phase 2 내용 전달 후, 아래 순서로 출력한다:

1. **이해 점검** (난이도별 **최소 2개**, 다룬 핵심 개념이 많으면 3~4개로 확장):

```
---
**이해 점검** (스킵하려면 "패스"라고 말씀해주세요)

**초급** (정의형)
1. {Phase 2에서 다룬 주요 컴포넌트의 역할을 한 줄로}
2. {핵심 데이터 흐름의 시작점과 끝점 확인}

**중급** (메커니즘형)
1. {Phase 2에서 다룬 핵심 동작 원리를 나의 단어로}
2. {특정 입력/이벤트가 들어올 때 내부에서 벌어지는 과정 추적}

**고급** (실무 연계형/트레이드오프형)
1. {이 내부 구조가 운영 중 어떤 상황에서 겉으로 드러나는지}
2. {이 구조가 깨지거나 병목이 되는 조건과 그때의 증상}
```

> 템플릿의 난이도별 2개는 **최소 개수**다. Phase 2에서 다룬 핵심 개념이 많으면 난이도별 3~4개까지 늘린다. 2개를 채우려고 범용 질문을 만들지 말고, 반드시 방금 다룬 내용에서 파생시킨다.

2. **Socratic 전환** (다음 Phase로 사고 연결):

```
**How를 고민할 주제**

- 왜 {핵심 컴포넌트가 이런 구조를 선택했는지 관련 질문}?
  (힌트: {한 줄 힌트})
- 왜 {가장 독특한 설계 결정 관련 질문}?
  (힌트: {한 줄 힌트})
- 왜 {다른 접근이 아닌 현재 방식인지: What-if로 이어지는 질문}?
  (힌트: {한 줄 힌트})

생각해보신 후 말씀해주세요. (패스 가능)
```

사용자가 이해 점검에 답변하면 간단히 피드백 후 Socratic 전환 질문을 출력한다.
사용자가 Socratic 질문에 답변하거나 "패스" 시 Phase 3으로 전환한다.

## Phase 3: What-if (선택)

현재 설계를 더 깊이 이해하기 위해 대안을 탐색한다.

### 다루는 내용

- **대안 설계 1~2개**: 실제로 고려되었거나 다른 프로젝트가 선택한 방식
- **Trade-off 비교표**:

```
| 기준         | 현재 설계  | 대안 A     | 대안 B     |
|-------------|-----------|-----------|-----------|
| 복잡도       | ...       | ...       | ...       |
| 성능         | ...       | ...       | ...       |
| 운영 부담    | ...       | ...       | ...       |
| 확장성       | ...       | ...       | ...       |
```

- **선택 이유**: 현재 설계가 채택된 결정적 요인

### 이해 점검 + Socratic 전환 질문 (Phase 3 → 4)

Trade-off 분석 후, 아래 순서로 출력한다:

1. **이해 점검** (난이도별 **최소 2개**, 다룬 핵심 개념이 많으면 3~4개로 확장):

```
---
**이해 점검** (스킵하려면 "패스"라고 말씀해주세요)

**초급** (정의형)
1. {현재 설계와 대안의 핵심 차이를 한 줄로}
2. {비교표의 특정 기준(복잡도/성능 등)에서 각 설계의 위치 확인}

**중급** (메커니즘형)
1. {현재 설계와 대안 중 특정 상황에서 어느 것이 더 적합한지, 그 이유는?}
2. {대안이 특정 기준에서 유리/불리해지는 구조적 원인 설명}

**고급** (실무 연계형/트레이드오프형)
1. {이 트레이드오프가 실제로 문제가 되는 상황은?}
2. {조건이 바뀌면(트래픽 규모, 팀 구조 등) 선택이 뒤집히는 임계점은?}
```

> 템플릿의 난이도별 2개는 **최소 개수**다. Phase 3에서 다룬 대안/트레이드오프가 많으면 난이도별 3~4개까지 늘린다. 2개를 채우려고 범용 질문을 만들지 말고, 반드시 방금 다룬 내용에서 파생시킨다.

2. **Socratic 전환** (다음 Phase로 사고 연결):

```
**What-if를 고민할 주제**

- 왜 {현재 설계가 어떤 조건에서 유리/불리한지 관련 질문}?
  (힌트: {한 줄 힌트})
- 왜 {대안이 특정 조건에서 더 나은지 관련 질문}?
  (힌트: {한 줄 힌트})
- 왜 {실제 적용 시 구체적으로 고려해야 할 질문}?
  (힌트: {한 줄 힌트})

생각해보신 후 말씀해주세요. (패스 가능)
```

사용자가 이해 점검에 답변하면 간단히 피드백 후 Socratic 전환 질문을 출력한다.
사용자가 Socratic 질문에 답변하거나 "패스" 시 Phase 4로 전환한다.

## Phase 4: Apply (선택)

학습 내용을 우리 환경(SOCRA AI 인프라)에 연결한다.

### 다루는 내용

- **현재 사용 현황**: 우리 인프라에서 이 기술을 어떻게 쓰고 있는지
- **적용 가능성**: 새로 도입하거나 개선할 수 있는 영역
- **주의사항**: 우리 환경 특성상 고려할 점 (EKS, Istio, Karpenter 등)

### 참고 환경

- EKS 클러스터: prod / global / stg / dev / idc
- Service Mesh: Istio
- GitOps: ArgoCD
- Node Provisioning: Karpenter
- GPU 클러스터: IDC (Proxmox + Cluster API)
