# 예시: public ingress gateway XFF 위조 차단 (2026-11-16)

세 칸을 처음 나눈 작업이다. 고쳐 쓰는 과정에서 나온 판단을 함께 남긴다.

## Goals
- 클라이언트 IP가 신뢰 경계(public gateway)에서 한 번 정해지고, 그 안쪽 서비스는 위조될 수 없는 값만 받는다.
- 이 신뢰 경계는 정상 사용자를 막지 않는다. 기업 프록시를 거친 사용자도 포함한다.
- 네트워크 앞단이 바뀌어도(홉 추가) 설정만 바꾸면 클라이언트 IP 판정이 유지된다.

## Key Result
(2026-11-23 OKR 형식으로 다시 씀: 한 줄 지표 제목 + 구체 기준 하위 불릿)

- KR1. 신뢰할 수 없는 XFF 항목 잔존율 100% → 0% 달성 (dev·stg·prod)
  - public ingress gateway가 신뢰할 수 없는 항목을 버리고 원래 클라이언트 IP만 남긴다
  - auth-server는 앱 수정 없이 XFF[0]으로 실제 클라이언트의 국가를 판단한다
  - santa-gateway-server 같은 경유지가 XFF[0]을 덧붙여도 그 값은 실제 클라이언트 IP다
- KR2. 사설 대역을 위조한 요청의 whitelistPaths 차단율 100% 유지 (회귀 방지)
  - 경유 경로와 직접 경로 모두 403을 받는다
- KR3. 정상 사용자 host별 5xx·403 비율을 적용 전 7일 최댓값 이하로 유지 (적용 후 24시간)
  - 기업 프록시를 거친 사용자도 포함한다
- KR4. XFF 외 전달 헤더 변경 0건 유지 (회귀 방지)
  - `X-Forwarded-Proto`는 `https`다
- KR5. 앞단에 CDN·WAF를 추가할 때 바꿀 설정 지점 2곳 이하 달성
  - 신뢰 CIDR과 원본 잠금만 바꾼다

## 고쳐 쓴 판단
- "XFF 위조를 탐지한다" → "신뢰할 수 없는 XFF 항목을 버린다": gateway는 위조를 알아내지 못하고 신뢰 여부만 판단한다. 위조가 아닌 기업 프록시의 사용자 IP도 버린다.
- "origin ip" → "원래 클라이언트 IP": CDN의 origin(원본 잠금)과 헷갈린다.
- "santa-gateway-server는 더 이상 [0] 원소를 넘기지 않는다" → 삭제 후 "덧붙여도 그 값은 실제 IP다": 이번 변경은 앱을 고치지 않으므로 사실과 다른 효과였다.
- "XFF를 직접 해석하는 앱 2곳 → 0곳" → 삭제: 앱이 XFF를 읽어도 되는 설계라 목표가 아니었다. KR1이 대신 판정한다.
- 초기 Goals는 "{조건}이 적용된 경우 ~해야 한다" 시나리오 9개였다. 너무 구체적이라는 지적으로 Goals는 방향으로, 판정은 Key Result로, 측정 방법은 `### 검증 설계`로, 세부 케이스는 Todo의 검증 스크립트 항목으로 나눴다.
