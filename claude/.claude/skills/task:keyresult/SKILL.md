# Goals·Key Result·Todo 작성 기준

Task와 업무 노트에서 목표, 판정 기준, 행동을 세 칸으로 나눠 쓰는 기준의 정본이다(2026-11-16 사용자 결정, Key Result 형식은 2026-11-23 OKR 형식으로 변경).
소비처: `tasks:capture`(기대 가치의 `Key Result:`), `notion:add-engineering-note`(`goals`, `value`, `plan`), `tasks:tech-spec`, `grill-me`, `alfred` gate, Jira 티켓(`docs/jira-ticket-template.md`). 소비처에는 이 스킬을 가리키는 포인터만 둔다.

---

## 세 칸 구분

OKR의 Objective·Key Result·Initiative 구조와 같다.

| 칸 | 답하는 질문 | 형태 | 판별 질문 | 놓는 곳 |
|----|------------|------|----------|---------|
| Goals | 끝나면 시스템이 어떤 모습인가 | 큰 방향, 개선 뒤의 모습 | 수단이 정해지지 않은 작업이면, 설계를 다른 안으로 바꿔도 이 문장이 그대로 참인가 | 업무 노트 `goals` |
| Key Result | Goals에 도달했음을 무엇으로 아는가 | 한 줄 지표 제목 + 구체 기준 하위 불릿 | 제3자가 대시보드·쿼리·PR diff의 숫자로 달성 여부를 판정할 수 있는가 | Task·노트 기대 가치의 `Key Result:` |
| Todo | 목표에 도달하려면 무엇을 하는가 | 구체적 Action Item 체크박스 | 했다·안 했다로 끝나는가 | 업무 노트 `plan` (실행 계획) |

- 칸이 섞였는지는 거꾸로 본다: 수단이 정해지지 않은 작업의 Goals에 수단 이름이 있으면 설계가, Goals에 수치가 있으면 Key Result가 섞였다. Key Result에 "작성한다"가 있으면 Todo가, Todo에 "0%"가 있으면 Key Result가 섞였다.
- 검증 방법(무엇으로 재는가, 그 측정이 신호를 잡는가, 언제 판정하는가)은 세 칸 어디에도 쓰지 않고 업무 노트 설계 섹션의 `### 검증 설계`에 둔다.

---

## Goals

- 2~4개. 수치는 넣지 않는다.
- 수단(도구·설정 이름)은 작업의 수단이 이미 정해졌으면 넣는다(예: Objective가 "PgBouncer를 도입해 ..."이면 Goal도 "같은 PgBouncer 표준으로 연결한다"). 수단을 아직 고르는 중이면 넣지 않는다. 이때 Goal은 설계를 다른 안으로 바꿔도 참이어야 한다(2026-11-23 사용자 결정).
- 막아야 할 것과 막으면 안 되는 것을 함께 둔다(예: 위조를 막는다 / 정상 사용자를 막지 않는다). 막는 목표만 두면 과잉 차단을 판정할 Key Result가 생기지 않는다.

```markdown
- 클라이언트 IP가 신뢰 경계에서 한 번 정해지고, 그 안쪽 서비스는 위조될 수 없는 값만 받는다.
- 이 신뢰 경계는 정상 사용자를 막지 않는다.
- 네트워크 앞단이 바뀌어도 설정만 바꾸면 클라이언트 IP 판정이 유지된다.
```

## Key Result

목표 달성 여부를 판단할 수 있는 정량적 수치를 담는다. 업무 목록(Todo)이 아니라 변화된 결과(Outcome)를 쓴다.

**형식: 제목 한 줄 + 구체 기준 하위 불릿 2~3개**(2026-11-23 사용자 결정).

- 제목:
  - `KRn. [대상] [지표] [현재 →] [목표값] [달성 / 단축 / 감소 / 유지] (대상 환경)`
  - 지표 하나, 목표값 하나. 3~5개. 끝은 "달성", "단축", "감소", "유지" 같은 명사형으로 맺는다.
  - 지표는 제3자가 대시보드·쿼리·PR diff로 확인할 수 있는 숫자다(비율, 시간, 건수). "개선", "안정화"처럼 숫자 없는 말은 쓰지 않는다.
- 하위 불릿(구체 기준):
  - 그 수치가 무엇을 뜻하는지 구체적으로 쓴다: 대상 범위(서비스·워크로드·환경), 함께 지켜야 할 기준값(회복 시간, 비교 기준 기간), 이 결과로 소비자가 얻는 것.
  - 현재형 평서문("~다", "~한다")으로 쓴다. 주어는 시스템이나 그 결과를 쓰는 소비자다.
  - 판정 시점이 필요하면 괄호로 붙인다: `(환경별 전환 후 24시간)`, `(적용 후 7일)`.
- 쓰지 않는 것:
  - 기한(날짜). 일정은 마일스톤·Todo에 둔다.
  - 측정 방법(쿼리, 주입 절차, CI 스크립트)과 판단용 시험(예: 다음 단계 결정을 위한 비교 실험). 업무 노트 `### 검증 설계`나 Tech Spec `### 검증`에 둔다. 리뷰 반영으로 KR이 길어지면 절차는 검증으로 옮기고 기준값만 하위 불릿에 남긴다.
  - 행동("작성한다", "배포한다"). Todo로 옮긴다.
  - 사실과 다른 효과: 이번 변경이 바꾸지 않는 대상의 변화를 결과로 쓰지 않는다(예: 수정하지 않는 앱이 "더 이상 ~하지 않는다").
- 짝:
  - 막는 결과와 막지 않는 결과(나빠지면 안 되는 것, 예: 정상 요청·지연이 변경 전과 같다)를 함께 둔다.
  - 이미 충족된 상태를 지키는 KR은 괄호에 `(회귀 방지)`를 붙인다.

```markdown
Key Result:
- KR1. 신뢰할 수 없는 XFF 항목 잔존율 100% → 0% 달성 (dev·stg·prod)
  - public ingress gateway가 신뢰할 수 없는 항목을 버리고 원래 클라이언트 IP만 남긴다
  - auth-server는 앱 수정 없이 XFF[0]으로 실제 클라이언트의 국가를 판단한다
- KR2. 정상 사용자 host별 5xx·403 비율을 적용 전 7일 최댓값 이하로 유지 (적용 후 24시간)
  - 기업 프록시를 거친 사용자도 포함한다
- KR3. 앞단에 CDN·WAF를 추가할 때 바꿀 설정 지점 2곳 이하 달성
  - 신뢰 CIDR과 원본 잠금만 바꾼다
```

엔지니어링 OKR 예시:

```markdown
DevOps 팀 Goal: 배포가 실패해도 서비스가 흔들리지 않는 배포 플랫폼을 만든다.
- KR1. 변경 실패율 15% → 5% 이하로 감소
- KR2. 장애 평균 복구 시간(MTTR) 30분 이내로 단축
  - 대상: prod sev1·sev2 장애. 알럿 발화부터 사용자 영향 해소까지
  - 분기 평균이며, 한 건도 2시간을 넘지 않는다
- KR3. 배포 롤백 소요 시간 5분 이내 달성
- KR4. 월간 배포 횟수 현재 수준 이상 유지

Developer Goal: 결제 API를 빠르고 믿을 수 있게 만든다.
- KR1. 결제 API p99 지연 800ms → 300ms 이하로 단축
- KR2. 결제 API 5xx 비율 0.1% 이하 유지
- KR3. 결제 도메인 테스트 커버리지 80% 이상 달성
```

## Todo (실행 계획)

- 목표에 도달하기 위한 구체적 Action Item을 체크박스(`- [ ]`)로 실제 실행 순서대로 나열한다. 한 체크박스 = 따로 착수하고 따로 끝낼 수 있는 행동 하나(문의, 측정, 스크립트 작성, PR 하나, 환경 롤아웃 하나).
- 동사로 끝내고("~한다"), Key Result에 번호가 있으면 끝에 기여하는 KR을 `(KR1, KR3)`로 붙인다. 통과 기준(수치)은 Key Result에만 두고 반복하지 않는다.
- 항목이 많으면 단계 라벨(`*사전 확인*`, `*환경별 적용*`, `*정착*`, `*분리*`)로 묶는다.
- 환경별로 PR이 따로 나가면(dev → stg → prod 단계적 배포) 환경마다 항목을 나눈다.
- 범위 밖 후속 작업도 `*분리*` 아래 체크박스로 남긴다.
- 롤백(`롤백:`) 등 업무 노트 고유 규칙은 `notion:add-engineering-note` "실행 계획 작성 기준"을 따른다.

```markdown
*사전 확인*
- [ ] 제품팀에 auth-server 국가 판정이 XFF의 어느 값을 쓰는지 문의한다 (KR2)
*환경별 적용*
- [ ] dev PR을 열고, 머지 뒤 검증 스크립트를 돌린다 (KR1, KR3)
```

## 작성 후 점검

1. Goals에 수치가 없는가. 수단을 아직 고르는 작업이면 수단 이름도 없는가
2. Key Result 제목이 지표 하나·목표값 하나이고, 하위 불릿에 대상 범위·기준값이 구체적으로 있는가. 기한이 들어가지 않았는가
3. Key Result에 막지 않는 쪽 문장이 있는가
4. Key Result에 행동·측정 방법이 섞이지 않았는가
5. Todo가 모두 동사로 끝나는 행동이고, 수치 기준을 반복하지 않는가
6. 이번 변경이 바꾸지 않는 대상의 변화를 결과로 쓰지 않았는가
