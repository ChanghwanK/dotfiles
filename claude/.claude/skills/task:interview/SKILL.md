# task:interview

완료한 작업 하나를 증거 기반 팩트 시트로 고정한 뒤, 4축 면접 문답 + hook + 취약점 방어 구조로 전환한다.

---

## 핵심 원칙

- **증거가 먼저, 스토리는 나중**: 모든 숫자·판단 근거는 수집한 산출물(PR 본문·코멘트·커밋·wiki·세션)에서
  나와야 한다. 기억이나 일반 지식으로 채우지 않는다. 숫자 하나가 틀리면 스토리 전체가 흔들린다.
- **발단을 지어내지 않는다**: "왜 이 작업을 시작했나"가 산출물에 없으면 사용자에게 묻는다.
  그럴듯한 발단을 만들어 넣으면 사용자가 면접에서 그걸 반복한다.
- **팩트 시트 확정 후 답변 작성**: Step 2에서 사용자 확인을 한 번 받는다. 틀린 숫자는 여기서 잡는다.
- **hook은 명시적으로**: 어떤 문장이 어떤 후속 질문을 유도하는지 표시한다. 면접관 질문을 "유도"하는 것이
  이 스킬의 차별점이다. 우연히 좋은 답변이 아니라 설계된 답변이어야 한다.
- **취약점은 3종으로 분류해 다르게 방어**: 미완료 / 설계상 한계 / 내가 틀렸던 것. 대응법이 다르다
  (`references/question-bank.md` 4절).
- **꼬리질문은 why 체인이다**: 압박이 아니라 "왜 → 왜 → 왜". 체인이 원리·제약·가치 판단에 닿으면 통과,
  "그냥"에서 끊기면 그 지점이 갭이다. 중간 판단은 PR이 아니라 세션에 있으므로 세션 수집이 필수다.
- **"안 쓴 것"이 클라이맥스**: 쓴 지표·선택한 대안을 나열하는 답변보다 "이건 안 썼다, 왜냐하면"이 강하다.
  선택 근거 축에서 반드시 기각한 대안과 이유를 넣는다.
- **한 덩어리로 쏟지 않는다**: script 모드도 라운드마다 구분선과 정지 지점을 둔다.
  6천 자를 한 번에 내면 읽지 않고 스크롤한다.
- **읽기만으로 끝내지 않는다**: script 모드 종료 시 drill 모드 재실행을 제안한다.
  모범답안을 읽는 것과 말할 수 있는 것은 다르다 (comprehension debt).
- **스크립트와 MCP만 사용**: `gh`, `git`을 직접 호출하지 않는다. PR·plan은 공유 수집 스크립트,
  Notion은 MCP, 세션 메모리는 claude-mem MCP로 읽는다.

## 워크플로우

### Step 0: 대상·모드·유형 확인

대화에서 파악 가능하면 묻지 않는다. 불명확한 항목만 한 번에 묻고 기본값을 명시한다.

| 항목 | 선택지 | 기본값 |
|------|--------|--------|
| **대상** | PR 번호 / Notion Task URL / plan 이름 / 현재 세션 | 현재 세션에서 감지, 없으면 질문 |
| **모드** | `script` (Claude가 질문과 답변을 모두 작성) / `drill` (질문만 내고 사용자 답변을 채점) | `script` |
| **면접 유형** | `deep-dive` (기술 심층) / `behavioral` (STAR, 협업·판단) / `mixed` | `deep-dive` |
| **출력 범위** | `full` / `opening` / `round <n>` | `full` (라운드 사이 정지 지점 포함) |

`behavioral`은 4축 질문의 초점이 "메커니즘"에서 "판단·협업·갈등"으로 바뀐다
(`references/question-bank.md` 5절).

**모드 규칙**: 명시가 없으면 무조건 `script`다. `drill`은 사용자가 "직접 답해보겠다", "채점해달라",
"문제 내달라"고 한 경우에만 쓴다. 인자에 `drill`이 있어도 이 세션에서 처음이면 한 줄로 확인한다:

```
drill 모드는 제가 질문만 내고, 답변을 직접 하시면 채점하는 방식입니다. 이대로 진행할까요?
(답변까지 제가 작성하는 script 모드를 원하시면 "script")
```

### Step 1: 증거 수집

**1-a. 1차 소스** (대상별)

```bash
# PR: 본문 + 코멘트 + 리뷰 + 참조 PR 번호. 코멘트에 실험 결과·사후 근거가 있는 경우가 많다
python3 /Users/changhwan/.claude/skills/task:understand-quiz/scripts/collect_work_context.py pr --ref <번호> --comments

# plan 파일
python3 /Users/changhwan/.claude/skills/task:understand-quiz/scripts/collect_work_context.py plan --name <이름>
```

Notion Task는 `mcp__notion-personal__API-retrieve-page-markdown`으로 읽는다.
현재 세션이 대상이면 대화 맥락 자체가 1차 소스다.

**1-b. PR 체인 추적** (MUST)

1차 PR의 `referenced_prs`를 따라 **같은 스크립트로 각 PR을 추가 수집**한다. 계측 PR → 변경 PR →
실험 PR → 정리 PR → 문서 PR 순으로 체인이 형성되는 경우가 많고, **발단(왜 시작했나)은 대개 첫 PR에만
있다.** 체인은 2단계(참조의 참조)까지 따라간다. 그 이상은 사용자에게 확인한다.

**체인이 닫힐 때** (A ↔ B만 서로 참조하고 발단 PR에 못 닿는 경우) 순서대로 보완한다:

```bash
# 커밋 로그 키워드 검색으로 체인 밖 PR을 찾는다 (레포 디렉토리에서 실행)
python3 /Users/changhwan/.claude/skills/task:understand-quiz/scripts/collect_work_context.py log-search \
  --grep "<작업 키워드>" --grep "<대상 컴포넌트>" --since "120 days ago"
```

1. `log-search` 결과에서 대상 PR보다 **앞선 날짜**의 PR을 골라 `pr --ref --comments`로 수집한다
   (계측·준비·대시보드 PR이 여기서 나온다)
2. 그래도 없으면 세션 메모리 검색 (1-c)
3. 그래도 없으면 발단 확인 게이트 (1-d)

**1-c. 세션 결정 로그** (MUST)

PR에는 최종 결정만 남고 **중간 판단(왜 그 값이었다가 바뀌었나, 어떤 대안을 검토했다 버렸나)은 세션에만
남는다.** 꼬리질문의 why 체인은 이 중간 판단에서 나온다. 소스는 압축도 순으로 읽는다.

| 순서 | 소스 | 도구 | 얻는 것 |
|------|------|------|--------|
| 1 | Notion Engineering 노트 (Task DB `Engineering` 관계) | `API-retrieve-page-markdown` | 대안 검토·미결 질문·정정 이력이 가장 압축돼 있다. 있으면 먼저 읽는다 |
| 2 | 세션 목록 | `claude-mem search` (키워드 + `dateStart` + `orderBy: date_asc`) | 시간 순서, 전환·오독 신호가 있는 세션 제목 |
| 3 | 결정 순간 스니펫 | `search_session_transcripts` (구체 문자열) | 어느 세션에 그 순간이 있는지 |
| 4 | 세션 본문 | `list_events` (`limit` 30~40, 최신부터) | 결정의 이유·버린 대안·계기 |

**검색 문자열 고르는 법 (3단계)**: 팩트 시트의 **숫자와 고유명사**를 그대로 넣는다. 자연어보다 훨씬 잘 잡힌다.
예: `"274 MiB"`, `"33.8%"`, `"채택선"`, `"victim"`, `"이건 iowait 아닌가"`. 사용자 본인의 질문 문장이
잡히면 그게 곧 전환 순간이다.

**주의**: `claude-mem timeline`의 query 모드는 관측(observation) 기준이라 관측이 생성되지 않은
세션(목록에 `0 obs`로 표시)에는 닿지 않는다. 그 경우 3~4단계의 ccd 도구를 쓴다.
`list_events`는 최신부터 보여주므로 꼬리는 문서 정리 단계인 경우가 많다. 결정 순간은 3단계 스니펫으로
위치를 잡은 뒤 필요한 구간만 `before_uuid`로 거슬러 읽는다. 1,000개 넘는 세션을 전부 페이징하지 않는다.

결정 로그 한 행 = `{결정, 이유, 검토했다 버린 대안, 바뀐 시점과 계기, 출처 세션}`.
팩트 시트 하단에 별도 표로 붙인다 (`assets/fact-sheet.md` 2절). **바뀐 결정**(값·방법·지표가 중간에
달라진 것)과 **안 한 결정**(도입하지 않은 것)을 우선 적는다. 바뀐 결정은 why가 두 겹이라 체인이 깊어진다.

보조: `task:review` 산출물이 있으면 Step 2의 초안으로, wiki는 문서 PR이 체인에 없을 때만 `Read`.

**1-d. 발단 확인 게이트**

수집 결과에 "왜 시작했나"(사건·요청·관측)가 없으면 **여기서 멈추고 묻는다.**

```
발단이 산출물에 없습니다. 이 작업을 시작하게 된 계기가 무엇이었습니까?
(예: 장애·알럿, 사용자 요청, 비용 리뷰, 관측 중 발견)
```

### Step 2: 팩트 시트 고정

`assets/fact-sheet.md` 템플릿으로 작성한다. 답변 작성 전 유일한 확인 지점이며, **모드에 따라 노출 범위가 다르다.**

| 모드 | 사용자에게 보여주는 것 | 이유 |
|------|----------------------|------|
| `script` | 팩트 시트 전체 + 확인 요청 | 틀린 숫자를 답변 전에 잡는다 |
| `drill` | **출처 커버리지 요약만** (소스 목록, 확보한 항목 수, 비어 있는 항목) + 비어 있는 항목만 질문 | 팩트 시트 전체를 펼치면 모범답안이 노출되어 채점이 무의미해진다 |

drill 모드 출력 예:

```
증거 수집 완료. 팩트 시트 18항목 중 17항목 확보 (출처: #8843 본문·코멘트, #8845, #8774, #8857).
비어 있는 항목: 없음. 발단은 #8774에서 확인됐습니다.
팩트 시트는 채점 라운드에서 항목별로 공개합니다.
```

MUST 포함:
- 발단 사건 (1줄), 문제 규모 (정량), 사용자 영향 증거
- 원인 귀속 증거 (독립 증거 N개, 각각 1줄)
- 선택지와 **기각 이유**
- 결과 (before → after 정량), 비용, 리스크, 롤백
- **미완료·미측정 항목** (Step 5 취약점 재료. 여기서 빠지면 압박 라운드가 빈약해진다)
- 방향 전환·오독 이력 (hook 재료)

정직성 규칙: 미측정을 측정으로, 부분 달성을 달성으로 쓰지 않는다. 면접에서 그대로 들통난다.

### Step 3: 스토리 골격 + hook 설계

- **90초 오프닝**: 결론 → 발단 → 접근 순서 → 남은 것. 두괄식
- **5분 확장판**: 오프닝에 원인 귀속 증거와 선택 근거 1개씩 추가
- **hook 3~4개**: `references/question-bank.md` 3절의 선정 기준(자기인식 / 반증 가능한 예측 적중 /
  표준에서의 의도적 이탈 / 상관·인과 구분)으로 고르고, 각 hook이 유도하는 후속 질문을 표로 명시

출력 골격은 `assets/output-script.md` 1~2절.

### Step 4: 4축 Q&A

축별 질문 설계 기준과 답변 필수 요소는 `references/question-bank.md` 1~2절을 따른다.
축당 2~3문항, 총 8~12문항. 각 답변은 실제로 말할 수 있는 길이(200~400자)로 쓴다.

**script 모드**: 질문 + 답변을 함께 출력한다. 라운드(축) 사이에 구분선과 정지 지점을 둔다.

```
--- Round 1 (문제 정의) 끝. 계속할까요, 여기서 멈출까요? ---
```

**drill 모드**: 라운드의 질문만 먼저 낸다. 사용자 답변 후 채점한다 (`assets/output-drill.md`).
채점 순서는 고정이다: ① 핵심 포인트 커버리지(✅/❌) → ② 모범답안 → ③ Socratic 후속 질문 1개.
❌가 있으면 그 갭을 겨냥한 후속 질문을 내고, 통과할 때까지 반복한다. 루프 종료는 사용자가 결정한다.

### Step 5: 꼬리질문 라운드 (why 체인) + 취약점 분류

꼬리질문은 압박이 아니라 **why를 파고들어 이해 깊이를 재는 것**이다. 면접관은 하나의 결정을 잡고
"왜 → 왜 → 왜"로 내려간다. 체인이 어디서 끝나는지가 이해 깊이다.

1. 결정 로그(1-c)에서 **핵심 결정 4~6개**를 고른다. 값 선택, 범위 선택, 방법 선택, 순서 선택, 지표 선택이 후보다
2. 결정마다 why 체인을 **깊이 2~3**으로 쓴다. 각 단계는 앞 답변의 한 구절을 잡아 "그건 왜"로 잇는다
3. 체인의 마지막은 반드시 셋 중 하나로 끝난다 (`references/question-bank.md` 4절):
   - **원리**: 정의·메커니즘 (예: weighted_io_time의 정의, iowait의 회계 위치)
   - **제약**: 바꿀 수 없는 외부 조건 (예: 인스턴스 EBS baseline, 팀 리드타임)
   - **가치 판단**: 명시된 트레이드오프 (예: 마진 8%를 비용보다 우선)
4. 체인이 셋 중 어디에도 닿지 못하고 "그냥", "관행상", "기억 안 남"으로 끝나면 **그 지점이 P0 갭**이다.
   Step 6에 넘긴다

도전형 질문(외적 타당도, ROI, 증상 vs 근본, 롤백, 다시 한다면)은 why 체인 뒤에 **2~3개만** 붙인다.
이건 깊이가 아니라 넓이를 재는 질문이라 보조다.

취약점은 **3종으로 분류**하고 유형별 대응 규칙으로 답변을 쓴다.

| 유형 | 대응 |
|------|------|
| 미완료 | "진행 중"이라고 정직하게 + 판정 기준을 이미 정해뒀음을 제시 |
| 설계상 한계 | 한계를 먼저 말하고 임계점·후속 레버 제시 |
| 내가 틀렸던 것 | 교훈으로 전환 + 재발 방지 산출물(문서·표준·알럿) 연결 |

취약점 섹션은 "미리 알고 들어가기" 표로 출력한다. 숨기면 파고들었을 때 무너지고, 먼저 말하면 신뢰가 올라간다.

### Step 6: 개념 갭 + 인계

- **P0** (답 못 하면 스토리 붕괴): Step 5에서 종결 못 한 why 체인의 끝 지점 + 핵심 지표·메커니즘의 정의.
  이 스킬 안에서 목록 + 핵심 질문 1개씩 + "왜 필요한가"
- **P1/P2**: 목록만 내고 인계 제안 한 줄

```

💡 `/wiki:note 무지` 로 P0 중 몰랐던 개념을 무지 노트에 저장할 수 있습니다.
```

## 주의사항

- **코멘트 수집을 빼먹지 않는다**: `--comments` 없이 PR을 읽으면 실험 결과·사후 검증이 통째로 빠진다.
  EBS throughput 케이스에서 채택 근거 전체가 코멘트에 있었다.
- **체인의 첫 PR을 반드시 읽는다**: 발단은 계측·준비 PR에만 적혀 있는 경우가 많다.
- **작업 특화 산출물을 프로세스로 오해하지 않는다**: "지표 지도" 같은 표는 그 작업의 산출물이지 스킬의
  기본 출력이 아니다. 축별 증거 정리 패턴으로만 일반화한다.
- **개념 설명을 스킬 안에서 하지 않는다**: P0 갭도 "무엇을 알아야 하는가"까지만. 설명은 `learn`으로.
- 설계 근거(첫 실행 세션 회고)는 `references/design-rationale.md` 참조.
