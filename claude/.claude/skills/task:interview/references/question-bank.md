# 질문 은행: 축별 설계 기준, hook, 압박, 취약점

## 1. 4축 질문 설계 기준

| 축 | 질문 성격 | 대표 질문 패턴 |
|----|----------|---------------|
| 문제 정의 | "왜 문제였나", "어떻게 판정했나" | "그게 왜 문제였습니까? 좀 느린 게 장애는 아니잖아요" / "X가 아니라 Y가 병목이라는 건 어떻게 아셨습니까?" / "포화·이상 판정은 어떤 지표로 하셨습니까?" |
| 해결 | "순서를 왜 그렇게", "어떻게 증명했나" | "그래서 바로 고치셨나요?" / "원인이 그것이라는 건 어떻게 증명하셨습니까?" / "실험은 어떻게 설계하셨습니까?" |
| 선택 근거 | "왜 그 값", "왜 그 범위만", "왜 표준에서 벗어났나" | "왜 하필 그 값입니까? 더 큰 값도 있는데요" / "왜 그 대상만 바꾸셨습니까? 전부 바꾸면 되지 않나요?" / "보통 dev → stg → prod인데 왜 안 그러셨습니까?" |
| 결과 | "정리해달라", "과다 아닌가", "뭘 남겼나" | "결과를 정리해 주시죠" / "그 값이 과다 프로비저닝은 아닙니까?" / "이 작업에서 팀에 남긴 게 뭡니까?" |

## 2. 축별 답변 필수 요소

| 축 | 반드시 들어갈 것 |
|----|-----------------|
| 문제 정의 | 사용자 영향 / 판정 지표 (**쓴 것과 안 쓴 것**) / 상관과 인과의 구분 명시 |
| 해결 | 독립 증거 N개 (각각 왜 독립인지) / 실험 설계 3요소 (교란 통제, 사전 등록 판정, 안전장치) / 순서를 바꾼 이유 |
| 선택 근거 | 역산 근거 (어디서 그 값이 나왔나) / **기각한 대안과 이유** / 표준 이탈의 명시와 이유 |
| 결과 | before → after 정량 / 한계 (fitted vs headroom) / 문서·표준·알럿 반영 / 아직 안 된 것 |

"안 쓴 것"을 말하는 답변이 나열형 답변보다 강하다. 판정 지표, 기각 대안, 도입하지 않은 컴포넌트 중 최소 하나는 "이건 안 했다, 왜냐하면"으로 쓴다.

## 3. hook 선정 기준

hook은 면접관이 따라 묻게 만드는 미끼다. 오프닝에 3~4개를 심고, 각 hook이 유도하는 후속 질문을 표로 명시한다.

| 기준 | 왜 강한가 | 예 |
|------|----------|-----|
| 자기인식 (틀렸던 것) | 성숙도 신호. 면접관이 거의 반드시 따라 묻는다 | "두 번 틀렸습니다. %util과 1-idle" |
| 반증 가능한 예측 적중 | 메커니즘 이해의 증거 | "언팩 쓰기가 pod cgroup 밖일 거라 예측했고 87% 미귀속으로 맞았습니다" |
| 표준에서의 의도적 이탈 | 판단력 신호. 규칙을 아는 사람만 의도적으로 벗어난다 | "dev → stg → prod를 의도적으로 건너뛰고 PR에 명시했습니다" |
| 상관과 인과의 구분 | 과학적 태도 신호 | "이건 상관이고 인과는 실험에서 확인했습니다" |
| 준비 단계의 부재 | "없던 것"을 먼저 만든 판단 | "판정할 계측 자체가 없었습니다" |

hook을 오프닝에만 두지 않는다. 각 라운드 답변 끝에도 다음 라운드를 유도하는 문장을 1개 둔다.

## 4. 꼬리질문: why 체인, 도전형, 취약점 3분류

### why 체인 규칙

하나의 결정을 잡고 "왜"로 내려간다. 각 단계는 **앞 답변의 한 구절**을 잡아 잇는다. 범용 질문으로 새지 않는다.

| 깊이 | 질문 형태 | 예 (EBS 케이스, 결정 = 250 선택) |
|------|----------|----------------------------------|
| 1 | 왜 그 결정인가 | "왜 250입니까?" → 인스턴스 baseline 298에서 PV 24를 뺀 274가 상한 |
| 2 | 앞 답변의 전제는 왜 그런가 | "PV 몫을 왜 24로 잡으셨습니까?" → 실측 최대값 |
| 3 | 그 전제의 전제는 | "왜 평균이 아니라 최대값입니까?" → 마진은 최악 케이스 기준. 평균으로 잡으면 피크에서 인스턴스 상한을 넘어 크레딧에 의존하게 됨 |
| 끝 | 종결 유형 표시 | **가치 판단** (재현성 > 8% 여유) + **제약** (baseline은 바꿀 수 없음) |

**종결 3유형**

| 유형 | 정의 | 답변에서 보이는 형태 |
|------|------|-------------------|
| 원리 | 정의·메커니즘. 더 물으면 교과서로 감 | "weighted_io_time은 in-flight 요청 수의 시간 적분이라 rate가 곧 평균 큐 깊이입니다" |
| 제약 | 바꿀 수 없는 외부 조건 | "m6i.2xlarge의 EBS baseline이 298이고 이건 인스턴스 타입을 바꾸지 않는 한 고정입니다" |
| 가치 판단 | 명시된 트레이드오프. 다른 사람은 다르게 고를 수 있음 | "비용 8%보다 크레딧 미의존 재현성을 우선했습니다. 반대로 골라도 틀린 건 아닙니다" |

**미종결 신호**: "그냥", "관행상", "그때는 그렇게 봤습니다", "기억이 안 납니다". 이 지점이 P0 갭이다.
script 모드에서는 Claude가 답변을 쓰다가 종결 유형을 못 붙이는 지점이 곧 갭이다. 억지로 붙이지 않는다.

**체인 후보 선정**: 결정 로그에서 (a) 값이 바뀐 결정 (250 → 300 → 250), (b) 방법이 바뀐 결정 (v1 → v2),
(c) 표준에서 벗어난 결정, (d) 안 한 결정 (도입하지 않은 것)을 우선한다. 바뀐 결정은 why가 두 겹이라 체인이 깊어진다.

### 도전형 질문 (why 체인 뒤에 2~3개만)

깊이가 아니라 넓이를 재는 질문이다. 보조로만 쓴다.

| 유형 | 질문 패턴 | 답변 골격 |
|------|----------|----------|
| 외적 타당도 | "dev에서 검증한 걸 prod에 그대로 적용해도 됩니까?" | 검증한 것은 절대값이 아니라 방향성 / 값은 prod 실측에서 / 남는 위협과 계획 |
| ROI | "실험 없이 그냥 했으면 빨랐을 텐데요" | 실험 비용 명시 / 얻은 것 3개 / **실험을 하지 말았어야 할 조건**도 제시 |
| 증상 vs 근본 | "근본 원인은 따로 있지 않습니까?" | 인정 / 지혈과 근본의 리드타임·비용 비교 / 근본을 잊지 않게 심어둔 임계점 |
| 롤백 | "되돌리기 쉽습니까?" | 방법 / 즉시 원복 여부와 이유 / 최악 시나리오 |
| 다시 한다면 | "다시 한다면 뭘 바꾸시겠습니까?" | 3개, 각각 구체적 (어떤 명령·어떤 지표·어떤 순서) |

### 취약점 3분류와 대응

| 유형 | 정의 | 대응 규칙 | 실패 패턴 |
|------|------|----------|----------|
| 미완료 | 계획했으나 아직 안 한 것 (측정 대기, 재현 미실행) | "진행 중"이라고 정직하게 + 판정 기준을 이미 정해뒀음을 제시 | "완료"로 포장 → 후속 질문에서 무너짐 |
| 설계상 한계 | 선택한 값·구조가 가진 구조적 한계 (fitted value, 헤드룸 없음) | 한계를 **먼저** 말하고 임계점과 후속 레버 제시 | "충분히 했다"고 말함 → 증상 vs 근본에서 무너짐 |
| 내가 틀렸던 것 | 오독·잘못된 초기 판단 | 교훈으로 전환 + 재발 방지 산출물(문서·표준·알럿) 연결 | 숨김 → 세션 기록이나 PR 코멘트에서 드러남 |

## 5. behavioral 유형일 때의 축 변환

| 축 | deep-dive 초점 | behavioral 초점 |
|----|---------------|----------------|
| 문제 정의 | 메커니즘, 지표 | 누가 어떻게 문제를 제기했나, 우선순위 갈등 |
| 해결 | 증거, 실험 | 협업 방식, 설득 과정, 반대 의견 처리 |
| 선택 근거 | 역산, 대안 기각 | 트레이드오프를 누구와 어떻게 합의했나, 표준 이탈을 어떻게 알렸나 |
| 결과 | 정량, 한계 | 팀에 남긴 것, 후속 오너십, 배운 것 |

behavioral은 STAR(Situation / Task / Action / Result)로 답변 골격을 잡되, Result에는 deep-dive와 같은 정량을 넣는다.

## 6. 개념 갭 우선순위 기준

| 등급 | 기준 | 처리 |
|------|------|------|
| P0 | 답 못 하면 스토리 신뢰도가 무너지는 개념 (핵심 지표의 정의, 핵심 메커니즘) | 스킬 안에서 목록 + 핵심 질문 1개 + 왜 필요한가 |
| P1 | 물어보면 답해야 하는 개념 (인접 메커니즘, 도구 내부) | 목록 + `learn:interview` 인계 |
| P2 | 여유 있으면 좋은 것 (방법론 용어, 대안 기술) | 목록만 |
