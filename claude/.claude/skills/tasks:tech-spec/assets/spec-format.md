# Tech Spec 포맷 (정본)

H2 다섯 개만 고정 포맷이다. 이름·순서를 바꾸지 않고, 더하거나 빼지 않는다. H3 이하는 주제에 맞게 자유롭게 짓는다.
`spec_tool.py lint`가 이 규칙을 기계적으로 검사한다.

```
# {제목}                                   ← H1 1개. 예: [PE - 2] pgbouncer 도입

> [!objective] {Objective 한 문장}          ← 콜아웃. "~한다."로 끝나는 목표 문장

## Background
## Goals & KeyResult
## 설계 및 계획
## 예상 질문 정리
## 마일스톤
```

문체는 `~/.claude/docs/notion-writing-style.md`를 따른다(평서체 "~한다", 결론을 첫 불릿에, em dash 금지).
아래 "작성 안내"는 작성자용 지침이다. 본문에 옮겨 적지 않는다.

---

## Objective (콜아웃)

- 작업이 끝났을 때 달라지는 상태를 한 문장으로 쓴다. 수단(무엇을 도입해)과 목적(무엇을 표준화·해결한다)을 함께 담는다
- 예: `PgBouncer를 도입해 파이썬 백엔드의 DB Connection 관리 계층을 표준화한다.`

## Background

작성 안내: 어떤 문제를 해결하고자 하는지 정리한다.

- 번호 목록으로 문제를 쓰고, 각 문제 아래 하위 항목(a, b...)으로 근거를 단다. 근거는 측정치·코드 경로·리서치 주장 id다
- 관측된 사건이 아니라 그 사건을 가능하게 한 구조·절차의 결함을 문제로 쓴다(문제 검증 게이트 G1~G4)
- 측정으로 확정하지 못한 원인은 문장 끝에 `(원인 미확인)`을 붙이고, 원인 후보와 가르는 관측을 하위 항목으로 쓴다

```markdown
1. 파이썬 백엔드의 커넥션 관리가 서비스별·환경별로 제각각이다.
    1. k6는 RDS Proxy를, socraai는 요청마다 커넥션을 새로 만든다.
```

## Goals & KeyResult

- `**Goal**` 불릿 아래에 큰 방향 1~3개, `**Key Result**` 불릿 아래에 핵심 결과 3~5개를 쓴다
- Key Result 형식의 정본은 `task:keyresult` 스킬이다(제목 한 줄: 지표 하나·목표값 하나, 구체 기준 하위 불릿 2~3개, 기한 없음, 측정 방법은 `### 검증`). 엔지니어링 OKR 예시도 그 스킬에 있다
- 범위를 통제할 필요가 있으면 `**Non-Goal**` 불릿을 더한다(선택)

이 스펙의 형태:

```markdown
- **Goal**
    - Python 백엔드는 어느 환경, 어느 서비스든 하나의 표준으로 DB에 연결한다.
    - DB 연결 계층의 장애가 서비스 장애로 번지지 않는다.
- **Key Result**
    - KR1. k6·socraai DB 연결의 PgBouncer 경유율 0% → 100% 달성 (dev·stg·prod)
        - 대상: k6·socraai 앱 워크로드 전체(migrate는 `{db}_session`)
        - CNPG Pooler·RDS Proxy 등으로 직접 가는 우회 연결이 0건이다(환경별 전환 후 24시간)
    - KR2. PgBouncer pod 장애 시 실패 요청 비율 0.1% 이하 유지 (stg)
        - Celery task는 최종 완료 100%, 즉시 종료 뒤 30초 안에 실패율이 장애 전 수준으로 돌아온다
- **Non-Goal**
    - ...
```

## 설계 및 계획

작성 안내:
- 테크 스펙에서 가장 긴 파트다. 준비한 모든 리서치와 준비 내용을 여기에 쓴다
- 어떻게 기술적, 엔지니어링적으로 접근할지 상세히 묘사한다(가설과 근거 등). 어떻게 할지 확실히 결정하지 못한 부분은
  어떤 것들을 고려하고 있는지 목록화해서 적는다
- 그렇게 하면 리뷰어들이 올바른 결정을 내리도록 돕게 된다. 얼마나 깊게 쓸지는 스펙의 목적과 독자에 맞춘다
- 작성자가 생산적인 제안을 받을 수 있도록 충분히 상세하게 계획을 적는다
- 이 섹션은 이 작업이 다른 시스템들과 어떻게 상호작용하는지 그림이나 다이어그램을 넣기 좋은 지점이다. 사용자와 시스템 간의 시퀀스
  다이어그램, 서비스와 API 간의 데이터 흐름 다이어그램, 데이터베이스 ERD 등을 넣으면 독자의 이해를 높인다.
  상호작용이 있는 스펙은 다이어그램을 1개 이상 넣는다(`archify`: 시퀀스·데이터 흐름·아키텍처, `diagram-design`: 비교·타임라인).
  흰 배경 PNG로 내보내 `![캡션](/절대경로.png)`로 넣는다. 간단한 시퀀스·흐름도는 ```mermaid 펜스로 써도 된다(HTML Artifact가 바로 그린다). 다이어그램은 본문을 대신하지 않으며, 결정에 필요한 핵심은 글로도 쓴다
- 스펙이 로우 레벨까지 다뤄야 한다면 인터페이스 명세까지 모두 쓴다: HTTP 응답 코드, JSON 요청·응답 포맷, 에러 명세,
  인프라 스펙이면 설정 파라미터와 값, 포트·프로토콜, 타임아웃, 에러 시 클라이언트가 받는 신호(에러 코드·메시지)

H3 구성(이름은 자유, 아래는 권장 순서):

0. `### 결정 필요` (본문에 `(미결정)`이 하나라도 있으면 필수, 설계 및 계획의 첫 H3): 사용자가 정해야 하는 항목을 한 표로 모은다.
   `| # | 결정 | 필수 | 선택지 | 추천 | 판단 기준 |`. 필수 칸은 `필수` 또는 `필수 아님`만 쓴다. 필수는 정해야 다음 단계가 진행되고
   추천만으로 정할 수 없는 항목(추천 없음, 보안, 제품팀 합의, KR 기준), 필수 아님은 추천값이나 측정 결과로 진행할 수 있어 확인만 하면 되는 항목이다. 표 위에 이 정의를 한 문장으로 쓴다.
   측정을 해야 정할 수 있는 항목은 추천 칸에 "측정 후"와 측정 방법 위치를 쓴다. 본문의 `(미결정 ...)` 표시는 그대로 두고, 표와 본문 표시가 서로 빠짐없이 대응해야 한다.
   HTML 렌더는 이 표를 상단 배너(필수·필수 아님 건수와 항목 이름, 필수 먼저)와 강조 표로 보여 준다.
   표 바로 아래에 항목마다 상세 설명을 `<details markdown="1"><summary>N. 결정 이름</summary> ... </details>`로 쓴다(N은 표의 #).
   독자가 그 기술을 모른다고 보고 쓴다: 무엇을 정하나, 배경(개념을 평문으로), 선택지별로 달라지는 것, 추천과 이유(추천이 없으면 없는 이유), 정하지 않으면 막히는 것.
   HTML 렌더는 이 설명을 해당 행의 '상세 보기' 버튼으로 펼치는 행으로 옮긴다
1. `### Todo` (필수): 체크박스 Action Item. 하위 체크박스로 쪼갤 수 있다. 실행 단위·문체는 `task:keyresult` "Todo"
2. 주제별 설계 H3 (1개 이상): 예 `### Server와 연결 관리`, `### pgbouncer 가용성 챙기기`.
   결정마다 "가설 → 근거(리서치 주장 id·측정·코드) → 기각한 대안"을 쓴다. 미결정이면 `(미결정)`과 고려 중인 선택지·판단 기준을 쓴다
3. `### 고려해야할 것 및 검증 목록` (권장): 카테고리 토글 아래 질문 토글, 그 안에 현재 답 또는 검증 방법
4. `### 검증` (권장): 각 Key Result의 검증 설계. 어떻게(다시 돌릴 수 있는 쿼리·명령), 왜 이 방법(신호를 잡는 근거, 버린 방법), 언제
5. `### 마이그레이션 계획` 또는 `### 롤아웃 계획` (인프라·prod 변경 시 권장): 단계, 단계별 통과 기준, Blast radius, 롤백 방법과 걸리는 시간

토글은 HTML `<details>`로 쓴다. 토글 블록은 목록 안에 넣지 않고 빈 줄로 감싼다.

```markdown
<details markdown="1">
<summary>안정성 및 회복 탄력성</summary>

<details markdown="1">
<summary>pgbouncer가 죽었을 때 어떻게 되는가?</summary>

- 현재 답 또는 검증 방법
</details>

</details>
```

## 예상 질문 정리

- 리뷰어·제품팀·운영자가 물을 질문과 답을 `**Q.** / A.` 쌍으로 쓴다
- 리뷰 루프에서 리뷰어가 낸 `expected_questions`를 여기로 모은다. 답이 아직 없으면 `A. (미결정) {판단 기준}`

## 마일스톤

- 날짜 또는 순서가 있는 표로 쓴다: `| 마일스톤 | 완료 기준 | 목표일 |`
- 완료 기준은 관측 가능한 상태로 쓴다(예: "dev 전 서비스가 PgBouncer 경유, 에러율 변화 없음 확인")
- 날짜를 모르면 목표일 칸에 `TBD`

## HTML 출력 구조 (정본)

`spec_tool.py render`만 HTML을 만든다. HTML을 손으로 쓰거나 고치지 않고, 바꿀 것이 있으면 `spec.md`나 템플릿을 고친 뒤 다시 렌더한다.
render는 아래 구조를 검사해 `structure.ok`가 false면 실패(exit 1)한다.

| 순서 | 블록 | 내용 |
|------|------|------|
| 1 | 메타 줄 | 날짜, 라벨(초안·브리핑), 리뷰 라운드와 심각도 칩 |
| 2 | H1 | 제목 |
| 3 | Objective | Objective 콜아웃 한 문장 |
| 4 | 목차 | "목차" 라벨이 있는 테두리 박스, H2 번호 목록과 그 아래 H3 |
| 5 | 결정 필요 배너 | `### 결정 필요`가 있을 때만. 건수, 필수·필수 아님 칩, 항목 이름(필수 먼저), 누르면 표로 이동 |
| 6 | 본문 | 고정 H2 순서. 결정 필요 표는 노란 강조 표, 필수 칸은 빨강·회색 칩, 행마다 "상세 보기" 버튼과 펼침 행, 표 위 "상세 모두 펼치기" |
| 7 | footer | 실행 폴더와 리서치 실행 이름 |

- 레이아웃: 노션 전체 너비 페이지 기준. 본문 폭 제한 없음, 좌우 여백 `clamp(16px, 6vw, 96px)`, 흰 배경 단일 라이트 테마
- 본문의 `(미결정 ...)`은 노란 표시로, 근거 `[@cNNN]`은 작은 위첨자로, mermaid 펜스는 다이어그램으로 렌더된다
- 브리핑처럼 Objective가 없는 문서는 3·5의 스펙 전용 검사를 건너뛴다
