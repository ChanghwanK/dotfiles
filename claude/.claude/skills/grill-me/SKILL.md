# grill-me: 설계 Decision Tree 검증 스킬

설계/계획의 모든 의사결정을 Decision Tree로 분해하고, 각 branch를 끈질기게 검증한다.
빈틈을 탐지하고 SOCRAAI 엔지니어링 원칙과의 정합성을 확인한다.

> 인터뷰 메커니즘(라운드·frontier·추천 답·사실/결정 분리)은 upstream
> [`mattpocock/skills` grilling](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md)
> `85f83d3`(2026-08-20) 기준으로 병합했다. upstream 갱신 시 이 커밋 이후의 grilling 변경분만 대조해 반영한다.

---

## 핵심 원칙

- **끈질긴 검증자**: 편의적 답변에 만족하지 않는다. "왜?", "대안은?", "영향은?"을 반복
- **Decision Tree 우선**: 설계를 의사결정 계층으로 분해한다 (Root → Child → Leaf)
- **라운드 단위 질문**: 선행 결정이 모두 확정된 질문(frontier)을 한 라운드에 번호를 매겨 한꺼번에 묻고, 질문마다 추천 답을 붙인다. 답을 받은 뒤 frontier를 다시 계산해 다음 라운드로 간다
- **사실은 에이전트가, 결정은 사용자가**: 코드·설정·환경에서 확인 가능한 사실은 사용자에게 묻지 않고 Explore Agent를 백그라운드로 보낸다. 설계 결정은 반드시 사용자에게 묻고 답을 기다린다
- **합의 확인은 가볍게**: 요약 끝에 확인을 한 번 묻는다. 사용자가 확인 없이 진행을 요청하면 막지 않고 진행하되, 사용자 답 없이 추천으로 채운 결정과 남은 미결을 먼저 밝힌다
- **SOCRAAI 원칙 연결**: 모든 branch에서 안정성 > 비용 > 가용성 수준 트레이드오프 체크

## Step 0: 입력 소스 결정

사용자 메시지와 대화 맥락을 분석하여 입력 소스를 자동 결정한다.

| 직전에 `/tasks:tech-spec` 세션이 있었음 | **Conversation 모드** | 대화 맥락에서 설계 의사결정 추출 |

| 파일 경로 언급 (예: `~/...yaml`, `kubernetes/src/...`) | **File 모드** | Read 도구로 파일 직접 로드 |
| 그 외 (일반 대화) | **Conversation 모드** | 현재 대화 맥락 분석 |

### eng-note 모드

업무 노트를 쓰기 전에 빈틈을 메우는 인터뷰다. 아직 스펙이 없으므로 "검증할 설계"보다 **노트 섹션을 채울
결정**을 끌어내는 데 초점을 둔다.

- **첫 질문은 항상 작업의 목적이다.** Decision Tree를 만들기 전에, 선택지를 주지 말고 열린 질문으로
  "이 작업이 끝나면 무엇이 달라져 있어야 하는가, 그걸 왜 원하는가"를 묻는다. 범위(설계만인지, 구현까지인지,
  적용까지인지)와 Non Goals는 이 답에서 Claude가 도출해 한 줄로 되묻고 확인만 받는다.
  - 목적이 확인되기 전에는 구현·셀프서비스·참조 사례처럼 범위를 넓히는 가정을 질문에 넣지 않는다.
  - 인터뷰 중 사용자가 범위를 좁히거나 목적을 다시 말하면, 앞서 확정한 노드 중 그 목적과 어긋나는 것을
    다시 열어 정리한다(버리거나 일반 원칙으로 옮긴다).
  - 실패 사례(2026-09-27 테라폼 모듈화 QA): 목적을 묻지 않고 "첫 모듈로 무엇을 만들까"부터 물어
    구현 전제가 끼어들었고, 셀프서비스 경계와 참조 설계까지 범위가 세 번 흔들렸다. 실제 목적은
    "좋은 모듈을 정의하는 표준 정책 설계"였다.
- Decision Tree의 Root 후보에 아래 4개 축을 반드시 포함한다(대화에 이미 확정된 축은 제외):
  - 문제·근본 원인: 현상이 아니라 메커니즘인가(`tasks:capture`의 "현상을 빼고 문제를 쓴다" 판별)
  - Before → After: 같은 축으로 대응되는가
  - Goals / Non Goals: 조건-결과 쌍으로 검증 가능한가, 범위 경계가 분명한가
  - 설계 선택: 이유와 기각한 대안이 있는가
- Step 5 후속 액션은 고정이다: 검증 결과(확정된 결정, 해소된 Gap, 남은 Gap)를 호출한 스킬에 돌려주고,
  호출한 스킬이 `tasks:tech-spec`으로 이어간다. A~D 선택지를 보여주지 않는다.

## Step 1: 설계 맥락 수집 및 의사결정 추출

로드된 소스에서 **명시적/암묵적 의사결정**을 추출한다.

**추출 대상:**
- "A 대신 B를 선택했다": 명시적 기술 선택
- "단순하게 유지한다": 범위 결정
- "비용 절감을 위해...": 제약 기반 선택
- "향후 확장을 고려해...": 미래 설계 가정
- "Dev/Stg 환경은 별도로...": 환경별 전략

**추출 메모 형식:**


## Step 2: Decision Tree 구축 및 제시

추출된 의사결정을 계층 구조로 분류한다.

### 노드 분류 기준

| 노드 타입 | 정의 | 예시 |
|-----------|------|------|
| **Root** | 전체 방향을 결정하는 핵심 선택 (1~3개) | "VictoriaMetrics를 직접 운영 vs AWS Managed" |
| **Child** | Root 결정에 종속된 선택 (2~4개/Root) | "단일 노드 vs 클러스터 모드" |
| **Leaf** | Child 결정에 종속된 구체적 설정 (0~2개/Child) | "retention 기간 30일 설정" |

### 트리 시각화 출력

```
## 설계 Decision Tree

🌳 Root 1: {결정 내용}
  ├─ 🌿 Child 1-1: {결정 내용}
  │   └─ 🍃 Leaf 1-1-1: {결정 내용}
  └─ 🌿 Child 1-2: {결정 내용}
      ├─ 🍃 Leaf 1-2-1: {결정 내용}
      └─ 🍃 Leaf 1-2-2: {결정 내용}

🌳 Root 2: {결정 내용}
  └─ 🌿 Child 2-1: {결정 내용}

총 {N}개 노드 ({R}개 Root, {C}개 Child, {L}개 Leaf)
```

트리 출력 후 사용자에게 확인:

```
이 트리로 첫 라운드를 시작할까요?
특정 branch부터 시작하고 싶으면 번호를 말씀해주세요. (예: "Root 2부터")
```

## Step 3: 라운드 단위 Socratic 인터뷰

### Frontier 계산

**frontier**는 선행 결정이 모두 확정되어, 아직 듣지 못한 답을 추측하지 않고 지금 물을 수 있는 질문의 집합이다.

1. 첫 라운드의 frontier는 보통 모든 Root 질문이다
2. 같은 라운드의 다른 질문 답에 따라 달라지는 질문은 이번 라운드에서 빼고 다음 라운드로 미룬다
3. 답을 받으면 확정된 결정이 frontier를 바깥으로 밀어낸다(Root가 확정되면 그 Child가 열린다). frontier를 다시 계산해 다음 라운드를 묻는다
4. frontier가 비면(모든 branch를 방문했고 암묵적 가정이 남지 않으면) 인터뷰를 끝내고 Step 4로 간다

### 라운드 출력 형식

한 라운드의 모든 질문을 아래 형식 하나로 낸다. 사용자는 번호로 답할 수 있다.

```
### Round {n} ({이번 라운드 질문 수}문항, 남은 노드 {m}개)

❓ **Q1** - **{질문 제목}** ({노드 번호, 예: Root 1 · 동기}): {질문 본문. 여러 문단 또는 선택지 가능}

➡️ {추천 답과 한 줄 근거}

---

❓ **Q2** - **{질문 제목}** ({노드 번호}): {질문 본문}

➡️ {추천 답과 한 줄 근거}
```

- 추천 답은 대화 맥락, 코드 탐색 결과, SOCRAAI 원칙에서 끌어낸다. 근거가 없으면 "추천 없음: {판단에 필요한 정보}"로 쓴다
- 사용자가 "추천대로"라고 답하면 그 라운드의 추천 답을 모두 결정으로 확정한다

### 노드별 질문 구성

아래는 frontier에 올릴 질문의 원천이다. 한 노드의 질문들은 서로 의존하지 않으면 같은 라운드에 함께 올린다.

**Root 노드 (3개 질문 순서):**

1. **동기(Why)**: "왜 {선택한 것}을 선택했나요? 해결하려는 핵심 문제는 무엇인가요?"
2. **대안(What-if)**: "가장 유력했던 대안은 무엇이었나요? 그것을 선택하지 않은 결정적 이유는?"
3. **영향(Impact)**: "이 선택이 잘못되었다면 어떤 방식으로 문제가 드러날까요? 롤백 전략은?"

**Child 노드 (1~2개 질문):**

1. **정합성(Consistency)**: "이 선택이 Root의 {부모 결정}과 어떻게 연결되나요?"
2. **비용/복잡도(Tradeoff)**: (선택적) "이 설정으로 인한 운영 부담은? 더 단순한 방법은 없었나요?"

**Leaf 노드 (0~1개 질문):**

1. **근거(Evidence)**: (복잡한 Leaf에만) "이 값은 어떻게 결정되었나요? 측정 근거가 있나요?"

### SOCRAAI 원칙 체크 질문

Root의 동기·대안·영향이 확정되면, 관련 원칙 체크 질문을 다음 라운드 frontier에 올린다. 질문 제목에
`SOCRAAI 원칙 체크 ({해당 원칙})`을 쓰고 형식은 라운드 출력 형식을 따른다.

| 원칙 | 체크 포인트 | 예시 질문 |
|------|------------|----------|
| 안정성 > 비용 > 가용성 수준 | 줄인 것이 가용성 수준인가, 안정성까지 깎았는가? | "이 결정에서 낮춘 것이 9의 개수·이중화 범위인가요, 아니면 가드레일·복구성인가요?" |
| Self-Service | 제품팀이 인프라 팀 없이 사용 가능한가? | "이 변경 후 제품팀이 자체적으로 뭘 할 수 있게 되나요?" |
| 비용 최적화 | Managed Service vs 오픈소스 비교가 있었나? | "비용 비교 시뮬레이션을 해보셨나요?" |
| 네트워크 최적화 | Cross-zone 통신, NAT GW 회피 고려? | "이 트래픽 경로에서 Cross-zone 비용이 발생하나요?" |
| Dev/Stg 비용 | 비프로덕션 환경이 과도하게 설계되지 않았나? | "Dev/Stg는 Single AZ로 운영하고 있나요?" |

### 코드베이스 탐색 분기 (사실 확인)

frontier 질문 중 답이 "현재 코드/설정을 보면 알 수 있는 사실"이면 사용자에게 묻지 않는다.
`agents/agent-codebase-explorer.md` 프롬프트로 **Explore Agent**를 백그라운드로 보낸다:

```
Agent(
  subagent_type: "Explore",
  prompt: agents/agent-codebase-explorer.md 내용 (question, scope 치환)
)
```

- 탐색을 기다리며 라운드를 멈추지 않는다. 진행 중인 탐색은 "확정되지 않은 선행 조건"으로 취급해, 그 결과에 의존하는 질문만 다음 라운드로 미루고 나머지 frontier는 지금 묻는다
- 라운드 머리에 `🔍 확인 중: {사실 항목}` 한 줄로 탐색 중인 항목을 알린다
- 결과가 오면 해당 노드를 🔍 Explored로 기록하고, 결과를 다음 라운드의 추천 답 근거로 쓴다
- 탐색 결과는 사실일 뿐 결정이 아니다. 결과가 설계 주장과 어긋나면 그 차이를 결정 질문으로 사용자에게 올린다
- Codex처럼 Agent 도구가 없는 런타임에서는 서브에이전트 대신 직접 읽기·검색으로 확인하고, 그 사실이 필요한 질문만 다음 라운드로 미룬다

| 키워드 | 동작 |
|--------|------|
| "패스", "pass", "건너뛰" (+ 질문 번호) | 해당 질문의 노드 Skip. 번호가 없으면 이번 라운드 전체 Skip. Branch 상태: Skipped |
| "추천대로" | 이번 라운드의 추천 답을 모두 결정으로 확정 |
| "충분해", "그만", "enough" | 인터뷰 즉시 종료, Step 4(요약) 진행 |
| "진행해", "그냥 해", "고쳐줘" 등 실행 요청 | 인터뷰를 종료하고 Step 4 "합의 확인" 절의 진행 요청 처리를 따른다 (되묻지 않는다) |
| "힌트" | 이 결정과 관련된 SOCRAAI 사례 또는 고려 기준 힌트 제공 |
| "코드 확인해줘" | Explore Agent를 명시적으로 spawn |

### Branch 상태 추적

인터뷰 중 각 노드 상태를 내부적으로 기록:

| 상태 | 의미 |
|------|------|
| ✅ Resolved | 사용자가 답했거나 "추천대로"로 채택해 근거가 확인됨 |
| 💬 Recommended | 사용자 답 없이 Claude 추천으로 채운 결정 (Resolved로 쓰지 않는다) |
| ⚠️ Gap | 근거 불충분 또는 추가 검토 필요 |
| 🔍 Explored | Explore Agent로 코드 확인 완료 |
| ⏭️ Skipped | 사용자가 패스 요청 |

---

## Step 4: 검증 요약

frontier가 비었을 때(또는 "충분해" 종료) 아래 형식으로 요약한다.

### 요약 출력 형식

```
## Grill-Me 검증 결과: {설계 제목}

### Decision Tree 결과 테이블

| # | 의사결정 | 타입 | 상태 | 비고 |
|---|----------|------|------|------|
| R1 | {결정 내용 요약} | Root | ✅ Resolved | {한 줄 요약} |
| C1 | {결정 내용 요약} | Child | ⚠️ Gap | {문제 요약} |
| L1 | {결정 내용 요약} | Leaf | 🔍 Explored | {확인 결과} |
| R2 | {결정 내용 요약} | Root | ⏭️ Skipped | - |

### 발견된 Gap 목록

| # | Gap 설명 | 심각도 | 권고 액션 |
|---|----------|--------|----------|
| 1 | {구체적인 빈틈} | 🔴 High / 🟡 Mid / 🟢 Low | {해결 방향} |

**심각도 기준:**
- 🔴 High: 배포 전 반드시 해결 (보안, 데이터 손실, 비용 급증 리스크)
- 🟡 Mid: 1주 내 해결 권고 (운영 부담, 확장성 우려)
- 🟢 Low: 나중에 개선 가능 (문서 부재, 최적화 여지)

### SOCRAAI 원칙 정합성

| 원칙 | 평가 | 코멘트 |
|------|------|--------|
| 안정성 > 비용 > 가용성 수준 | ✅ / ⚠️ / ❌ | {한 줄 평가} |
| Self-Service | ✅ / ⚠️ / ❌ | {한 줄 평가} |
| 비용 최적화 | ✅ / ⚠️ / ❌ | {한 줄 평가} |
| 네트워크 효율 | ✅ / ⚠️ / ❌ | {한 줄 평가} |
| Dev/Stg 비용 | ✅ / ⚠️ / ❌ | {한 줄 평가} |

### 권고 변경사항

{Gap이 있는 경우만 작성. 없으면 "특이사항 없음."}

1. {구체적 변경 제안 (파일 경로 또는 설정값 포함)}
2. {구체적 변경 제안}

이 요약이 우리가 합의한 이해와 맞나요? 다른 항목이 있으면 말씀해 주세요.
```

### 합의 확인

요약 끝에 확인을 한 번 묻는다. 막는 장치가 아니라 사용자가 무엇을 확정하지 않았는지 보이게 하는 장치다.

- **확인 또는 지적**: "맞다"면 Step 5로 간다. 어긋난 항목을 지적받으면 그 노드를 frontier에 다시 올려 라운드를 재개한다
- **진행 요청 (인터뷰 도중 포함)**: 되묻지 않고 진행한다. 진행 직전에 아래 블록만 먼저 출력한다

  ```
  진행합니다. 답을 받지 않고 추천으로 채운 결정: {노드: 채택한 추천}, ...
  남은 미결: {노드}, ... (이번 변경에 반영하지 않음)
  ```

- **예외 (질문 1개만)**: 미결 결정 중 하나를 고르지 않으면 변경 자체가 성립하지 않고(선택지가 서로 배타적), 추천도 없을 때만 그 하나를 묻는다
- 진행 요청으로 끝난 인터뷰도 Step 4 요약의 노드 상태는 💬 Recommended로 남긴다. 나중에 결과를 읽는 사람이 사용자 결정과 Claude 추천을 구분할 수 있어야 한다

---

## Step 5: 후속 액션 제안

요약 출력 후, 아래 후속 옵션을 제안한다. 표준 작업 워크플로우는 grill-me(작업 파악) → tech-spec(작성) →
업무 노트 반영이므로 A가 기본 추천이다. 인터뷰가 실제 작업에서 출발했다면 A를 추천으로 표시한다:

```
다음 중 어떻게 진행할까요?

A) 업무 노트로 정리 [추천] → /notion:add-engineering-note (이 인터뷰 결과를 넘겨 tech-spec으로 확정 후 저장)
B) 권고 변경사항 즉시 구현 → 관련 파일 직접 수정
C) 종료
```

### Option A: 업무 노트로 정리

사용자가 A를 선택하면:
1. 확정된 결정, 해소된 Gap, 남은 Gap, 권고 변경사항을 정리한다
2. `notion:add-engineering-note`를 Skill 도구로 호출하고 args에 위 정리와 "grill-me 인터뷰 완료(Step 1 생략)"를 넘긴다.
   노트 스킬은 인터뷰를 다시 하지 않고 `tasks:tech-spec`(Step 2)부터 이어간다

## 검증 (내부용)

인터뷰 시작 전 체크:

- [ ] Step 0 소스 감지가 완료되었는가
- [ ] Decision Tree에 최소 1개 Root 노드가 있는가
- [ ] 사용자가 트리 구조를 확인했는가

라운드마다 체크:

- [ ] 이번 라운드 질문이 서로 의존하지 않는가 (의존 질문은 다음 라운드로 미뤘는가)
- [ ] 모든 질문에 `➡️` 추천 답(또는 "추천 없음" 사유)이 붙었는가
- [ ] 코드로 확인 가능한 사실을 사용자에게 묻지 않았는가

인터뷰 종료 후 체크:

- [ ] frontier가 비었거나 사용자가 "충분해"로 종료했는가
- [ ] Step 4 요약에 Decision Tree 결과 테이블이 포함되었는가
- [ ] 사용자 답 없이 추천으로 채운 결정이 💬 Recommended로 표시되었는가 (진행 요청으로 끝났다면 진행 전에 밝혔는가)
- [ ] Gap이 있는 경우 심각도가 분류되었는가
- [ ] SOCRAAI 원칙 정합성 테이블이 작성되었는가
- [ ] Step 5 후속 액션이 제안되었는가
