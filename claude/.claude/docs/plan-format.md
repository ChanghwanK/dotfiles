# Plan 모드 출력 형식

플랜은 아래 순서로 작성합니다. 대괄호 `[ ]` 섹션은 조건부이며, 조건에 해당하지 않으면 제목째 생략합니다.
섹션 이름은 아래 표기를 그대로 씁니다. 같은 역할에 다른 이름(리스크, Risk, 배경, 트레이드오프와 위험 등)을
붙이면 렌더러·grep·플랜 간 비교가 깨집니다.

```
Summary → Context → [문제와 가설] → Goals → [Non-Goals] → [옵션 비교]
→ Steps → 완료 조건 (DoD) → [위험과 롤백] → 스텝별 상세 계획 → [가정] → [후속 판정] → [이해 점검]
```

- 하네스 기본 플랜 지시는 "Context 섹션으로 시작"을 요구합니다. 이 형식에서는 Context를 **Summary 바로 아래**에 둡니다 (두괄식 유지)
- 결정에 필요한 섹션(Summary~DoD, 위험과 롤백)이 위에, 실행 상세(스텝별 상세 이하)가 아래에 오도록 배치했습니다

## 템플릿

```
## Summary
- **무엇을**: (대상 및 목표, 한 문장)
- **어떻게**: (핵심 접근 방식, 한 문장)
- **범위/주의**: (영향 범위 또는 주의사항, 한 문장)

## Context
- (왜 이 변경을 하는가: 해결하려는 문제나 필요)
- (무엇이 촉발했는가: 관측값, 알럿, 요청)
- (의도한 결과)
- (사용자가 이미 확정한 결정)

## 문제와 가설  ← 조건부: 해결하려는 문제가 있을 때 (CLAUDE.md Hypothesis-First)
- **문제**: (지금 무엇이 문제인가 + 근거. 원인을 알면 포함, 모르면 (원인 미확인))
- **원인 가설**: (원인 미확인일 때만: 후보 x / z / 그 외, 후보별로 보여야 할 것, 변별 증거, 측정 결과)
- **가설**: (무엇을 적용하면 그 문제가 해결되는가)
  - **검증 기준 (적용 직후)**: (변경이 의도대로 걸렸는가. 알럿·기능이면 적용 전 백테스트)
  - **검증 기준 (결과)**: (무엇이 어느 방향으로 얼마나 바뀌면 문제가 풀린 것인가. 판정 기회가 없을 수 있으면 대리 지표)
- **검증 설계**: (필수: 무엇으로 재는가 / 측정이 그 신호를 잡는가(간격·범위·과거 구간·기준선) / 언제 판정하는가. 필요할 때: 어떻게 일으키는가, 틀렸을 때 원인을 가를 값)
- **반증 조건**: (이 관측이 나오면 틀린 것 + 그때의 원인 후보와 가르는 방법)
- **안 바뀔 것**: (이 변경이 고치지 않는 것 / 유지돼야 하는 정상 지표. 인프라·prod면 필수)
- **한계**: (해결하지 못하는 범위 + 이 변경이 새로 만드는 위험)

## Goals
- (이번 플랜이 달성하는 목표 1)
- (이번 플랜이 달성하는 목표 2)

## Non-Goals  ← 조건부: 범위 혼동 우려가 있을 때
- (이번 플랜에서 명시적으로 다루지 않는 것)

## Steps
1. (단계 1 요약)
2. (단계 2 요약)

## 완료 조건 (DoD)
- [ ] (검증 가능한 결과: 명령어 출력·리소스 상태·메트릭 등 측정 방법 포함)
- [ ] (예: `kubectl get pod -n santa | grep Running` 모두 Running)

## 위험과 롤백  ← 조건부: 인프라·prod·외부 산출물에 영향
- **Blast radius**: (영향받는 서비스·환경 범위)
- **실패 시나리오**: (잘못되면 어떤 장애가 나는가)
- **롤백**: (어떻게 원복하는가, 얼마나 걸리는가)

## 스텝별 상세 계획

### Step 1: {단계 제목}

1. (구체적 액션: 파일 경로 또는 명령어 포함)
2. (구체적 액션)

- **대상 파일**: `path/to/file`
- **재사용**: (따라갈 기존 패턴·함수와 경로, 해당 시)
- **검증**: (이 단계 완료 확인 방법)

## 가정  ← 조건부: 질문으로 닫지 못한 기본값이 남았을 때
- (가정한 기본값) / 틀리면 바뀌는 스텝: (Step N)

## 후속 판정  ← 조건부: 실행 후 기다려야 하는 판정이 있을 때
- YYYY-MM-DD: (판정 내용) / (판정 쿼리·명령) / (기준)

## 이해 점검  ← 조건부: 아래 "이해 점검 섹션" 조건
```

## 섹션별 규칙

### Summary
- 줄당 한 문장입니다. 세부 근거는 Context로 내립니다

### Context
- 하네스 기본 지시의 정의(왜 바꾸는가, 무엇이 촉발했는가, 의도한 결과)를 따릅니다
- 관측값과 사용자가 확정한 결정을 여기에 둡니다. 결정이 필요한 미결 사항은 여기에 묻지 않고 질문으로 닫거나 `## 가정`으로 뺍니다
- 문제의 근거와 겹치는 관측값은 `## 문제와 가설`에 두고, Context에는 촉발 사건과 확정된 결정만 남깁니다

### 문제와 가설
- 해결하려는 문제가 있는 플랜(트러블슈팅, 기능 개발, 개선, 재발 방지, 검증 시나리오)에 씁니다. 판별 질문과 항목 요건은 CLAUDE.md Hypothesis-First가 정본이며 여기서 재서술하지 않습니다
- 문장 틀은 고정하지 않습니다. 위 템플릿의 괄호는 채울 내용이지 문장 모양이 아닙니다
- `원인 가설`은 트러블슈팅에서 원인이 미확인일 때만 씁니다. 측정으로 확정된 원인은 `문제`에 사실로 적습니다
- 검증 기준을 기다려야 판정할 수 있으면(관찰 기간, 재발 여부) `## 후속 판정`에 날짜와 판정 쿼리를 둡니다
- 옵션이 여러 개면 선택의 근거와 트레이드오프는 `## 옵션 비교`에 둡니다
- 단순 조회, 문서 한 줄 수정, 해결할 문제 없이 이미 결정된 기계적 실행이면 생략합니다

### Steps
- 제목은 접미사 없이 정확히 `## Steps`로 씁니다. `plan-todo.py`가 이 제목만 인식해 frontmatter TODO를 만듭니다 (`## Steps (7개)`는 TODO가 비어 버립니다)
- 각 스텝은 이 세션에서 실행하고 바로 체크할 수 있는 단위입니다. "24시간 관찰 후 판정"처럼 기다려야 하는 항목은 Steps에 넣지 않고 `## 후속 판정`으로 뺍니다. Steps에 넣으면 실행이 끝나도 플랜이 active로 남습니다

### 완료 조건 (DoD)
- plan **전체**의 수용 기준이며, 스텝별 `검증`은 해당 단계 내부 확인용입니다 (역할이 다름)
- 검증 가능한 결과(명령어 출력, 리소스 상태, 메트릭 임계값, 산출물 존재) 중심으로 쓰고, 주관적 표현("잘 동작한다", "문제 없다")은 쓰지 않습니다
- 후속 판정으로 뺀 항목은 DoD에 넣지 않습니다

### 위험과 롤백
- 인프라·prod·외부 산출물에 영향을 주면 필수입니다 (CLAUDE.md 2장). 영향 범위가 자명하면(오타, 문서 한 줄) 생략합니다
- 수용하는 잔여 위험도 이 섹션에 둡니다

### 스텝별 상세 계획
- 자명하지 않은 스텝만 씁니다. Steps 한 줄로 충분한 스텝은 생략합니다
- `재사용`: 새 코드·설정을 만들기 전에 따라갈 기존 패턴(같은 차트를 쓰는 다른 circle, 기존 함수·스크립트)을 경로와 함께 적습니다

### 가정
- 미결 질문은 ExitPlanMode 전에 AskUserQuestion으로 닫는 것이 기본입니다
- 닫지 못한 기본값만 적고, 항목마다 "틀리면 어느 스텝이 바뀌는가"를 붙입니다

### 후속 판정
- 플랜이 완료되면 `plan-todo.py`가 후속 판정 건수를 안내합니다. 이때 각 항목을 Notion Task(`tasks:capture`, due = 판정일)로 등록하자고 사용자에게 제안합니다
- 로컬에 별도 추적 목록을 만들지 않습니다 (할 일은 Notion Task로 단일화)

### 옵션 비교
설계 과정에서 복수의 접근 방식이 존재할 때만 씁니다. 옵션이 1개뿐이면 생략합니다.

```
## 옵션 비교

### Option A: (옵션명)
- **장점**: (핵심 이점)
- **단점**: (트레이드오프/리스크)

### Option B: (옵션명)
- **장점**: (핵심 이점)
- **단점**: (트레이드오프/리스크)

**추천**: Option X: (선택 이유 한 줄)
```

- 추천에는 반드시 선택 이유를 적습니다
- 본문(Steps 이하)에는 추천안만 씁니다. 기각안은 이 섹션에만 남깁니다

## 이해 점검 섹션 (조건부)

플랜을 승인하기 직전이 blast radius와 설계 선택을 스스로 확인하기에 가장 좋은 지점입니다.
아래 조건 중 **하나라도** 해당하면 플랜 **맨 끝**에 `## 이해 점검` 섹션을 추가합니다.

- prod 또는 인프라 컴포넌트를 건드림
- 되돌리기 어려운(one-way door) 변경을 포함

조건에 해당하지 않으면 섹션을 아예 생략합니다 (스텝 수만 많은 플랜에 퀴즈가 붙는 노이즈 방지).
렌더러는 섹션이 없으면 패널을 그리지 않으므로 별도 처리가 필요 없습니다.

```
## 이해 점검

### Q1 (초급): (정의형 질문)
- **모범답안**: (1~2문장)

### Q2 (중급): (메커니즘형 질문)
- **컨텍스트**: (선택적, 질문 이해에 필요한 배경 한 줄)
- **모범답안**: (동작 원리 중심 답변)

### Q3 (고급): (트레이드오프형 또는 blast radius형 질문)
- **모범답안**: (선택의 대가, 깨지는 조건까지)
```

- 문항은 **3개**, 난이도는 초급(정의형) → 중급(메커니즘형) → 고급(트레이드오프/blast radius형) 순서
- 모두 **이 플랜에서 직접 파생**시킵니다. 범용 질문("K8s란?") 금지
- 들여쓰기 없는 평문으로 작성합니다 (렌더러가 중첩 불릿을 파싱하지 않음)
- `**모범답안**:` 다음 줄부터 다음 `###`까지가 답변 본문이므로, 여러 줄·코드블록·불릿 모두 사용 가능합니다
- 답변은 브라우저 프리뷰에서 입력창으로 렌더되며, "논의" 제출 시 Claude에게 전달되어 채점됩니다.
  즉 정답을 숨기는 장치가 아니라 **논의의 입력**입니다 (정답은 플랜 원문에 이미 보입니다)
