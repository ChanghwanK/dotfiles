# Code Quality Convention

이 문서는 코드 작성, 수정, 리팩터링, 테스트 작성 시 사용하는 전역 품질 기준입니다.
`CLAUDE.md` 또는 `AGENTS.md`에는 짧은 진입점만 두고, 세부 판단은 이 문서를 참조합니다.

## 핵심 정의

좋은 코드는 단순히 짧거나 보기 좋은 코드가 아닙니다.
좋은 코드는 미래의 변경자가 의도를 이해하고, 영향 범위를 예측하고, 기대 동작을 검증할 수 있는 코드입니다.

가독성은 포맷만의 문제가 아니라 아래 3가지의 합입니다.

- **의도**: 이 코드가 왜 존재하고 어떤 정책을 표현하는지 드러나는가?
- **경계**: 어디까지가 이 코드의 책임이고, 어디를 바꾸면 위험한지 보이는가?
- **검증 가능성**: 기대 동작이 테스트, 타입, 검증, 에러 처리로 확인 가능한가?

## 판단이 충돌할 때 우선순위

Kent Beck의 Simple Design 네 규칙을 위에서부터 적용합니다. 위 규칙이 아래 규칙보다 우선합니다.

1. 테스트나 검증으로 기대 동작이 확인된다
2. 의도를 드러낸다, 같은 지식이 두 곳에 없다 (두 규칙은 같은 순위이며 서로를 강화합니다)
3. 요소(클래스, 함수, 추상화)가 가장 적다

- 요소를 줄이려고 의도를 희생하지 않습니다. 이름 붙은 함수를 하나 더 뽑아 의도가 드러난다면 요소가 늘어도 그쪽을 택합니다.
- 무엇이 중복인지는 코드 모양이 아니라 같은 이유로 함께 바뀌는지로 판단합니다(기준: "5. 추상화 기준").

## 코드 작업 기본 원칙

- 겉보기의 간결함보다 유지보수 가능한 명확성을 우선합니다.
- 기존 코드베이스의 패턴을 먼저 따릅니다.
- 변경 범위는 전역 하드 가드레일 Surgical Changes를 따릅니다.
- 새 추상화는 실제 복잡도를 줄이거나 책임 경계를 명확히 할 때만 도입합니다.
- 테스트 보강은 변경 위험도와 blast radius에 맞춰 결정합니다.

## 1. 의도를 드러내는 코드

- 변수명, 함수명, 타입명, 상수명은 도메인 의미를 담아야 합니다.
- `data`, `result`, `handler`, `process` 같은 넓은 이름은 작은 스코프에서 의미가 명확할 때만 사용합니다.
- magic number, magic string, 상태값은 named constant 또는 enum으로 표현합니다.
- 조건문은 가능한 한 비즈니스 규칙이 읽히게 작성합니다.
- 짧지만 추론이 필요한 코드보다, 조금 길어도 판단 근거가 보이는 코드를 선호합니다.

```ts
// 부족한 코드
if (user.type === 2 && score > 80) {
  upgrade(user)
}

// 더 좋은 코드
if (user.isPaidMember && score >= PREMIUM_ELIGIBILITY_SCORE) {
  promoteToPremiumCandidate(user)
}
```

## 2. 책임 경계가 명확한 구조

- 함수 하나가 여러 책임을 동시에 갖지 않게 합니다.
- 도메인 로직, I/O, 외부 API 호출, 포맷 변환, 영속성 처리는 가능한 한 분리합니다(부수효과를 다루는 방식: 아래 "부수효과 격리").
- 추상화는 내부를 숨기기 위해서가 아니라 변경 경계를 명확히 하기 위해 사용합니다.
- 너무 잘게 나눠 실행 흐름이 흐려지는 구조는 피합니다(판단 기준: 아래 "함수 추출 기준").
- 기준은 함수 길이가 아니라 "변경 시 영향 범위를 예측할 수 있는가"입니다.

### 부수효과 격리

부수효과(상태 변경, I/O, 외부 호출)는 없앨 수 없으므로 정해진 곳에 모으고 이름으로 드러냅니다.

- 계산·판단 로직은 순수 함수로 작성합니다. 입력은 인자로만 받고 결과는 반환값으로만 냅니다. 부수효과는 호출하는 쪽 가장자리(핸들러, 서비스 진입점)에 모읍니다.
- 값을 돌려주는 메서드(Accessor, 질의)는 상태를 바꾸지 않습니다. 상태를 바꾸는 메서드(Mutator, 명령)는 값을 돌려주지 않습니다(Command-Query Separation).
- 인자로 받은 객체를 고쳐서 결과를 전달하는 출력 파라미터를 쓰지 않고 새 값을 반환합니다.
- 예외: 읽기와 쓰기가 원자적이어야 하는 연산(pop, compare-and-set, 원자적 증가)은 둘로 나누면 경쟁 상태가 생기므로 합칩니다. 대신 이름(`pop`, `take`, `incrementAndGet`)으로 쓰기가 일어남을 드러냅니다.
- 단위 테스트에 mock이 많이 필요하면 계산과 부수효과가 섞였다는 신호입니다.

```ts
// 부족한 코드: 조회처럼 보이는데 상태를 바꾼다
nextInvoiceNo(): number {
  this.counter += 1
  return this.counter
}

// 더 좋은 코드: 질의와 명령을 나눈다
peekNextInvoiceNo(): number {
  return this.counter + 1
}

advanceInvoiceNo(): void {
  this.counter += 1
}
```

### 함수 추출 기준

추출 기준은 줄 수가 아니라 의도와 구현의 분리입니다. 추출한 뒤 호출하는 쪽을 읽을 때 함수 본문을 열어 보지 않아도 되면 좋은 추출입니다.

- 이름에 "그리고"를 넣지 않고 무엇을 하는지 말할 수 있을 때 추출합니다. 이름이 방법(`loopAndCheck`)이나 넓은 말(`process`)이 되면 추출 단위를 다시 잡습니다.
- 이름은 책임의 경계입니다. 새로 넣으려는 코드가 이름과 맞지 않으면 그 함수에 넣지 않고 새 함수를 만듭니다.
- 파라미터가 많거나, 출력 파라미터나 여러 반환값이 필요하면 의미가 아니라 줄 수로 자른 신호입니다.
- boolean 플래그로 동작이 갈리는 함수는 함수 둘로 나눕니다.
- 본문이 이름만큼 명확하거나 간접 호출이 흐름을 가리면 다시 인라인합니다(Inline Function).

### private 메서드 판별 기준

private 메서드 자체는 문제가 아닙니다. 판단 기준은 "private이냐 아니냐"가 아니라
**이 메서드가 조작하는 데이터의 주인이 누구인가**입니다.

- 그 함수가 속한 클래스/모듈 자신의 상태만 다루는 단순 헬퍼(포맷 변환, 파싱, 짧은 절차 분해)라면
  private로 그대로 둡니다.
- 파라미터로 받은 다른 객체의 데이터를 계속 꺼내 쓰며 판단·계산 로직을 수행한다면(Feature Envy),
  그 로직은 원래 그 객체가 가져야 할 책임입니다. 해당 객체로 옮겨 public 메서드로 만듭니다.
- 이 private 메서드를 독립적으로 테스트하고 싶다는 충동이 든다면, 그 자체가 설계 신호입니다.
  독립적으로 검증할 가치가 있는 로직은 대개 별도 책임이며, 별도 객체의 public 메서드로 뽑아내면
  "private을 어떻게 테스트하지" 라는 질문 자체가 사라집니다.

```ts
// 부족한 코드: OrderService가 order의 데이터를 계속 꺼내 판단한다 (Feature Envy)
class OrderService {
  confirm(order: Order) {
    if (this.isEligibleForDiscount(order)) {
      this.applyDiscount(order)
    }
  }

  private isEligibleForDiscount(order: Order): boolean {
    return order.totalAmount > 100_000 && order.memberGrade === "VIP"
  }

  private applyDiscount(order: Order) {
    order.totalAmount *= 0.9
  }
}

// 더 좋은 코드: 판단·계산 로직을 order 자신에게 위임한다 (Tell, Don't Ask)
class Order {
  isEligibleForDiscount(): boolean {
    return this.totalAmount > 100_000 && this.memberGrade === "VIP"
  }

  applyDiscount() {
    this.totalAmount *= 0.9
  }
}

class OrderService {
  confirm(order: Order) {
    if (order.isEligibleForDiscount()) {
      order.applyDiscount()
    }
  }
}
```

## 3. 주석 기준

- 주석은 코드가 이미 말하는 "무엇"을 반복하지 않습니다.
- 주석은 코드에 드러나지 않는 "왜"를 설명합니다.
- 비즈니스 예외, 운영 제약, 과거 장애에서 나온 우회, 트레이드오프는 주석으로 남길 수 있습니다.
- 코드와 맞지 않는 주석은 없는 것보다 위험하므로, 변경 시 함께 수정하거나 제거합니다.
- 여러 파일에 공통으로 적용되는 아키텍처 결정(계층 규칙, 패턴 선택 이유 등)은 컨벤션
  문서(`CLAUDE.md`/프로젝트 `CODE_CONVENTION.md`)에 한 번만 적고, 개별 파일 docstring·
  주석에 반복 서술하지 않습니다. 파일 안에는 그 결정에서 벗어나거나 그 파일에서만
  성립하는 예외·트레이드오프만 남깁니다.
- 판별 질문: "이 설명이 프로젝트의 다른 유사한 파일에도 똑같이 적용되는가?" 그렇다면
  전역/프로젝트 컨벤션 문서로 옮기고, 그 파일만의 사정이면 로컬 주석으로 남깁니다.

```ts
// 나쁜 주석
// user를 필터링한다
const users = allUsers.filter(user => user.active)

// 좋은 주석
// 비활성 계정은 결제 상태가 남아 있어도 캠페인 대상에서 제외한다.
// CS에서 수동 복구하는 계정이 포함되면 중복 쿠폰이 발급될 수 있다.
const eligibleUsers = allUsers.filter(user => user.active)
```

## 4. 테스트 코드 기준

좋은 테스트 코드는 기대 동작을 읽을 수 있는 문서이자 변경 안전장치입니다.

- 테스트 이름은 구현 방식이 아니라 정책 또는 사용자에게 관찰되는 동작을 설명합니다.
- Given / When / Then 흐름이 자연스럽게 읽히도록 작성합니다.
- 내부 구현 디테일보다 외부에서 관찰 가능한 결과를 우선 검증합니다.
- 정상 케이스뿐 아니라 경계값, 실패 케이스, 권한 없음, 중복 요청, 이미 처리된 상태, 시간/타임존, 외부 의존성 실패를 필요에 따라 포함합니다.
- 테스트 데이터는 의도를 드러내야 하며, 의미 없는 랜덤 값이나 과도하게 현실적인 fixture는 피합니다.
- 하나의 테스트는 보통 하나의 이유로 실패해야 합니다.
- 테스트는 결정적이어야 합니다. 실제 시간, 랜덤 값, 네트워크, 공유 상태, 실행 순서에 의존하지 않게 제어합니다.
- 테스트 helper는 반복 노이즈를 줄이되, 시나리오의 의미를 숨기지 않아야 합니다.

```ts
it("does not issue coupons to inactive paid users", () => {
  const user = createUser({ active: false, subscription: "paid" })

  const result = issueCoupon(user)

  expect(result).toEqual({ issued: false, reason: "INACTIVE_USER" })
})
```

## 5. 추상화 기준

- 중복이 보인다는 이유만으로 추상화하지 않습니다.
- 같은 이유로 함께 변경되는 코드라면 추상화 후보입니다.
- 서로 다른 정책이 우연히 비슷한 모양을 가진 경우에는 명시적 중복이 더 안전할 수 있습니다.
- generic helper에 flag, mode, 예외 조건이 계속 늘어나면 추상화가 잘못된 신호입니다.
- 호출자가 내부 주의사항을 알아야만 안전하게 쓸 수 있다면 좋은 추상화가 아닙니다.

## 6. 변경 안전성 기준

- 타입, 인터페이스, validation으로 잘못된 사용을 가능한 한 앞에서 막습니다.
- 에러 메시지는 운영자나 개발자가 원인을 좁힐 수 있게 작성합니다.
- 중요한 도메인 규칙은 한 곳에서 확인 가능해야 합니다.
- 리팩터링은 기존 동작을 보존해야 하며, 보존 여부를 테스트 또는 명확한 검증으로 확인합니다.

## 작업 전 체크리스트

코드 변경 전 다음을 확인합니다.

- 증상 해결인지 근본 원인 해결인지, 기존 패턴과 다르면 그 이유가 정리됐는가? (기준: 전역 CLAUDE.md "조건부 덧붙임")
- 변경 경계가 요청 범위에 맞게 작게 잡혔는가? (Surgical Changes)
- 테스트 또는 검증으로 기대 동작을 확인할 수 있는가?
- 실패했을 때 원복 방법이 명확한가?

## 작업 후 체크리스트

코드 변경 후 다음을 확인합니다.

- 이름과 구조만으로 의도가 읽히는가?
- 책임 경계가 흐려진 부분은 없는가?
- 값을 돌려주는 함수가 상태를 바꾸지 않고, 계산 로직에 I/O가 섞이지 않았는가?
- 추출한 함수는 본문을 열지 않고 이름만으로 읽히는가?
- 주석은 필요한 이유만 설명하는가?
- 테스트가 정책, 경계값, 실패 조건 중 변경 위험에 맞는 부분을 보호하는가?
- 새 추상화가 실제 복잡도를 줄였는가?
