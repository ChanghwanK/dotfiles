# PAR 성과 문장 포맷 표준

경력기술서·성과평가용 PAR(Problem / Action / Result) 문장의 **단일 출처**다.
소비하는 스킬은 이 문서를 Read로 읽어 그대로 적용하며, 규칙을 요약하거나 재정의하지 않는다.

이력서 work experience의 **1줄 bullet 포맷은 이 문서 대상이 아니다**. 그쪽은
`~/.claude/docs/resume-format-convention.md`를 따른다. 두 문서의 관계는 다음과 같다.

| 산출물 | 표준 문서 | 성격 |
|--------|-----------|------|
| 이력서 1줄 bullet | `resume-format-convention.md` | 압축, 명사형 종결, 정량 대괄호 표기 |
| 경력기술서·성과평가 PAR | 이 문서 | 맥락과 판단 근거를 남기는 서술형 |

## 1. PAR 구성

- **Problem**: `Situation + Pain/Risk/Goal`
  - Situation: 어떤 운영·비즈니스·개발 맥락이었는가
  - Pain/Risk: 그 상황에서 무엇이 병목·위험·비효율이었는가
  - Goal: 그래서 무엇을 개선해야 했는가
- **Action**: 본인이 어떤 판단으로 무엇을 실행했는가
- **Result**: 그 결과 무엇이 측정 가능하게 달라졌는가

## 2. 공통 작성 규칙

- **Problem은 기술이 아니라 필요를 쓴다**: "기술을 썼다"가 아니라 "어떤 상황에서 왜 그 기술적 개입이
  필요했는가"를 쓴다.
- **Action은 기여가 드러나는 동사로 시작한다**: 설계, 표준화, 자동화, 마이그레이션, 최적화, 검증, 문서화.
- **기여 범위를 구분한다**: 본인이 직접 수행한 것과 팀·타 조직과 협업한 것을 섞지 않는다. 협업 항목은
  "OO팀과 협업하여"처럼 역할을 명시한다. 팀 성과를 1인칭 단독 성과로 쓰지 않는다. 면접·평가에서 가장
  먼저 검증되는 지점이므로 애매하면 범위를 좁게 쓴다.
- **판단이 갈렸던 지점을 남긴다**: 초기 가설이 틀려 정정한 과정이 있으면 Action에 포함한다. 진단의
  깊이는 정정 과정에서 드러난다.
- **Result는 측정된 값만 쓴다**: 수치가 없으면 "정성 결과"로 표시하고 과장하지 않는다. 숫자가 없을 때는
  "추적 가능성 개선", "롤백 경로 명확화"처럼 검증 가능한 변화만 쓴다.
- **성과가 여러 개면 임팩트 순으로 최대 3개**까지 작성한다.

## 3. 표기 프로파일

산출물이 놓이는 매체에 따라 레이블 표기와 구조가 다르다. 소비 스킬이 프로파일을 지정한다.

### 프로파일 A: 채팅 간이형

터미널·채팅에 바로 출력하는 경우다. 레이블은 볼드로 쓰고 그룹핑하지 않는다.

```
**Problem**
{Situation + Pain/Risk/Goal, before 수치}

**Action**
{구체적 방법과 그 방법을 택한 이유. 기여 범위. 판단이 갈렸던 지점이 있으면 포함}

**Result**
{정량 결과. 목표 대비 달성도까지 명시할 수 있으면 포함}
```

사용자가 이 내용을 Notion에 옮기겠다고 하면 프로파일 B의 레이블 표기 규칙을 안내한다.

### 프로파일 B: Notion 문서형

Notion Task·Eng Note에 남기는 경우다. 레이블 표기와 그룹핑이 모두 필수다.

- **레이블 스타일**: 상위 불릿의 레이블(`Problem:` / `Action:` / `Result:`)은 이탤릭(`*...*`)으로
  처리한다. 볼드나 색상은 적용하지 않는다.
- **레이블 중첩**: 레이블만 상위 불릿에 두고, 내용은 들여쓴 하위 불릿에 둔다. 레이블과 내용을 한 줄에
  붙여 쓰지 않는다.
- **Action / Result 그룹핑 (필수)**: 평평한 불릿 나열로 쓰지 않고 `레이블 → 볼드 그룹 헤드라인 →
  세부 항목`의 3단 구조로 쓴다.

| 항목 | 기준 |
|------|------|
| 그룹 수 | Action 3~5개, Result 2~4개 |
| 그룹당 세부 | 2~4개. 1개뿐이면 그룹으로 묶을 이유가 없으니 상위 그룹에 합친다 |
| Action 그룹 축 | **판단 단위**로 나눈다. 시간 순서가 아니라 "어떤 결정을 했는가"가 그룹이 된다 |
| Result 그룹 축 | **효과 성격**으로 나눈다. 즉시 복구 / 리스크 해소 / 재발 방지 산출물처럼 시점과 지속성이 다른 것을 섞지 않는다 |
| 그룹 헤드라인 | 명사구가 아니라 동사구로 쓴다. "진단"(X) → "하이퍼바이저 계층까지 하강해 원인 특정"(O) |
| 세부 항목 | 근거가 되는 수치·명령·대조 결과를 포함한다. 추상어만 남기지 않는다 |

**그룹핑이 드러내는 것**: 순서를 뒤집은 판단, 하나의 선택으로 두 문제를 푼 구조, 조사의 깊이는 평평한
나열에서 전부 묻힌다. 그룹 헤드라인이 의사결정 목록으로 읽혀야 한다.

**Problem은 그룹핑 대상이 아니다.** 맥락 한 덩어리이므로 레이블 + 하위 불릿 1~2개로 둔다. 억지로
쪼개지 않는다.

```
### PAR 성과 문장

**대표 PAR**
- *Problem:*
    - {Situation + Pain/Risk/Goal: 어떤 맥락에서 왜 중요한 문제였는가}
- *Action:*
    - **{판단 그룹 1: 무엇을 왜 했는가가 읽히는 동사구}**
        - {세부 실행: 구체적 명령·수치·판단 근거}
        - {세부 실행}
    - **{판단 그룹 2}**
        - {세부 실행}
        - {세부 실행}
- *Result:*
    - **{효과 그룹 1: 즉시 복구된 것}**
        - {측정된 결과: 수치 우선}
        - {측정된 결과}
    - **{효과 그룹 2: 해소된 리스크 또는 재발 방지 산출물}**
        - {검증된 정성 결과}

**이력서 bullet** (표준 포맷: `~/.claude/docs/resume-format-convention.md`)
- {해당 문서 규칙에 따라 1줄로 압축}

**성과평가용 확장형**
- {Situation과 Pain/Risk/Goal}. 이를 해결하기 위해 {판단 기준과 실행 내용}. 그 결과 {측정된 효과와
  팀·운영 관점의 의미}.
```

## 4. 품질 체크

출력 전 아래를 점검하고 위반 항목은 고친 뒤 출력한다.

**공통**

- [ ] Problem 없이 Action만 있지 않은가 (있으면 단순 업무 나열이다)
- [ ] Result 없이 Action만 있지 않은가 (있으면 성과가 아니라 활동 기록이다)
- [ ] Action 없이 Result만 있지 않은가 (있으면 본인의 기여가 불명확하다)
- [ ] 본인 기여와 협업 범위가 구분돼 있는가
- [ ] 수치가 없는 항목을 검증 가능한 정성 표현으로 썼는가 (막연한 표현 금지)

**프로파일 B 추가**

- [ ] Action / Result이 평평한 불릿 나열이 아닌가 (그룹 헤드라인 + 세부 항목 구조인가)
- [ ] Action 그룹 헤드라인만 읽었을 때 의사결정 목록으로 읽히는가 (시간 순서로 나뉘어 있으면 축이 틀렸다)
- [ ] Result 그룹에 즉시 효과와 향후 가치가 섞여 있지 않은가
- [ ] 세부 항목이 1개뿐인 그룹이 없는가
- [ ] 레이블이 이탤릭이고 내용이 하위 불릿으로 중첩됐는가

## 5. 적용 범위

- `task:review` 스킬 Part A.5 "PAR 성과 문장" (프로파일 B)
- `resume:bullet` 스킬 Step 3 "경력기술서 PAR 생성" (프로파일 A)
- `notion-review` 에이전트가 `### PAR 성과 문장` 섹션이 포함된 Task 문서를 리뷰할 때 (프로파일 B)
