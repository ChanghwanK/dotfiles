# PAAR 성과 문장 포맷 표준

경력기술서·성과평가용 PAAR(Problem / Analyze / Action / Result) 문장의 **단일 출처**다.
소비하는 스킬은 이 문서를 Read로 읽어 그대로 적용하며, 규칙을 요약하거나 재정의하지 않는다.

> 파일명은 `par-format-convention.md`를 유지한다. 2026-09-10에 PAR 3요소에서 PAAR 4요소로 전환했으며,
> 파일명을 바꾸면 이 문서를 참조하는 스킬·에이전트 5곳의 경로를 함께 바꿔야 하므로 이름은 그대로 둔다.

이력서 work experience의 **1줄 bullet 포맷은 이 문서 대상이 아니다**. 그쪽은
`~/.claude/docs/resume-format-convention.md`를 따른다. 두 문서의 관계는 다음과 같다.

| 산출물 | 표준 문서 | 성격 |
|--------|-----------|------|
| 이력서 1줄 bullet | `resume-format-convention.md` | 압축, 명사형 종결, 정량 대괄호 표기 |
| 경력기술서·성과평가 PAAR | 이 문서 | 맥락과 판단 근거를 남기는 서술형 |

## 1. PAAR 구성

| 요소 | 답해야 하는 질문 | 내용 |
|------|------------------|------|
| **Problem** | 어떤 문제가 있었나 | `Situation + Pain/Risk/Goal` |
| **Analyze** | 어떤 선택지를 비교했고 왜 그 선택을 했나 | 가설·대안 후보, 비교 축, 기각 근거, 선택의 대가·깨지는 조건 |
| **Action** | 무엇을 실행했나 | 본인이 실제로 수행한 것. 판단은 Analyze에 두고 여기에는 실행만 남긴다 |
| **Result** | 어떤 결과가 나왔고 어떻게 측정했나 | 측정 가능하게 달라진 것과 그 측정 방법 |

- **Problem**
  - Situation: 어떤 운영·비즈니스·개발 맥락이었는가
  - Pain/Risk: 그 상황에서 무엇이 병목·위험·비효율이었는가
  - Goal: 그래서 무엇을 개선해야 했는가
- **Analyze**
  - 후보: 검토한 가설(진단 작업) 또는 대안(구현 작업)을 나열한다
  - 비교 축: 무엇을 기준으로 비교했는가 (우리 제약: 비용, 운영 부담, 위험도, 실측 근거)
  - 기각 근거: 버린 후보를 왜 버렸는가
  - 선택의 대가 또는 깨지는 조건: 채택한 것이 무엇을 포기했고 어떤 상황에서 무효가 되는가
- **Action**: 본인이 무엇을 실행했는가
- **Result**: 그 결과 무엇이 측정 가능하게 달라졌고, 무엇으로 측정했는가

**Analyze와 Action을 분리하는 이유**: PAR 3요소에서는 "왜 그 방법이었는가"가 Action 안에 섞여
실행 목록에 묻혔다. 면접·평가에서 검증되는 것은 실행량이 아니라 판단이므로, 판단을 별도 요소로
꺼내 그것만 읽어도 의사결정이 재구성되게 한다.

## 2. 공통 작성 규칙

- **Problem은 기술이 아니라 필요를 쓴다**: "기술을 썼다"가 아니라 "어떤 상황에서 왜 그 기술적 개입이
  필요했는가"를 쓴다.
- **Analyze는 기각한 후보로 판단을 보인다**: 선택한 방법의 장점만 쓰면 벤더 문서 요약과 구분되지
  않는다. 검토했다 버린 후보를 최소 1개, 그 기각 근거(우리 제약에 비춰 왜 아니었는가)와 함께 남긴다.
  여기에 선택의 대가(무엇을 포기했는가)와 깨지는 조건(어떤 상황에서 이 선택이 무효가 되는가) 중
  최소 하나를 덧붙인다. 대안 검토가 실제로 없었으면 지어내지 말고 "대안 검토 없음"으로 명시한다.
- **판단이 갈렸던 지점을 Analyze에 남긴다**: 초기 가설이 틀려 정정한 과정이 있으면 포함한다. 진단의
  깊이는 정정 과정에서 드러난다.
- **Analyze에는 실행 세부를 쓰지 않는다**: 명령어·파일 경로·적용 절차는 Action 몫이다. Analyze에
  남는 것은 후보, 비교 근거, 결론이다. 반대로 Action에는 "왜"를 다시 쓰지 않는다.
- **Action은 기여가 드러나는 동사로 시작한다**: 설계, 표준화, 자동화, 마이그레이션, 최적화, 검증, 문서화.
- **기여 범위를 구분한다**: 본인이 직접 수행한 것과 팀·타 조직과 협업한 것을 섞지 않는다. 협업 항목은
  "OO팀과 협업하여"처럼 역할을 명시한다. 팀 성과를 1인칭 단독 성과로 쓰지 않는다. 면접·평가에서 가장
  먼저 검증되는 지점이므로 애매하면 범위를 좁게 쓴다.
- **Result는 측정된 값과 측정 방법을 쓴다**: 수치가 없으면 "정성 결과"로 표시하고 과장하지 않는다.
  숫자가 없을 때는 "추적 가능성 개선", "롤백 경로 명확화"처럼 검증 가능한 변화만 쓴다. 어떤 지표·도구로
  측정했는지를 함께 적어 전후 비교가 재현 가능하게 한다.
- **진행 중인 작업은 단계를 명시한다**: 원인 특정만 끝나고 개선이 미적용이면 Result에 "원인 특정 단계,
  개선 미적용"처럼 상태를 적는다. 진단 결과를 개선 효과처럼 쓰지 않는다.
- **성과가 여러 개면 임팩트 순으로 최대 3개**까지 작성한다.

## 3. 표기 프로파일

산출물이 놓이는 매체에 따라 레이블 표기와 구조가 다르다. 소비 스킬이 프로파일을 지정한다.

### 프로파일 A: 채팅 간이형

터미널·채팅에 바로 출력하는 경우다. 레이블은 볼드로 쓰고 그룹핑하지 않는다.
Analyze의 후보 비교는 표로 써도 된다.

```
**Problem**
{Situation + Pain/Risk/Goal, before 수치}

**Analyze**
{검토한 후보와 비교 축. 기각 근거. 채택한 것의 대가 또는 깨지는 조건. 정정한 가설이 있으면 포함}

**Action**
{실행한 것. 기여 범위}

**Result**
{정량 결과와 측정 방법. 목표 대비 달성도까지 명시할 수 있으면 포함. 진행 단계}
```

사용자가 이 내용을 Notion에 옮기겠다고 하면 프로파일 B의 레이블 표기 규칙을 안내한다.

### 프로파일 B: Notion 문서형

Notion Task·Eng Note에 남기는 경우다. 레이블 표기와 그룹핑이 모두 필수다.

- **레이블 스타일**: 상위 불릿의 레이블(`Problem:` / `Analyze:` / `Action:` / `Result:`)은
  이탤릭(`*...*`)으로 처리한다. 볼드나 색상은 적용하지 않는다.
- **레이블 중첩**: 레이블만 상위 불릿에 두고, 내용은 들여쓴 하위 불릿에 둔다. 레이블과 내용을 한 줄에
  붙여 쓰지 않는다.
- **Analyze / Action / Result 그룹핑 (필수)**: 평평한 불릿 나열로 쓰지 않고 `레이블 → 볼드 그룹
  헤드라인 → 세부 항목`의 3단 구조로 쓴다.

| 항목 | 기준 |
|------|------|
| 그룹 수 | Analyze 2~4개, Action 2~4개, Result 2~4개 |
| 그룹당 세부 | 2~4개. 1개뿐이면 그룹으로 묶을 이유가 없으니 상위 그룹에 합친다 |
| Analyze 그룹 축 | **판단 단위**로 나눈다. "어떤 결정을 했는가"가 그룹이 된다. 시간 순서가 아니다 |
| Action 그룹 축 | **실행 단위**로 나눈다. 어떤 대상·계층에 무엇을 적용했는가. Analyze의 결정 하나가 Action 그룹 하나에 대응되면 가장 읽기 쉽다 |
| Result 그룹 축 | **효과 성격**으로 나눈다. 즉시 복구 / 리스크 해소 / 재발 방지 산출물처럼 시점과 지속성이 다른 것을 섞지 않는다 |
| 그룹 헤드라인 | 명사구가 아니라 동사구로 쓴다. "진단"(X) → "하이퍼바이저 계층까지 하강해 원인 특정"(O) |
| 세부 항목 | 근거가 되는 수치·명령·대조 결과를 포함한다. 추상어만 남기지 않는다 |

**그룹핑이 드러내는 것**: 순서를 뒤집은 판단, 하나의 선택으로 두 문제를 푼 구조, 조사의 깊이는 평평한
나열에서 전부 묻힌다. Analyze 그룹 헤드라인만 읽으면 의사결정 목록으로, Action 그룹 헤드라인만
읽으면 실행 목록으로 읽혀야 한다.

**Problem은 그룹핑 대상이 아니다.** 맥락 한 덩어리이므로 레이블 + 하위 불릿 1~2개로 둔다. 억지로
쪼개지 않는다.

```
### PAAR 성과 문장

**대표 PAAR**
- *Problem:*
    - {Situation + Pain/Risk/Goal: 어떤 맥락에서 왜 중요한 문제였는가}
- *Analyze:*
    - **{판단 그룹 1: 무엇을 비교해 무엇을 택했는가가 읽히는 동사구}**
        - {후보와 비교 축}
        - {기각 근거 또는 선택의 대가}
    - **{판단 그룹 2}**
        - {후보와 비교 축}
        - {기각 근거 또는 깨지는 조건}
- *Action:*
    - **{실행 그룹 1: 어디에 무엇을 적용했는가가 읽히는 동사구}**
        - {세부 실행: 구체적 명령·파일·수치}
        - {세부 실행}
    - **{실행 그룹 2}**
        - {세부 실행}
        - {세부 실행}
- *Result:*
    - **{효과 그룹 1: 즉시 복구된 것}**
        - {측정된 결과: 수치 우선, 측정 방법}
        - {측정된 결과}
    - **{효과 그룹 2: 해소된 리스크 또는 재발 방지 산출물}**
        - {검증된 정성 결과}

**이력서 bullet** (표준 포맷: `~/.claude/docs/resume-format-convention.md`)
- {해당 문서 규칙에 따라 1줄로 압축}

**성과평가용 확장형**
- {Situation과 Pain/Risk/Goal}. {검토한 후보와 그중 이것을 택한 이유}. 이를 위해 {실행 내용}.
  그 결과 {측정된 효과와 팀·운영 관점의 의미}.
```

## 4. 품질 체크

출력 전 아래를 점검하고 위반 항목은 고친 뒤 출력한다.

**공통**

- [ ] Problem 없이 Analyze·Action만 있지 않은가 (있으면 단순 업무 나열이다)
- [ ] Analyze 없이 Action만 있지 않은가 (있으면 "왜"가 없는 활동 기록이다)
- [ ] Result 없이 Action만 있지 않은가 (있으면 성과가 아니라 활동 기록이다)
- [ ] Action 없이 Result만 있지 않은가 (있으면 본인의 기여가 불명확하다)
- [ ] Analyze에 기각한 후보가 1개 이상 근거와 함께 있는가 (실제로 없었으면 "대안 검토 없음"으로 명시했는가)
- [ ] Analyze에 선택의 대가 또는 깨지는 조건이 1개 이상 있는가
- [ ] Analyze에 실행 세부(명령·경로·절차)가 섞여 있지 않은가, Action에 "왜"가 반복되지 않는가
- [ ] 본인 기여와 협업 범위가 구분돼 있는가
- [ ] Result에 측정 방법이 있는가, 진행 단계(개선 미적용 등)가 명시돼 있는가
- [ ] 수치가 없는 항목을 검증 가능한 정성 표현으로 썼는가 (막연한 표현 금지)

**프로파일 B 추가**

- [ ] Analyze / Action / Result이 평평한 불릿 나열이 아닌가 (그룹 헤드라인 + 세부 항목 구조인가)
- [ ] Analyze 그룹 헤드라인만 읽었을 때 의사결정 목록으로 읽히는가 (시간 순서로 나뉘어 있으면 축이 틀렸다)
- [ ] Action 그룹 헤드라인만 읽었을 때 실행 목록으로 읽히는가
- [ ] Result 그룹에 즉시 효과와 향후 가치가 섞여 있지 않은가
- [ ] 세부 항목이 1개뿐인 그룹이 없는가
- [ ] 레이블이 이탤릭이고 내용이 하위 불릿으로 중첩됐는가

## 5. 적용 범위

- `task:review` 스킬 Part A.5 "PAR 성과 문장" (프로파일 B)
- `resume:bullet` 스킬 Step 3 "경력기술서 PAR 생성" (프로파일 A)
- `alfred` 스킬 gate 모드 6단계가 task:review를 인라인 수행할 때 (프로파일 B)
- `notion-review` 에이전트가 `### PAR 성과 문장` 섹션이 포함된 Task 문서를 리뷰할 때 (프로파일 B)

소비처의 섹션 제목·설명 문구에 남아 있는 "PAR"은 이 문서의 PAAR을 가리킨다. 소비처는 요소 구성을
자체 정의하지 않고 이 문서의 4요소를 따른다.
