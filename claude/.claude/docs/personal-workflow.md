# 개인 업무 방식

정본입니다. 학습 세션, 면접 준비, 경력 문서, 브리핑, Notion Task, 에이전트 실험을 할 때 Read합니다.
Notion 문장·포맷은 `docs/notion-writing-style.md`, 이력서 bullet은 `docs/resume-format-convention.md`, PAR은 `docs/par-format-convention.md`가 정본입니다.

## 학습

- 개념 학습 요청에는 우리 클러스터 현황을 조회해 답하지 않는다. 사용자가 명시한 학습 기준(예: flannel)이나 범용 모델로 설명하고, "이걸 알면 무엇을 판단·디버깅할 수 있나"를 축으로 구성한다(증상 → 의심 지점). 학습용 글 목차·실험 설계에도 적용한다
- `/learn` 세션의 질문 노트(`질문_노트.md`) 저장 방식은 learn 스킬이 정본이다

### 이해 점검 형식

응답에 붙이는 이해 점검의 형식이다. 언제 붙이는지는 전역 CLAUDE.md "조건부 덧붙임"이 정하고, 플랜의 `## 이해 점검` 섹션은 `docs/plan-format.md`가 정한다. 세 문항 모두 방금 설명한 핵심 개념에서 직접 파생하고, 범용 질문은 내지 않는다. 사용자가 답하면 짧게 피드백하고, 건너뛰면 바로 넘어간다.

```
---
**이해 점검** (건너뛰려면 다음 질문으로 넘어가세요)
- **초급**: {정의형 질문}
- **중급**: {메커니즘형 질문}
- **고급**: {실무 연계형 또는 트레이드오프형 질문}
```

## 면접 준비

- 이력서·경력기술서 기반 면접은 개념 퀴즈로 시작하지 않는다. "이 작업을 소개해 주세요: 어떤 문제였고, 어떻게 접근했고, 결과는?"으로 열고, 답에 나온 판단·수치·기각안을 꼬리 질문으로 판다
- 오프닝 멘트는 결과를 아는 사람의 요약이 아니라 발견 순서로 쓴다: 문제(관측된 증상·영향만, 원인 단어 없이) → 접근(무엇을 먼저 의심했고 어떻게 좁혔나) → 검증에서 처음 원인 이름이 나옴 → 결과
- 사용자가 자기 말로 요약하면 세부 오차를 표·수치로 정정하지 않는다. 그 요약이 면접 답변으로 통하면 30초~1분 멘트로 다듬어 주고, 틀린 부분은 멘트 안의 한 구절로 바로잡는다
- 상황해결형 기술 면접 질문은 한 문장의 열린 질문으로 낸다. 상황극 서사, 제품명, 답의 힌트가 되는 키워드, 다음 질문 목록을 보여 주지 않는다. 어투는 가벼운 해요체다(이 맥락에 한해 전역 격식체의 예외). 피드백·모범답안 단계에서는 키워드를 써도 된다

## 경력 문서

- 사용자가 제공한 문서(경력기술서·이력서 PDF 등)의 수치와 서술을 정본으로 쓴다. Notion·wiki·git으로 수치를 재검증하지 않는다. 사용자가 "검증해 줘"라고 할 때만 대조한다
- 자기소개·경력 문안은 "~해 왔습니다"처럼 실제로 한 일로 쓴다. "~관점에서 일합니다" 같은 관점 선언은 쓰지 않는다
- 포트폴리오는 문제 해결 목록으로만 구성한다. 항목마다 문제 상황 → 접근 방법 → 해결 → 성과 4단을 회사별로 나열한다. 묶음 섹션, "일하는 방식" 요약, 단계 라벨·색 칩·수치 카드는 쓰지 않는다. 넓은 페이지에서 왼쪽은 글, 오른쪽은 Before/After 그림 두 열로 둔다(Artifact 정리형 페이지 스타일의 예외)

## 브리핑과 Task

- 브리핑의 Task 정렬은 마감 임박도가 1차 축이다: 오늘 마감 → 기한 초과 → 이번 주 마감 → 마감 없음. 같은 묶음 안에서는 상태(진행 중 → 해야 할 것 → 대기) 순이다
- 브리핑에서 Task·일정 나열은 표가 아니라 목록으로 쓰고, 메타데이터는 항목 끝에 괄호로 붙인다
- Task는 개인 Task DB(`tasks:manage/scripts/notion-task.py`가 쓰는 DB, `Category` MY/WORK)에만 등록한다. 팀 dashboard에 넣지 않는다. 회고·개인 기록은 MY다
- 완료는 `상태=완료` 하나로 판단한다(`update-status --status "완료"`). Done 체크박스·Priority·ROI 속성은 DB에 없다
- 본격 Task를 만들 때는 `Type`(Task/Project)을 확인 화면에서 함께 확정한다. 단순 메모는 묻지 않고 Task로 둔다
- Notion 페이지·Task를 만들거나 고친 뒤 보고할 때는 항상 페이지 URL을 붙인다
- "기대 가치"나 "개선하면 무엇이 좋아지나"에는 사용자 시나리오로 답한다: 평상시 모습 / 알럿·운영자가 겪는 변화 / 장애 여유 / 대가 / 달라지지 않는 것. 지표 표·검증 쿼리·판정일은 기대 가치가 아니라 `검증 기준:` 자리에 둔다
- `/alfred gate`는 항목마다 묻지 않는다. 세션 근거로 초안을 모두 채우고 한 번만 확인받는다. 리스크 신호가 있는데 공유 여부가 불명확할 때만 예외로 묻는다

## 에이전트 실험

- 스킬 행동 QA에서 구현을 유도하는 턴을 보낼 때는 worktree 격리만 믿지 않는다. 대상 파일을 `chmod a-w`로 잠그고 해시를 기록한 뒤 보내고, 끝나면 권한을 복구한다. 턴 전후로 메인 체크아웃과 worktree의 `git status`를 모두 확인한다
