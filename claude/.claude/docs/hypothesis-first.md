# Hypothesis-First: 문제와 가설을 먼저 세우고 검증한다

정본입니다. 전역 CLAUDE.md의 "Hypothesis-First" 진입점이 이 문서를 가리킵니다.
플랜(`## 문제와 가설`), PR 본문, Task·업무 노트, RCA 결론을 쓰기 전에 읽습니다.

## 언제 쓰는가

- 언제 쓰는지(판별 질문, 생략 대상)와 경량 등급의 세 항목은 전역 CLAUDE.md "Hypothesis-First"가 정본이다. 이 문서는 전체 등급(인프라·prod·되돌리기 어려운 변경, 원인 미확인 트러블슈팅)과 플랜·PR·Task·RCA에 쓰는 항목을 정한다
- 트러블슈팅은 "왜 이런가"(원인 가설)를, 기능·개선은 "풀 가치가 있는 문제인가"(문제 가설)를 먼저 묻는다
- 경량 등급은 판정일을 "후속 판정 자격"이 있을 때만 둔다. 아래 "(필수)" 표시는 전체 등급에 적용한다
- 흐름은 루프다: 모델 → 문제 → (현상 확정 → 원인 가설) → 가설 → 반증 우선 → 검증 설계 → 신뢰도·결정 → 판정·갱신 → 모델

## 모델 (전체 등급, 코어 앞)

- "이 시스템이 이렇게 동작한다고 나는 믿는다"를 한 줄로 적는다. 원인 후보와 가설은 이 모델에서 나온다
- 후보가 전부 기각되면 "후보가 아니라 모델이 틀렸다"로 올라간다. 후보 집합 자체가 틀린 실패를 다루는 자리는 여기뿐이다

## 문제

- 관측된 사실이나 확인 가능한 결함을 쓴다. 추측은 문제가 아니다. 문장은 장치·절차·경계의 결함으로 쓰고, 시각·횟수 같은 관측값은 근거로 내린다
- 근거는 번호를 붙인 하위 불릿으로 나누고, 관측 근거와 원인 근거를 분리한다. 원인 근거에는 대조(변별 증거)를 담는다
- **근거 품질**: 근거마다 출처·측정 범위·시간창을 적는다. 부정 근거("없었다", "0건")는 탐지기가 그 사건을 잡았을 것임을 먼저 보인다. 증거가 소실됐으면 그 사실을 적고 주장 강도를 낮춘다
- **문제 가설**: 증상이 풀 가치가 있는지(사용자 영향이 있는가, 노이즈·known issue는 아닌가)는 사실이 아니라 가설이다. 근거를 붙이거나 "풀 가치 미확인"으로 둔다
- 측정으로 확정된 원인은 문제 서술에 사실로 쓴다. 모르면 `(원인 미확인)`(전역 CLAUDE.md "작업 원칙")으로 두고 아래 "원인 가설 단계"를 먼저 거친다

## 가설

- 형식(무엇을 하면 → 어떤 동작 때문에 → 어떤 결과)은 전역 CLAUDE.md "Hypothesis-First"를 따르고, 위 문제를 겨냥해야 한다
- 틀릴 수 있어야 한다. 적용해도 검증 기준이 충족되지 않는 경우를 상상할 수 없으면 가설이 아니라 기계적 실행이다
- **검증 기준을 시점별로 나눈다**:
  - 적용 직후: 변경이 의도대로 걸렸는가, 그리고 가설의 "어떤 동작 때문에"가 실제로 걸렸는지 보여 주는 값(메커니즘 확인)
  - 결과: 무엇이 어느 방향으로 얼마나 바뀌면 문제가 풀린 것인가. 크기가 없는 "개선될 것"은 쓰지 않는다
  - 알럿·기능은 적용 전 백테스트(과거 사건 구간에서 발화, 그 외 0회)와 적용 후 관찰로 나눈다
- **반증 우선**: "이 가설이 틀렸다면 가장 먼저 어긋날 관측" 하나를 고르고, 확인 증거보다 먼저 본다

## 검증 설계

- (필수) **무엇으로 재는가**: 지표·쿼리·명령. 다른 사람이 다시 돌릴 수 있어야 한다
- (필수) **측정이 그 신호를 실제로 잡는가** (착수 전에 확인한다)
  - 측정 간격이 이벤트 길이보다 짧은가
  - 측정 범위가 결과를 다 덮는가 (알럿 상태인가, 실제 도착인가)
  - 지표가 존재하고 과거 사건 구간에서 신호가 보이는가 (백테스트)
  - 변경 전 값(기준선)을 이미 쟀는가. 기준선이 이미 목표값이면 그 기준은 반증력이 없으니 다른 기준을 고른다
- (필수) **언제 판정하는가**: 적용 직후인가 관찰 기간 뒤인가, 판정일
- (필요할 때) **어떻게 일으키는가**: 백테스트, 합성 입력, dev 재현, 대조군, 제거 실험, prod 관찰 중 무엇인가. prod에서 장애를 일부러 재현하지 않는다
- (필요할 때) **틀렸을 때 원인을 가를 수 있는가**: 반증 조건에서 가르는 데 쓸 값을 이 측정이 함께 남기는가
- **대리 지표 제한**: 결과를 판정할 기회가 낮으면 "어떻게 일으키는가"가 필수다. 그것도 불가능하면 "결과 검증 불가"를 명시하고 주장 강도를 낮춘다. 적용 직후 값만으로 문제가 풀렸다고 판정하지 않는다(아래 "적용 상태가 곧 결과인 변경"은 예외)

## 보조 항목 (전체 등급)

- **반증 조건**: 이 관측이 나오면 가설이 틀린 것이다. 틀렸을 때의 원인 후보와 그 둘을 가르는 방법까지 쓴다
- **안 바뀔 것**: 이 변경이 고치지 않는 것, 그리고 유지돼야 하는 정상 지표. 인프라·prod 변경에는 필수다
- **한계**: 이 적용이 해결하지 못하는 범위와, 이 변경이 새로 만드는 위험. 추가 측정이나 추가 액션의 후보가 된다

## 원인 가설 단계 (트러블슈팅, 원인 미확인일 때)

0. **현상을 먼저 확정한다.** 원시 증상 → 메커니즘 수준 분류 → 둘을 가르는 측정값 순서로 적는다. "OOM", "timeout"은 이미 해석이 들어간 이름이라, 그 이름을 붙이는 순간 가설 하나를 채택한 것이다(예: exit 137은 종료 사유로 OOMKilled와 probe 실패를 가른다)
1. 후보를 둘 이상 세우고 "그 외"도 둔다
   - 경쟁 후보(같은 층에서 배타적인 설명)와 인과 사슬(깊이가 다른 고리)을 구분한다. 사슬을 경쟁으로 놓으면 둘 다 참인데 하나를 버린다
   - 여러 조건이 동시에 참이어야 생기는 경우는 "진짜 원인 하나"를 고르지 않는다. 충분조건 집합과 그중 바꿀 고리를 찾는다
2. 후보마다 "이게 원인이라면 무엇이 보여야 하는가"를 적는다
3. **변별 증거**를 고른다: 후보들이 서로 다른 결과를 예측하는 관측. 모든 후보에서 똑같이 보이는 관측은 아무것도 가르지 못한다
4. 측정(대조군, 재현, 제거 실험)으로 기각하거나 확정한다. 관측과 추론을 구분해 표시하고, 변별력이 크고 비용이 싼 것부터 잰다. "그 외"만 남으면 모델 항으로 올라간다
5. 확정되면 원인을 문제 서술에 사실로 채운다. 확정하지 못한 채 행동해야 하면 `(원인 미확인)`을 유지하고, 가설의 반증 조건이 원인 판정을 겸한다
   - **신뢰도 등급**: 관측 일치만 / 변별 증거 / 재현 또는 제거 실험. prod·되돌리기 어려운 변경은 변별 증거 이상에서 행동한다. 등급 미달로 행동하면 그 사실과 되돌리는 방법을 함께 적는다

## 후속 판정 자격

- 판정을 기다려야 하는 결과 기준은 판정 날짜를 정해 후속 판정으로 남긴다. 항목 형식은 `docs/plan-format.md` "후속 판정"을 따른다
- **후속 판정은 적용한 방법의 결과 검증 기준만 담는다.** 한계(이 변경이 못 막는 틈)나 새 위험을 지켜보는 항목은 후속 판정이 아니다. 한계 항목에 적고, 필요하면 별도 알럿이나 Task로 다룬다
- 판정 기회가 관찰 기간 안에 자연히 오는지 기저율로 먼저 확인한다. 오지 않으면 강제로 일으킬 방법을 정하거나, "결과 검증 불가"로 적고 후속 판정을 두지 않는다
- 적용 상태가 곧 결과인 변경(알럿 규칙 삭제 → 그 알럿 발화 0)은 적용 직후 검증으로 종료한다. 적용과 결과 사이에 동작 고리가 하나라도 있으면(설정 → 런타임 동작 → 지표) 예외가 아니다

## 판정과 갱신

- 빗나가면 숨기지 않는다. 모델의 어느 믿음이 어떻게 바뀌었는지를 쓴다
- 이 문서의 개정 기준은 전역 CLAUDE.md "규칙 생애주기"를 따른다

## 반영처

- 플랜: `## 문제와 가설` (형식은 `docs/plan-format.md`)
- Task·업무 노트: `문제` / `근본 원인` / `기대 가치` 섹션, `*가설:*`·`*검증 기준:*` 라벨 (Notion 템플릿이 이 이름을 씀)
- PR 본문: 문제와 가설(검증 기준)을 먼저 쓰고, 그 아래 변경 전 값 / 기대 값 / 검증 쿼리
- 검증 시나리오·테스트 케이스·DoD 판정 기준을 사람이 읽는 문서에 쓸 때는 `docs/verification-scenario.md`를 따른다

## 안티패턴: 형식만 빌려 쓰기

- 용량 추정치를 검증 기준으로, 롤백 임계값을 반증 조건으로, 한계·위험 감시를 후속 판정으로 적는 것은 형식 차용이다
- 검증 기준은 문제가 풀렸는지에 대한 관측이고, 반증 조건은 가설이 틀렸음을 보이는 관측이다. 롤백 임계값이 필요하면 별개 항목으로 적는다

## 점검 질문

1. 문제에 근거가 붙어 있고, 부정 근거는 탐지기 검증을 거쳤는가
2. 가설이 그 문제를 겨냥하고, 틀릴 수 있는가
3. 검증 기준을 보고 제3자가 "풀렸다/안 풀렸다"를 판정할 수 있는가
4. 측정이 그 신호를 실제로 잡는가 (간격, 범위, 과거 구간 신호, 기준선)
5. 전체 등급이면 모델이 적혀 있고, 후보와 가설이 거기서 나왔는가
6. 반증 관측을 확인 증거보다 먼저 봤는가

**왜**: 가설은 결과를 본 뒤에도 만들 수 있지만 검증 기준은 그럴 수 없다. 변경 전에 숫자로 적어야 반증할 수 있다. 검증 기준이 충족되면 "확인"만 얻고, 빗나가면 멘탈 모델의 오류 위치라는 더 비싼 정보를 얻는다.
