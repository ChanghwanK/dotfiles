# 이력서 Work Experience 포맷 표준

이력서 work experience 항목(bullet)의 표준 작성 포맷이다. `task:review` 스킬의 "이력서 bullet" 출력이
이 기준을 참조한다.

경력기술서/성과평가용 문장(PAAR 구조: Problem/Analyze/Action/Result 레이블 + 서술형)은 이 표준의 적용 대상이
**아니다**. 그쪽 표준은 `~/.claude/docs/par-format-convention.md`가 단일 출처다.

## 핵심 구조

한 줄에 **상황 → 규명(근본 원인) → 설정값 before → after → 대표 성과(배수 등)** 를 압축하고, **명사형으로 종결**한다.
이 뼈대(상황·규명·설정값·배수)는 필수다.

```
{발생 상황(트리거)} 후 {병목}으로 인한 {증상}을 {근본 원인}으로 규명,
{구체 설정} {before → after} 상향 및 {보조 조치}로 {대표 성과}
```

- 왜 이 뼈대인가: 추상 요약형은 어떤 상황에서 무엇을 진단했고 무엇을 바꿨는지가 보이지 않아 면접관이
  꼬리 질문을 걸 고리가 없다. 트리거, 진단 동사(규명), 실제 설정값(before → after)이 드러나야 기술 깊이가 읽힌다.
- 성과는 비율 지표(0.31% → 0.03%)보다 "최대 N배 단축" 같은 체감 성과를 우선한다.

## 규칙

- **명사형 종결 필수**: "~했습니다", "~합니다" 같은 문장형 종결을 쓰지 않는다. 개선/해결/절감/구현/전환/완료
  같은 명사형으로 끝맺는다.
- **Before 수치를 Problem 절에 포함**: 가능하면 "[N건/월] 발생하던"처럼 문제 발생 시점의 수치를 함께 적는다.
  Before 수치가 없으면 생략하되, After 수치(Result)는 반드시 있어야 한다. 정성 결과만 있을 때도 검증
  가능한 표현("추적 가능성 확보", "롤백 경로 확보")을 쓰고 막연한 표현("잘 됨", "개선됨")은 쓰지 않는다.
- **설정값은 before → after로 표기**: 바꾼 구체 설정을 `125 → 250 MiB/s`처럼 화살표로 드러낸다.
  대표 성과는 "최대 10배 단축"처럼 배수·체감 수치로 쓰고, 대괄호(`[N분→M분]`) 표기는 선택이다.
- **기술명은 Action의 근거로만 사용**: 기술 나열이 아니라 "왜 그 방법을 택했는지"가 드러나야 한다.
- **1줄 압축, 최대 2줄**: 긴 배경 설명은 넣지 않는다.
- **실측 수치가 없을 때**: `[N건]`, `[N%]` 같은 플레이스홀더로 남기고, 실제 작성 시 반드시 실측치로
  치환해야 함을 표기한다. 가짜 수치를 채워 넣지 않는다.
- **글자수**: 공백 포함 110자 이내 권장(90자면 더 좋음). 단 뼈대(상황·규명·설정값·배수)가 우선이다.
  뼈대를 지키느라 110자를 조금 넘는 것은 허용한다(확정 예시는 119자). 넘치면 뼈대를 자르지 말고 보조
  디테일을 경력기술서 PAAR로 내린다.
- **Result 대괄호에는 성과 1개만**: 병기해도 최대 2개(`[즉시 식별 / MTTR N분→M분]`)까지. 3개 이상
  들어가면 성과 선별이 안 된 것이므로 가장 강한 1개를 고른다.
- **근본 원인은 한 구절만, 진단 서사·구현 디테일 금지**: 뼈대의 "{근본 원인}으로 규명"처럼 원인을 한 구절로
  적는 것은 허용한다(필수). 다만 "왜 그렇게 발화했는지"의 원인 분석 서사, 룰/API/스크립트 이름 같은
  구현 경로는 bullet에 넣지 않는다. 그 내용은 경력기술서 PAAR의 Analyze·Action 몫이다.
- **구현 산출물 수치는 성과 수치가 아니다**: 룰 개수, 파일 수, PR 수 같은 산출물 증가는 Result로 쓰지
  않는다. Result는 독자에게 가치가 읽히는 지표(시간, 비용, 에러율, 가용 경로)여야 한다.
- **사내/내부 고유명사 금지**: 외부 면접관이 아는 수준(AWS 서비스명, 일반 기술명)까지만 허용한다.
  내부 알럿 룰 이름, 사내 시스템명, 특정 도구의 API 이름은 일반 용어로 바꾼다.

## 예시

- (뼈대 기준 예시, 사용자 확정 2026-09-26) "Consolidation 후 Image Pull 병목으로 인한 파드 시작 지연을 root
  볼륨 처리량 포화로 규명, gp3 throughput 125 → 250 MiB/s 상향 및 이미지 경량화로 최대 10배 단축"
- "Istio Ingress Gateway 재배치 후 [N건/월] 5xx를 preStop/SIGTERM 순서 문제로 규명, NLB draining
  [N → M초] 조정 및 preStop 드레이닝으로 5xx [N건 → 0건]"
- "CronJob 실행 시 디스크 병목으로 인한 지연·데이터 유실을 gp2 burst 한계로 규명, 볼륨 gp2 → gp3
  전환으로 유실 [N건 → 0건]·지연 [N분 → M분] 해소"
- "AWS 비용 점검 중 과다 지출을 idle 리소스와 On-Demand 위주 구매로 규명, rightsizing 및
  On-Demand → Spot/RI 전환으로 비용 [50% 절감 ($100K/month)]"

## 나쁜 예 (수정 전)

- "Kubernetes 클러스터를 운영하고 OpenTelemetry Operator를 업그레이드함" (문제·결과 없이 활동만 나열)
- "~을 통해 보안을 개선했습니다" (문장형 종결, 결과 미정량)
- "이미지 풀 스톰 시 노드 볼륨 처리량 천장으로 5분을 넘던 파드 기동을, A/B 실측 기반 처리량 상향과 이미지
  경량화로 개선 [5분 초과 기동 92% 감소]" (추상 요약형: 트리거·규명·실제 설정값 before → after가 없다.
  위 뼈대 기준 예시로 수정)
- "단일 SEARCH 룰이 전 prod Aurora DB의 slow query를 무차원 합산 발화해 대상 DB 식별이 불가하던 알럿을,
  CloudWatch metricName 기반 DB별 분리(Grafana provisioning API)와 runbook 연동으로 재구성 [1룰→6룰,
  발화 라벨만으로 대상 DB 즉시 식별 / 조회→개선 셀프서비스 대응 경로] 확보"
  (PAAR 내용물을 한 줄에 압축한 형태: 진단 서사 포함, 내부 고유명사 과다, 대괄호에 성과 3개,
  구현 산출물 수치(1룰→6룰)를 성과로 사용, 110자 초과)
  → 수정: "prod Aurora slow query 알럿 발화 시 대상 DB 식별 불가를 전 DB 합산 단일 알럿 구조로 규명,
  알럿 단일 → DB별 분리 및 runbook 연동으로 MTTR [N분 → M분] 단축"

## 적용 범위

이 문서가 이력서 bullet 포맷의 **단일 출처**다. 아래 소비처는 규칙을 요약·재정의하지 않고 이 문서를
읽어 그대로 적용한다.

- `task:review` 스킬 Part A.5 "이력서 bullet" 출력
- `resume:bullet` 스킬 Step 2(bullet 생성) 및 Step 5(출력 전 검증 체크리스트)
